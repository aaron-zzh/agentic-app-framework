# AAF-121 微信登录与扫码绑定设备

## 背景

AAF-120 的养老设备用"屏幕配对码加所有者用户"绑定，一期由运营在管理端代绑，家属端后置。家属自助绑定、服务号预警通知都需要两样东西：能在微信里识别家属是谁，以及一个能被微信扫开的绑定入口。当前这两样都没有。

登录侧的现状：

- 已有开放平台扫码登录：`WechatOAuthClient` 走 `qrconnect`（`snsapi_login`），换 token 后取 openid、昵称、头像，provider 为 `wechat`。流程由 `AuthController` 的 `/oauth/{provider}/url`、`redirect`、`callback`、`exchange`、`bind-url`、`bind`、`unbind` 提供，state 与交换码都是一次性的。
- 未绑定的微信用户首次扫码登录时，`AuthService.oauthLogin` 直接创建新用户并写入绑定。
- 绑定关系按 `(provider, provider_user_id)` 匹配，`sys_user_oauth` 没有 unionid 字段，代码里也没有处理 unionid。同一个人从服务号、小程序、开放平台进来，会被当成不同的人。
- 服务号只有消息适配器：`WechatMpChannelAdapter` 能收消息与事件、发客服消息、发模板消息，回调为 `/api/channel/wx/mp/callback`，默认关闭。
- 没有服务号网页授权登录、没有带参二维码、没有 `subscribe` 与 `SCAN` 事件的业务处理、没有粉丝管理，没有把服务号 openId 与 AAF 用户关联的流程。服务号 AccessToken 存在内存里，多实例部署不安全。

设备绑定侧的现状：

- 机器人调用 `POST /api/device/pair/start`，服务端生成 8 位配对码和设备凭据领取码 `deviceCode`，并返回 `qrContent = aaf://device/pair?deviceCode=…&pairCode=…`。
- `aaf://` 是自定义协议，微信扫到只当文本，不会跳转，也没有任何页面或小程序承接。后端、管理端、前端都没有处理该协议的代码，`DeviceCreateDTO` 只认 `pairCode`，没有扫码入口。
- 二维码里带了 `deviceCode`。机器人用它调用 `POST /api/device/pair/poll`，绑定完成后第一个轮询到的人领走一次性设备密钥（含 MQTT 接入信息）。配对码本来靠"看到设备屏幕"证明物理接近，现在二维码把领取凭据也一起暴露了：拍下或转发二维码的人，可以在绑定完成后抢先领走密钥。
- 创建设备接口走通用 CRUD，需要 `device:device:create` 权限，种子只授予管理员和养老运营角色，家属没有；绑定校验目前只检查对长者的 `VIEW_PROFILE` 授权范围。
- 设备所有者（计费主体）在创建时由请求指定，家属自助绑定的默认值没有定义。

## 目标

- 微信登录覆盖三个入口：电脑网页的开放平台扫码、电脑网页的服务号扫码关注、微信内 H5 的服务号网页授权。三个入口认出同一个人时进入同一个 AAF 账号。
- 服务号扫码关注登录同时让用户关注服务号，拿到服务号 openId，为预警模板消息提供接收人。
- 家属在微信里扫设备屏幕二维码，登录后选择长者即可完成设备绑定，不需要运营代办。
- 设备二维码不再暴露轮询凭据。

## 范围

- 账号模型：`sys_user_oauth` 增加 unionid，登录与绑定时按 unionid 打通同一人的多个入口。
- 开放平台扫码登录：补 unionid 记录与合并规则，核实前端入口与新用户策略。
- 服务号扫码关注登录：带参临时二维码、`subscribe` 与 `SCAN` 事件处理、登录结果下发、取关事件处理。
- 服务号网页授权登录：微信内 H5 免扫码登录。
- 服务号基础设施：AccessToken 改 Redis 存储、回调域名与授权域名配置、关注状态记录。
- 扫码绑定设备：二维码内容改为 HTTPS 链接且只含配对码、落地页、家属自助绑定接口、权限与所有者规则。

## 非目标

- 粉丝列表、标签、群发、素材管理、服务号自定义菜单。关注状态只记录是否可推送，不做粉丝管理页面。
- 小程序承接设备绑定与小程序码。先用 H5 落地页，后续按需追加。
- 预警模板消息的内容与发送策略，属于 AAF-120 的家属端通知，本故事只提供 openId 与可推送状态。
- 微信支付、企业微信登录（已有 `wecom` provider，不在本故事内改动）。

## 用户故事

### 开放平台扫码登录并打通账号

**作为**电脑端用户，**我希望**用微信扫码登录，并且和我在服务号、小程序里的身份是同一个账号，**以便**换入口不用重新注册，也不会出现两个账号。

### 扫码关注服务号登录

**作为**电脑端用户，**我希望**扫一个二维码就同时完成关注服务号和登录，**以便**不用先关注再另找入口登录，后面也能收到服务号通知。

### 微信内免扫码登录

**作为**在微信里打开链接的用户，**我希望**直接登录而不用再扫码，**以便**从服务号消息进入页面时一步到位。

### 家属扫码绑定设备

**作为**长者家属，**我希望**用微信扫机器人屏幕上的二维码，登录后选择长者就完成绑定，**以便**不需要联系运营，也不需要手输配对码。

### 二维码不泄露设备凭据

**作为**平台安全负责人，**我希望**设备屏幕上的二维码只包含配对码，**以便**拍下二维码的人无法抢走设备密钥。

## 验收标准

```gherkin
Feature: 账号打通

  Scenario: 同一个人从两个入口登录进入同一账号
    Given 服务号与网站应用已绑定到同一个开放平台账号
    And 用户 A 已通过开放平台扫码登录，账号记录了 unionid
    When 用户 A 通过服务号扫码关注登录
    Then 进入同一个 AAF 账号
    And 账号新增一条服务号 openId 的绑定

  Scenario: 服务号未绑定开放平台时不自动合并
    Given 服务号事件与网页授权返回里没有 unionid
    When 用户通过服务号登录
    Then 按服务号 openId 匹配账号
    And 不按昵称、手机号等信息自动合并其他账号
    And 用户可在已登录状态下手动绑定开放平台微信

  Scenario: 绑定被其他账号占用
    Given 微信身份 W 已绑定账号 B
    When 已登录的账号 A 尝试绑定 W
    Then 被拒绝，提示该微信已绑定其他账号

Feature: 服务号扫码关注登录

  Scenario: 未关注的用户扫码登录
    Given 登录页展示一个有效期内的带参临时二维码，场景值随机且一次性
    When 用户扫码并关注服务号
    Then 服务端收到 subscribe 事件并解析出场景值
    And 微信内提示用户确认本次登录
    When 用户确认
    Then 登录页在数秒内完成登录
    And 账号记录服务号 openId 与关注状态为已关注

  Scenario: 已关注的用户扫码登录
    Given 用户已关注服务号
    When 用户扫码
    Then 服务端收到 SCAN 事件并走同样的确认与登录流程

  Scenario: 二维码过期或重复使用
    Given 二维码超过有效期，或其场景值已被消费
    When 服务端收到该场景值的事件
    Then 不产生登录结果
    And 登录页提示二维码已过期并可刷新

  Scenario: 未确认不登录
    Given 用户扫码后没有在微信内确认
    When 登录页轮询结果
    Then 一直是等待状态，直到二维码过期
    And 不会登录任何账号

  Scenario: 取消关注
    Given 用户取消关注服务号
    When 服务端收到 unsubscribe 事件
    Then 账号上的服务号关注状态置为未关注
    And 不再向该 openId 发送模板消息
    And 账号与登录能力不受影响

Feature: 微信内网页授权登录

  Scenario: 在微信里打开页面自动登录
    Given 用户在微信内置浏览器打开 AAF 的 H5 页面且未登录
    When 页面发起服务号网页授权
    Then 用户授权后按 unionid 或服务号 openId 匹配账号并登录
    And 登录后回到进入时的页面

  Scenario: 非微信环境
    Given 用户在普通浏览器打开 H5 页面
    When 页面判断不在微信内
    Then 不发起网页授权，改用其他登录方式

Feature: 扫码绑定设备

  Scenario: 家属扫码绑定
    Given 机器人屏幕展示配对码与二维码，二维码内容是 HTTPS 链接且只带配对码
    When 家属用微信扫码
    Then 在微信内打开绑定落地页
    And 未登录时先走微信内登录
    When 家属选择自己有权管理的长者并确认
    Then 设备绑定到该长者
    And 设备所有者默认为当前登录家属
    And 机器人通过轮询领取一次性密钥并完成接入

  Scenario: 二维码不含领取凭据
    Given 机器人调用配对开始接口
    When 服务端返回 qrContent
    Then 内容中不含 deviceCode
    And 只含配对码

  Scenario: 抢先领取失败
    Given 有人拍下了二维码
    When 他在绑定完成后用二维码里的信息调用轮询接口
    Then 无法取得设备密钥，因为二维码里没有 deviceCode

  Scenario: 无权管理该长者
    Given 家属对某长者没有管理设备的授权
    When 家属尝试把设备绑定到该长者
    Then 被拒绝
    And 配对码不被消耗

  Scenario: 配对码过期或错误
    Given 配对码已超过十分钟，或已被使用，或输入错误
    When 家属提交绑定
    Then 提示配对码无效或已过期
    And 连续失败达到上限后暂时锁定，沿用现有失败计数规则

  Scenario: 设备已被绑定
    Given 该序列号已处于已绑定状态
    When 家属再次绑定
    Then 被拒绝，提示先解绑

  Scenario: 落地页链接不可被篡改域名
    Given 服务端生成二维码链接
    Then 链接的域名取自服务端配置的白名单
    And 不取请求头里的 Host
```

## 待确认的决策

以下是产品建议，评审时确认：

- 扫码关注登录要在微信内二次确认。二维码属于发起登录的那个浏览器会话，谁扫码，该会话就登录成谁。攻击者在自己的浏览器里打开登录页，把二维码放到钓鱼页或截图里，以"扫码领奖""扫码验证身份"等理由让受害者扫码，攻击者的浏览器就登录成了受害者的账号。受害者扫的是自己的微信，没有任何异常提示。账号下有长者健康数据，建议必须确认，确认页显示发起登录的网站与大致地点；二维码有效期也要尽量短，减少被实时转发的窗口。
- 账号打通只认 unionid，不按昵称、手机号等自动合并。服务号没绑开放平台时，服务号账号独立存在，靠手动绑定合并。
- 家属自助绑定使用专用接口，不向家属开放 `device:device:create`。权限为对长者拥有"管理设备"的授权范围，建议在授权范围里新增，不复用 `VIEW_PROFILE`。设备所有者默认为当前登录的家属。
- 绑定二维码链接形如 `https://<配置域名>/device/bind?pairCode=XXXXXXXX`，域名放在服务端配置里。机器人端不用改，直接显示服务端返回的内容。
- 二维码去掉 `deviceCode` 是独立的安全修复，不依赖落地页，建议先于其他内容上线。
- 前置条件：服务号需要是已认证的服务号（带参二维码、模板消息等接口需要认证），公众号后台配置网页授权域名与业务域名并做 ICP 备案，服务器出口 IP 加入白名单，服务号与网站应用绑定到同一个开放平台账号才能拿到 unionid。

## 建议的交付顺序

1. 安全修复：设备二维码去掉 `deviceCode`，只含配对码（2026-10-16 已完成，改为 HTTPS 链接随落地页一起做）。
2. 账号模型：`sys_user_oauth` 增加 unionid，开放平台扫码登录补记录与合并规则。
3. 服务号基础设施：AccessToken 改 Redis，回调与授权域名配置，关注状态记录。
4. 服务号扫码关注登录。
5. 微信内网页授权登录与设备绑定落地页，家属自助绑定接口。

## 风险

- 服务号未认证或域名未备案时，带参二维码、网页授权与模板消息都无法联调，需要先确认账号条件。
- unionid 依赖开放平台绑定，未绑定时账号会分裂，需要在上线前核对绑定关系。
- 服务号事件回调有 5 秒响应限制，登录结果下发不能阻塞回调，要异步处理。
- 家属自助绑定放开了原本由运营掌控的步骤，设备所有者即计费主体，默认值与转移规则要在设计时明确。

## 关联

- 依赖 [AAF-120](../AAF-120/requirement.md) 的设备配对与场景模型；AAF-120 将服务号通知与家属端后置，本故事补齐其前置的微信身份。
- AAF-120 的预警模板消息依赖本故事提供的服务号 openId 与可推送状态。
