# AAF-122 知识图谱领域本体与实例双层抽取

任务编号：AAF-122
scope_mode：selective-expansion（基线为"本体层 + 受约束抽取 + 自动演进 + 审核 + 回填"，组织级共享等扩展项逐个评估，见开放问题）

## 需求分析（六问）

| # | 问题 | 结论 |
|---|------|------|
| 1 | 需求还是方案？ | 两者都有。真实需求是"图谱能按领域类型查询、关系边能聚合、同名不同义的实体不被混在一起"。"本体层 + 实例层双层"是解法，且是知识图谱领域的成熟做法，产品侧接受；但阈值、隔离粒度、回填方式等属于方案细节，列入开放问题交 architect 设计 |
| 2 | 真正痛点？ | 已入库的医疗、养老文档图谱基本不可用：疾病、并发症、干预措施都是 CONCEPT，按类型查询返回整库；predicate 几乎每种只出现一次，边无法聚合，多跳检索走不通；LITERAL 存的是整句改写，图里没有结构；同名不同类型实体可能被精确别名匹配误合并，污染真理表且难以发现。AAF-120 养老康复指导依赖知识库问答，图谱不可用会直接降低回答质量 |
| 3 | 隐含前提？ | ① 模型能在注入词表后稳定优先复用已有类型和关系（需样本验证）；② 领域内同义 predicate 可以通过向量相似度加同义判断归一，误合并率可接受；③ 知识库文档量足以让候选在合理时间内达到阈值，单文档或小库可能永远达不到；④ strict 结构化输出能接受随知识库变化的枚举，且词表规模在提示词预算内（词表膨胀后需裁剪）；⑤ 现有已入库数据可在开发阶段直接重建，不需要迁移兼容 |
| 4 | 最窄 MVP？ | 先行小改进：精确别名匹配加类型一致条件、LITERAL 只允许短值。MVP：按知识库隔离的本体（类型含一层父类型、关系类型含 subject/object 约束、同义词）+ 抽取注入词表 + 候选归一与阈值自动生效 + 结构性变更审核提案 + 确定性回填 + 事实记录本体版本。砍掉组织级共享与继承、本体导入导出、类型拆分、全量重抽 |
| 5 | 完整愿景成本？ | 完整版再加组织级共享本体与知识库继承、跨知识库实体对齐、类型属性 schema、本体可视化编辑、OWL/RDF 互通、基于本体的推理规则、本体变更后自动全量重抽。工作量约为 MVP 的两到三倍，且多数能力当前没有使用方 |
| 6 | 推荐？ | 推荐 MVP，分两步交付。先行小改进不依赖本体设计、改动小、立即止损，协调者在本任务内先做；本体部分涉及表结构、抽取契约与后台审核，属于 🔴 高风险，必须设计经人类审核后开发。组织级共享等扩展在 MVP 的版本模型里预留来源基线即可，不在本故事实现 |

## 背景

AAF 知识入库已有可信抽取链路：切块，逐块事实抽取（qwen 结构化输出，JSON Schema strict），文档级批量实体消歧，写入 PostgreSQL 真理表，再投影到 Neo4j。证据必须逐字来自焦点块，入库按代际整体发布，Neo4j 可从 PostgreSQL 重建。

实际入库日志暴露了以下问题：

- **实体类型写死**：12 个通用类型（PERSON、ORGANIZATION、LOCATION、EVENT、PRODUCT、TECHNOLOGY、SYSTEM、DOCUMENT、CONCEPT、METRIC、ROLE、OTHER）所有知识库共用。医疗、养老文档里糖尿病、视网膜病变、饮食管理、规律运动全被标为 CONCEPT，图谱无法按类型查询。
- **predicate 是自由文本**：如"核心问题是""导致后果""可能引发""作用是""建议频率"，几乎每种只出现一次，边无法聚合。
- **LITERAL 滥用**：大量事实的 object 是整句原文改写，图结构没有起作用。
- **精确别名匹配不看类型**：只按归一化别名查询，命中唯一实体就复用；向量自动关联却要求类型一致。两处规则不一致，同名不同类型的实体存在误合并风险。

## 目标

- 知识图谱拆为两层，两层都随入库自动演进：
  - **领域本体层**（按知识库隔离）：实体类型（可有父类型）、关系类型（含定义、允许的 subject/object 类型、是否对称或可逆）、别名与同义词。每次变更产生新版本。
  - **实例层**：实体、别名、事实三元组与证据。抽取受当前本体版本约束，事实记录抽取时的本体版本。
- 图谱可按领域类型和关系类型查询与聚合。
- 本体演进以自动为主，结构性变更由人审核，变更结果可回填到已有实例。

## 用户故事

### 新知识库开箱可用

**作为**知识库管理员，**我希望**新建知识库时自动带一套默认本体，**以便**不做任何配置也能入库抽取，再随文档逐步长出领域类型。

**完成条件**：新知识库有一个以 12 个通用类型为内容的初始本体版本，首个文档即可按该版本抽取。

### 抽取跟随领域本体

**作为**知识库管理员，**我希望**抽取时模型优先使用本库已有的类型和关系，确实没有合适的才提出候选，**以便**同一领域的实体归到同一类型、同一种关系落到同一条边上。

**完成条件**：抽取结果只使用当前生效本体中的类型和关系，或以带定义和证据的候选提出；候选经归一去重后映射到已有项或累计计数。

### 本体自动生长

**作为**知识库管理员，**我希望**被多次、跨文档提到的新类型和新关系自动生效，**以便**本体随资料积累自然完善，不用我逐个审批。

**完成条件**：候选达到阈值后自动生效并产生新本体版本，相关实例按新版本回填。

### 结构性变更可审核

**作为**知识库管理员，**我希望**合并、重命名、删除类型或关系、调整类型层级时先生成提案，在管理后台审核后才生效，**以便**避免模型误判一次性改坏整库图谱。

**完成条件**：结构性变更只以提案形式出现；通过后生效并回填，驳回后本体和实例都不变。

### 按类型检索图谱

**作为**知识检索使用方（含智能体），**我希望**按实体类型和关系类型查询图谱，并知道每条事实是按哪个本体版本抽取的，**以便**做定向检索、多跳推理和结果溯源。

**完成条件**：检索可按类型或关系类型过滤，事实可追溯到抽取时的本体版本。

### 回填可放心重跑

**作为**平台运维，**我希望**本体变更后的回填幂等、可重试、可观测，Neo4j 可随时从 PostgreSQL 重建，**以便**回填失败或中断后重跑即可恢复一致。

**完成条件**：同一本体变更重复触发回填，最终实例层和图投影结果一致；回填状态可在后台查看。

## 范围

- 本体层：按知识库隔离的实体类型（含父类型）、关系类型（定义、subject/object 类型约束、对称或可逆、可逆时的反向名称）、别名与同义词，以及本体版本。
- 默认本体：现有 12 个通用类型作为新知识库的起点。
- 受约束抽取：抽取时注入当前生效本体的类型和关系词表，结构化输出的可选值随本体版本生成。
- 候选机制：类型候选、关系候选的提出、归一、去重、计数、自动生效。
- 结构性变更：合并、重命名、删除、调整层级以提案形式审核。管理员也可以手动发起提案。
- 回填：本体变更后按影响范围对实例层重新归类、合并关系、重算图投影。
- 版本追溯：事实记录抽取时的本体版本。
- 管理后台：本体、候选、提案、回填状态的查看与审核入口，用 EntityDef 声明。
- 先行小改进：精确别名匹配加类型一致条件，LITERAL 只允许短值。

## 非目标

- 组织级共享本体、知识库之间的本体继承（见开放问题，MVP 只预留扩展可能）。
- 跨知识库实体对齐与合并。
- 类型属性 schema（如"疾病"必须有"ICD 编码"属性）。
- 类型拆分（一个类型拆成多个）。拆分需要逐个实体重新判断，回填无法确定性完成。
- 本体变更后自动全量重新抽取。回填只做确定性映射，不重新调用抽取模型；需要按新本体重抽时由管理员重新入库文档。
- 本体导入导出、OWL/RDF/SKOS 互通、基于本体的推理规则。
- 可视化本体编辑器。MVP 后台只做列表、详情与提案审核。
- 修改证据规则、入库代际发布机制和计费规则。

## 功能点

- [ ] P0 精确别名匹配加类型一致条件，同名不同类型不复用同一实体
- [ ] P0 LITERAL 只允许短值，整句描述拒绝入库
- [ ] P0 按知识库隔离的本体层与本体版本，新知识库以默认本体初始化
- [ ] P0 抽取注入当前生效本体，结构化输出可选值随本体版本生成
- [ ] P0 事实记录抽取时的本体版本
- [ ] P0 类型候选与关系候选的提出、归一、去重与计数
- [ ] P0 候选达阈值自动生效，产生新本体版本
- [ ] P0 关系类型的 subject/object 类型约束校验
- [ ] P0 结构性变更提案，审核通过前不生效，驳回无副作用
- [ ] P0 本体变更后实例回填（重新归类、关系合并、图投影重算），幂等可重试
- [ ] P1 检索按实体类型、关系类型过滤，可按父类型展开
- [ ] P1 管理后台本体、候选、提案、回填状态页（EntityDef 声明）
- [ ] P1 管理员手动发起结构性变更提案
- [ ] P2 词表超出提示词预算时的裁剪策略

## 业务规则

### 概念登记表

表名与字段由 architect 在设计中确定，本表只登记产品概念与数据实体的一一对应。

| 产品概念 | 数据实体 | 说明 |
|---------|---------|------|
| 本体版本 | OntologyVersion | 某知识库某一时刻生效的完整本体快照，版本号单调递增 |
| 实体类型 | EntityTypeDef | 本体中的一个实体类型，可有一个父类型 |
| 关系类型 | RelationTypeDef | 本体中的一个关系类型，含 subject/object 类型约束 |
| 同义词 | OntologySynonym | 类型或关系类型的别名与同义写法，用于归一映射 |
| 本体候选 | OntologyCandidate | 抽取中提出、尚未生效的新类型或新关系 |
| 变更提案 | OntologyChangeProposal | 待审核的结构性变更 |
| 回填任务 | OntologyBackfill | 一次本体版本变更引起的实例层回填 |

实例层的实体、别名、事实、证据沿用现有可信知识模型，本故事只增加本体版本关联和类型约束。

### 本体层数据项

| 数据项 | 规则 |
|--------|------|
| 实体类型 | 编码（知识库内唯一、稳定，用于引用）、显示名、定义、父类型（可空）、来源（默认本体 / 自动生效 / 审核通过 / 管理员创建）、状态 |
| 关系类型 | 编码、显示名、定义、允许的 subject 类型集合、允许的 object 类型集合（或"短值"）、是否对称、是否可逆及反向名称、来源、状态 |
| 同义词 | 指向一个类型或关系类型；同一知识库内一个归一化写法只能指向一个目标 |
| 本体版本 | 所属知识库、版本号、生效时间、触发原因（初始化 / 候选自动生效 / 提案通过）、相对上一版本的变更摘要 |

### 默认本体

- 新建知识库时生成版本 1，内容为 12 个通用类型：PERSON、ORGANIZATION、LOCATION、EVENT、PRODUCT、TECHNOLOGY、SYSTEM、DOCUMENT、CONCEPT、METRIC、ROLE、OTHER。
- 默认本体不预置关系类型，关系类型全部随入库生长。是否预置少量通用关系（如"属于""包含"）由 architect 评估。
- OTHER 是兜底类型，不可删除、不可作为其他类型的父类型。
- 新领域类型可以把默认类型作为父类型（如"疾病"的父类型为 CONCEPT），也可以没有父类型。

### 受约束抽取规则

- 抽取开始时锁定知识库当前生效的本体版本。同一次入库代际内所有块使用同一版本，入库中途本体变更不影响正在进行的代际。
- 注入模型的词表包含类型和关系类型的编码、显示名和定义。
- 结构化输出中实体类型和关系类型的可选值只能是当前版本的生效项。
- 当前版本中没有合适项时，模型可以提出候选，必须给出名称、定义和来自 FOCUS 的证据。
- 实例写入时只使用生效的类型和关系类型：
  - 实体的建议类型是未生效候选时，实体按模型给出的最接近生效类型写入（无合适项时为 OTHER），并关联到该候选。候选生效后由回填重新归类。
  - 事实的建议关系是未生效候选时，按开放问题"关系类型是否严格白名单"的结论处理。
- 事实的 subject 和 object 类型必须满足其关系类型的约束，违反约束的事实不入库并记录原因，不影响同块其他事实。
- 本体内容来自文档抽取，属于不可信数据。注入提示词时作为数据处理，候选名称和定义有长度上限，不得改变抽取指令。
- 同一文档在本体版本变化后重新入库，必须按新版本重新抽取，不得复用旧版本的抽取结果。

### 候选归一与自动生效规则

- 每个候选先做归一：去空白、大小写和全半角统一，再与已有类型、关系类型及其同义词比较，比较方式包括精确匹配、向量相似度和同义判断。
- 能映射到已有项时直接映射，把候选写法登记为该项的同义词，不新增类型或关系。
- 不能映射时与同库其他未生效候选合并去重，累计出现次数和覆盖文档数。
- 候选的出现次数和覆盖文档数达到阈值后自动生效，生成新本体版本并触发回填。阈值口径见开放问题。
- 自动生效只能做"新增"，不能改动已有项。
- 候选来源的事实被入库代际替代或撤销后，其计数相应扣减。已生效的项不因计数扣减而自动撤销，撤销走删除提案。

### 结构性变更规则

- 结构性变更包括：合并（两个类型或两个关系类型合为一个）、重命名、删除、调整类型层级（改父类型）、修改关系类型的 subject/object 约束。
- 结构性变更只能以提案形式出现。来源可以是归一过程中发现的疑似重复或冲突，也可以由管理员手动发起。
- 提案包含：变更类型、涉及项、变更后内容、理由、影响范围预估（涉及实体数、事实数、文档数）、提案时的基线本体版本。
- 审核通过后生成新本体版本并触发回填；驳回后本体和实例都不变，提案保留驳回理由。
- 提案的基线版本已不是当前版本，且涉及项在此期间被改动时，提案失效，需要重新生成。
- 删除类型时，原属该类型的实体归入其父类型，没有父类型时归入 OTHER。删除关系类型时，原属该关系的事实转为"未归类"或不再参与图投影，具体由开放问题结论决定。
- 类型层级不能成环。

### 回填规则

- 每次本体版本变化（候选生效或提案通过）产生一次回填，回填范围限于受影响的类型和关系类型。
- 回填只做确定性映射：重新归类实体、把被合并的关系类型下的事实合并到目标关系、重算受影响部分的图投影。回填不重新调用抽取模型。
- 回填幂等：同一版本变化无论触发几次，最终实例层和图投影结果一致。
- 回填失败可重试，不留下半完成状态对检索可见。
- PostgreSQL 是唯一真理源，Neo4j 投影可随时从 PostgreSQL 全量重建，重建结果与回填结果一致。

### 精确别名匹配规则（先行）

- 实体消歧的精确别名匹配只复用归一化名称相同且类型相同的实体。
- 同一文档内同名不同类型的两次提及，分别解析为两个实体。
- 同名同类型仍按现有规则直接复用。
- 先行阶段的"类型相同"指归一化类型严格相等。类型层级落地后，父子类型是否视为相同由设计确定。

### LITERAL 短值规则（先行）

- LITERAL 只允许短值：数值（可带单位）、日期或时间、版本号、状态值、布尔值、短属性值。
- 判定条件：去首尾空白后长度不超过 32 字符，且不含句子分隔字符（全角 `。！？；，`、半角 `!?;`、换行）。半角 `.` 与 `,` 不计入，避免误伤 `7.0`、`1,000`。协调者于 11-07 将默认 64 收紧为 32。
- 不满足短值条件的 LITERAL 事实被拒绝，不入库，记录拒绝原因，不影响同块其他事实。
- 抽取提示中明确要求：整句描述拆成实体加关系，无法拆分时不抽取。

### 证据规则（不变）

- evidenceQuote 必须逐字来自 FOCUS，不满足的事实被丢弃。
- 候选类型和候选关系的证据同样必须逐字来自 FOCUS。

### 状态机

本体版本：

| 状态 | 含义 | 迁移 |
|------|------|------|
| 生效中 | 知识库当前版本，新抽取使用该版本 | 产生新版本时 → 已替代 |
| 已替代 | 历史版本，只读，供事实追溯 | 终态 |

每个知识库同一时刻只有一个"生效中"版本。版本只增不改。

本体候选：

```text
观察中 ──归一命中已有项──→ 已映射（终态）
观察中 ──达到阈值────────→ 已生效（终态，产生新版本）
观察中 ──来源全部撤销────→ 已失效（终态）
观察中 ──管理员驳回──────→ 已驳回（终态，同一写法后续再出现仍按驳回处理）
```

变更提案：

```text
待审核 ──通过──→ 已通过 ──回填完成──→ 已应用（终态）
待审核 ──驳回──→ 已驳回（终态，无副作用）
待审核 ──基线过期且涉及项已变──→ 已失效（终态）
```

回填任务：

```text
待执行 → 执行中 → 已完成
             ↓
           已失败 ──重试──→ 执行中
```

### 管理后台

- 入口位于 `(workspace)/admin/**`，列表、表单与审核动作由 EntityDef 声明，审核通过与驳回写入 `actions`，不手写页面。
- 可查看：本体版本历史与变更摘要、类型与关系类型列表（含层级与约束）、候选列表（状态、出现次数、覆盖文档数、证据样例）、提案列表与影响范围、回填任务状态。
- 审核动作只对有知识库管理权限的用户开放。

## 约束条件

- 证据规则不变：evidenceQuote 必须逐字来自 FOCUS。
- PostgreSQL 是唯一真理源，Neo4j 可重建。
- 入库代际发布机制不变：本体版本锁定在代际内，代际整体发布。
- 开发阶段未部署，表结构直接改现有迁移文件，不写增量迁移、不做兼容层。
- 候选归一、同义判断等新增模型调用沿用现有知识入库计量，不新增计费规则。
- 管理后台遵守 EntityDef 规范。
- 本故事的本体部分涉及表结构、抽取契约和权限，属于 🔴 高风险，设计经人类审核后开发。

AC-17 至 AC-20 属于先行小改进，其余属于本体双层。

```gherkin
Feature: 默认本体

  Scenario: AC-01 新知识库使用默认本体
    Given 管理员新建知识库 K
    When 查看 K 的本体
    Then K 有且只有一个生效中的本体版本 1
    And 版本 1 包含 PERSON、ORGANIZATION、LOCATION、EVENT、PRODUCT、TECHNOLOGY、SYSTEM、DOCUMENT、CONCEPT、METRIC、ROLE、OTHER 共 12 个实体类型
    When 向 K 入库第一个文档
    Then 抽取按版本 1 进行，实体类型只取上述 12 个之一

  Scenario: AC-02 本体按知识库隔离
    Given 知识库 A 和 B 都处于版本 1
    When A 的候选类型"疾病"自动生效
    Then A 升到版本 2 且包含"疾病"
    And B 仍为版本 1，不包含"疾病"

Feature: 受约束抽取

  Scenario: AC-03 抽取优先复用已有类型
    Given 医疗知识库 M 的生效本体包含实体类型"疾病"
    When 入库一篇含"糖尿病可能引发视网膜病变"的文档
    Then "糖尿病"和"视网膜病变"的实体类型为"疾病"
    And 不产生与"疾病"同义的新类型候选

  Scenario: AC-04 无合适类型时提出候选
    Given 知识库 M 的生效本体没有表示干预措施的类型
    When 抽取到"规律运动"
    Then 产生类型候选，包含名称、定义和逐字来自 FOCUS 的证据
    And "规律运动"实体按最接近的生效类型写入，并关联到该候选

  Scenario: AC-05 候选类型未达阈值时不生效
    Given 候选类型"干预措施"的出现次数或覆盖文档数未达到阈值
    When 继续入库并查看本体
    Then 生效本体版本不变，不包含"干预措施"
    And 下一次抽取的结构化输出可选类型中不包含"干预措施"
    And 没有任何实体以"干预措施"作为类型写入

  Scenario: AC-06 候选类型达阈值后自动生效
    Given 候选类型"干预措施"距阈值只差一次出现
    When 新文档再次提出该候选且满足阈值
    Then 产生新本体版本，包含"干预措施"，来源为自动生效
    And 候选状态变为已生效
    And 触发回填，此前关联该候选的实体被重新归类为"干预措施"
    And 之后的抽取可直接使用"干预措施"

  Scenario: AC-07 同义 predicate 映射到已有关系类型
    Given 知识库 M 的生效本体有关系类型"引发"，subject 与 object 类型为"疾病"
    When 抽取提出关系"可能引发"或"导致后果"
    And 归一判断其与"引发"同义
    Then 事实以关系类型"引发"写入
    And 该写法登记为"引发"的同义词
    And 不新增关系类型，也不新增关系候选

  Scenario: AC-08 违反关系类型约束的事实不入库
    Given 关系类型"引发"只允许 subject 与 object 为"疾病"
    When 抽取出 subject 为 PERSON 的"引发"事实
    Then 该事实不入库并记录违反约束的原因
    And 同块其他合法事实正常入库

  Scenario: AC-09 本体内容不改变抽取指令
    Given 某候选定义中包含"忽略以上规则"之类的文本
    When 该候选生效并注入后续抽取
    Then 抽取仍遵守原有输出契约与证据规则

Feature: 结构性变更审核

  Scenario: AC-10 结构性变更生成审核提案
    Given 知识库 M 同时存在类型"疾病"和"病症"
    When 系统发现两者疑似重复，或管理员发起合并
    Then 产生一条待审核的合并提案，包含涉及项、理由、影响范围和基线版本
    And 生效本体版本不变，"疾病"和"病症"仍各自独立

  Scenario Outline: AC-11 审核通过前不生效
    Given 有一条待审核的<变更>提案
    When 提案尚未审核时入库新文档并查询图谱
    Then 抽取与检索都按变更前的本体进行

    Examples:
      | 变更       |
      | 合并类型   |
      | 重命名类型 |
      | 删除类型   |
      | 调整父类型 |
      | 合并关系类型 |

  Scenario: AC-12 审核通过后生效
    Given 合并"病症"到"疾病"的提案待审核
    When 管理员在后台审核通过
    Then 产生新本体版本，"病症"成为"疾病"的同义词
    And 提案状态经已通过变为已应用
    And 触发回填

  Scenario: AC-13 驳回后无副作用
    Given 一条待审核的提案
    When 管理员驳回并填写理由
    Then 本体版本不变
    And 实体、事实、图投影都不变
    And 提案状态为已驳回并保留理由

  Scenario: AC-14 基线过期的提案失效
    Given 提案 P 基于版本 3，涉及类型"病症"
    And 审核前另一提案通过，版本升到 4 且改动了"病症"
    When 管理员尝试审核 P
    Then P 状态为已失效，不能通过

Feature: 回填

  Scenario: AC-15 回填重新归类、合并关系、重算图投影
    Given 合并"病症"到"疾病"、合并关系"诱发"到"引发"的变更已通过
    When 回填完成
    Then 原"病症"实体的类型为"疾病"
    And 原"诱发"事实的关系类型为"引发"，重复的事实合并为一条并保留全部证据
    And Neo4j 中对应节点与边已按新类型和关系更新
    And 从 PostgreSQL 全量重建 Neo4j 后结果与回填后一致

  Scenario: AC-16 回填幂等
    Given 某本体版本变化的回填已完成
    When 再次触发同一回填，或回填中途失败后重试
    Then 最终实体、事实、证据数量与类型和第一次成功完成时完全一致
    And 回填期间检索不会看到半完成的结果

Feature: 先行小改进

  Scenario: AC-17 同名不同类型的实体不被合并
    Given 知识库已有实体"苹果"，类型 ORGANIZATION
    When 新文档抽取到"苹果"，类型 PRODUCT
    Then 新建一个类型为 PRODUCT 的"苹果"实体
    And 不把它解析到 ORGANIZATION 的"苹果"
    And 同一文档内同时出现两种类型的"苹果"时，解析为两个实体

  Scenario: AC-18 同名同类型仍复用
    Given 知识库已有实体"苹果"，类型 ORGANIZATION
    When 新文档抽取到"苹果"，类型 ORGANIZATION
    Then 解析到已有实体，不新建

  Scenario: AC-19 LITERAL 整句被拒绝
    When 抽取出 object 为"患者应在医生指导下长期坚持低糖饮食并定期复查。"的 LITERAL 事实
    Then 该事实不入库并记录拒绝原因
    And 同块其他合法事实正常入库

  Scenario Outline: AC-20 LITERAL 短值正常入库
    When 抽取出 object 为"<值>"的 LITERAL 事实，证据合法
    Then 该事实入库

    Examples:
      | 值         |
      | 7.0 mmol/L |
      | 2026-11-07 |
      | v2.1       |
      | 已停用     |
      | 是         |
      | 每周 3 次  |

Feature: 版本追溯与证据

  Scenario: AC-21 事实可追溯其抽取时的本体版本
    Given 文档 D1 在版本 2 时入库，文档 D2 在版本 3 时入库
    When 查询 D1 和 D2 的事实
    Then D1 的事实记录本体版本 2，D2 的事实记录本体版本 3
    And 版本 2 的内容仍可查看

  Scenario: AC-22 本体变化后重新入库按新版本抽取
    Given 文档 D1 在版本 2 时入库
    And 本体已升到版本 3
    When 重新入库 D1，内容不变
    Then 按版本 3 重新抽取，不复用版本 2 的结果
    And 新事实记录本体版本 3

  Scenario: AC-23 evidenceQuote 逐字规则保持
    When 抽取的事实或候选的 evidenceQuote 不能在 FOCUS 中逐字找到
    Then 该事实或候选被丢弃，不计入候选计数

Feature: 检索与后台

  Scenario: AC-24 按类型和关系类型检索
    Given 知识库 M 有"疾病"类型实体和"引发"关系事实
    When 检索方按类型"疾病"或关系类型"引发"查询
    Then 只返回对应类型的实体或对应关系的事实
    And 每条事实带本体版本

  Scenario: AC-25 管理后台审核入口
    Given 有知识库管理权限的用户进入管理后台
    Then 可查看本体版本、类型、关系类型、候选、提案与回填状态
    And 提案的通过与驳回是 EntityDef 声明的动作
    And 无知识库管理权限的用户看不到审核动作
```

## 测试要点

- 验收测试：JUnit 5 `*AcceptanceTest.java`，`@DisplayName` 引用 AC 编号。
- 单元测试：JUnit 5 + Mockito，覆盖归一映射、阈值判定、约束校验、LITERAL 短值判定、精确匹配类型条件。
- 模型调用使用录制回放或桩，不依赖真实模型，确保候选与阈值场景可复现。
- 关键场景：阈值恰好达到与差一次；单文档知识库的阈值行为；同一文档内同名不同类型；合并后重复事实的证据合并；回填中途失败重试；入库代际进行中发生本体变更；Neo4j 清空后重建与回填结果比对。

## 开放问题

以下问题的产品侧倾向仅供参考，最终由 architect 设计并经人类审核决定。

| # | 问题 | 产品侧倾向 | 理由 |
|---|------|-----------|------|
| 1 | 本体是只按知识库隔离，还是支持组织级共享、知识库继承？ | MVP 只按知识库隔离；新建时从默认本体复制一份。版本模型预留"来源基线"字段，组织级共享与继承后续单独立项 | 当前没有多知识库共用领域词表的使用方；共享和继承会引入跨库回填与冲突合并，成本翻倍 |
| 2 | 自动生效阈值用出现次数、覆盖文档数，还是两者结合？阈值是否可配置？ | 两者同时满足才生效（如出现 ≥ 5 次且覆盖 ≥ 2 篇文档）；平台给默认值，知识库级可覆盖 | 只看次数时单篇长文档里反复出现的写法会被误推；只看文档数时小库长不出类型。需要单独处理文档少于 2 篇的知识库，建议文档数阈值取"配置值与库内文档数的较小值" |
| 3 | 关系类型是严格白名单（不在词表内就丢弃），还是允许候选关系先以"未归类"状态入库？ | 允许以"未归类"入库：保留原始 predicate 与证据，不投影图谱，不参与按关系类型检索；候选生效后由回填转正 | 严格白名单让新领域冷启动时大部分事实被丢弃，事后只能重抽；未归类入库只占存储，不污染图谱 |
| 4 | 回填同步还是异步？回填期间检索读取哪个版本？ | 异步回填；回填完成前检索读取旧版本的完整结果，完成后整体切换，与现有入库代际发布方式一致 | 合并类型可能涉及大量实体，同步会阻塞审核动作；整体切换保证检索不看到半完成状态 |
| 5 | 类型层级需要几层？检索时是否按父类型展开？ | 最多 3 层（如 CONCEPT → 疾病 → 慢性病）；按类型检索默认包含子类型，可显式关闭 | 3 层足以表达医疗、养老领域的常见分类，层级越深模型越难稳定选择；默认展开符合"查疾病应包含慢性病"的直觉 |
