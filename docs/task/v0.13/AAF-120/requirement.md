# 需求：养老业务模块（elder）

任务编号：AAF-120
scope_mode：hold

> 状态：设计已确认（2026-10-15 通过人类审核），可按 [tasks.md](tasks.md) 开工。本文只定范围与验收口径，实现方案见 [design.md](design.md)。

## 需求分析（六问）

| # | 问题 | 结论 |
|---|------|------|
| 1 | 需求还是方案？ | 业务方给出的是子域划分、机器人工程、后台功能架构和视觉场景，背后的需求是"以家庭陪伴机器人为主要终端，在 AAF 上做居家养老服务" |
| 2 | 真正痛点？ | 独居老人跌倒后长时间无人发现；忘记吃药；缺少陪伴；想要服务但不知道怎么找；家属不在身边又放心不下 |
| 3 | 隐含前提？ | ① 以居家养老为主，机构养老不在本期；② 机器人终端软件（`modbot`）由我们自己维护，原先用本地模型，现在改为对接 AAF 助理；③ 机器人一期上报语义事件、接收提醒，不做物理控制；④ 监控与预警画面不出设备，仅用户主动或经授权拍摄的照片可上传；⑤ 一期不做在线支付，服务费用线下结算；⑥ 短信暂不发送，预留开关。以上均未向业务方验证 |
| 4 | 最窄 MVP？ | 建档与家属授权、跌倒等预警与通知、用药提醒、机器人对接助理陪伴聊天、服务预约、康复指导最小版、相册最小版 |
| 5 | 完整愿景成本？ | 七个子域约 38 个实体，需要固定摄像头节点、可穿戴设备、支付与补贴规则、监管口径，且依赖外部输入 |
| 6 | 推荐？ | 折中：一期做七个核心场景共 13 个实体，并按三个里程碑交付（先预警与用药，再相册与预约，最后助理语音与康复指导）；二期补服务履约、体征与更多视觉预警、支付结算；三期做监管运营与入户识别 |

## 背景

AAF 已具备多智能体、知识库、记忆、工作流、数字人、支付与结算引擎等框架能力，缺一个能体现"AI 原生业务"的完整业务样板。养老是典型场景：服务对象需要被理解，事件需要被研判，服务需要被调度，决策需要被支撑。

当前计划以居家养老为主，用在线服务预约和家庭陪伴机器人等智能化方式解决老人需求。机器人是主要终端：它在老人身边做陪伴、提醒和求助，同时用摄像头发现跌倒等异常，并拍摄照片；AAF 作为后台保存老人信息、管理预警和提醒、连接家属与运营，并通过助理为机器人提供语音识别、对话和语音合成。

模块名定为 `elder`，位于 `aaf-api` 的 `module/elder/`，按子域拆分，每个子域沿用 `todo` 模块确立的写法（资源定义、Patch 更新、乐观锁、ReBAC、EntityDef 管理端）。机器人工程、后台功能架构 PDF 与视觉检查需求都由这一个模块管理，对照见设计文档。

## 范围

### 子域

| 子域 | 中文名 | 回答的问题 | 包含 |
|------|--------|-----------|------|
| `profile` | 长者中心 | 谁、多大、什么状况、住哪 | 老人主数据、联系人与监护授权、健康条目、用药计划与服药记录；后置：体征、能力评估 |
| `guard` | 安全守护 | 出事了能不能被发现、找得到人 | 设备接入、下行消息（提醒与配置）、预警事件与响应、设备语音网关 |
| `mall` | 服务商城 | 能提供什么、怎么买 | 服务项目、预约单；后置：套餐、权益、支付 |
| `album` | 相册 | 机器人拍的照片在哪、谁能看 | 照片上传、查看、删除、家属可见性 |
| `rehab` | 康复指导 | 怎么康复、依据是什么 | 康复指导管理、关联知识文档、查看、问答 |
| `provider` | 服务资源 | 谁能干、干得怎么样 | 二期。服务商、护理员、资质、排班、评分 |
| `workorder` | 服务执行 | 谁去、干了啥、干完了没 | 二期。派单、上门签到签退、工单闭环、评价 |
| `settle` | 结算中心 | 钱从哪来、分给谁、对不对得上 | 二期。费用、补贴、分账、对账 |
| `ops` | 监管运营 | 给管理层与政府看的全局视角 | 三期。质控、投诉、报表、大屏 |
| `agent` | 智能层（横切） | 让 AI 能理解并操作以上各域 | 工具、技能、角色、知识库与工作流的种子配置 |

`agent` 不是业务子域，不拥有业务表，只通过各子域公开的 `api/` 接口工作。

### 一期七个核心场景

| 场景 | 一期 | 做法与理由 |
|---|---|---|
| 基础信息 | 做 | 所有场景的数据底座：长者档案、联系人与家属授权、健康条目 |
| 预警（跌倒等） | 做 | 机器人最能体现价值的场景。一期做跌倒、一键求助、长时间无活动、设备离线四类，机器人本体即可覆盖 |
| 用药提醒 | 做 | 管理端录入，也可以通过对话创建（两步确认）；药品信息由人提供，系统不给用药建议 |
| 陪伴聊天 | 做 | 机器人对接 AAF 助理，使用 AAF 的语音识别、对话和语音合成；本机大脑保留为断网兜底 |
| 服务预约 | 做（精简） | 只做服务项目和预约单，运营在管理端确认并线下安排服务，不含服务商、派单、上门闭环 |
| 康复指导 | 做（精简） | 管理康复指导并关联知识文档，支持查看和基于文档的问答；不做个性化康复计划与打卡 |
| 相册管理 | 做（精简） | 机器人拍的照片上传，家属查看和管理；不做分组与人物标签 |
| 家属关怀 | 融入 | 家属绑定与授权属于基础信息，预警与漏服通知属于预警和用药提醒，相册属于相册；周报、视频通话后置 |

各子域在一期的取舍：

| 子域 | 一期做 | 后置 |
|------|--------|------|
| `profile` | 长者档案、联系人与家属授权、健康条目、用药计划与服药记录 | 体征记录、能力评估 |
| `guard` | 机器人设备登记与绑定、下行消息、预警事件与响应记录、设备语音网关 | 预警规则表、通知链路表、体征触发 |
| `mall` | 服务项目、预约单（一次预约一个服务项目，不支付） | 套餐、权益、支付 |
| `album` | 照片上传、查看、删除、家属可见性 | 分组、人物标签 |
| `rehab` | 康复指导管理、关联文档、查看、问答 | 个性化康复计划与打卡 |
| `provider`、`workorder`、`settle`、`ops` | 无 | 全部 |
| `agent` | 长者陪伴、家属服务、运营助手三个角色及对应工具 | 预警研判、周报、回访工作流 |

一期实体共 13 个，见 [design.md](design.md#一期实体范围)。

### 一期前端范围

一期只做运营管理端，由 EntityDef 驱动，覆盖：长者与联系人、设备（创建即绑定、解绑、轮换凭据）、预警（认领、代记已知晓、填写结论）、用药计划、服务项目与预约单、相册、康复指导。家属端和长者端页面不做。

家属端后置的影响：

- 家属不能自助绑定设备、绑定微信、查看照片与预警、代为预约，这些由运营代办。
- 家属只被动收到通知：站内信需要家属登录现有 AAF 网页才看得到，服务号需要家属先绑定微信。因此一期的预警实际依赖运营值班和电话联系，短信渠道对可用性更关键。
- 联系人"已知晓"由运营电话确认后代记。

### 通知渠道

| 接收方 | 渠道 | 一期 |
|---|---|---|
| 运营值班 | 站内信（发给默认值班服务账号） | 开 |
| 运营值班 | 钉钉群机器人（复用现有发送能力） | 开 |
| 联系人 | 站内信（联系人有 AAF 账号时） | 开 |
| 联系人 | 微信服务号、小程序订阅消息 | 后置，随家属端 |
| 联系人 | 短信 | 预留开关，默认关闭；框架已有发送能力，开启前需要先申请并审核短信模板 |

预警同时通知运营值班和联系人，不做逐级升级；运营电话联系联系人。运营 7x24 值班使用一个默认的统一服务账号，一期不做排班。

### 不在范围

- 机构养老（床位、入退住、巡房、机构费用）。
- 自研硬件与固件；机器人终端软件改造在机器人工程内完成，不属于本故事的后端交付，但在设计文档中列出配合项。
- 医疗诊断与处方；康复方案的生成。系统只提供知识参考与异常提示。
- 监控视频、预警现场画面、人脸特征上传到后台。
- 家属端前端（家属自助绑定设备、绑定微信、查看相册与预警、自助确认预警）与长者端页面，后续另立故事；本故事交付后端、运营管理端 EntityDef 与 AI 配置。

## 用户故事

- 家属相关的故事（查看相册、预警、自助确认、自助绑定）一期由运营在管理端代办，家属端上线后开放自助入口；家属一期只被动收到通知。

### 建立长者档案并授权家属

**作为**社区工作人员或家属，**我希望**为长者建档，维护联系人、健康条目，并授权家属查看，**以便**机器人、预警和预约都有统一的对象和依据。

### 跌倒等异常被及时发现

**作为**独居长者的家属，**我希望**机器人发现疑似跌倒、长时间没有活动或长者一键求助时，系统先确认长者状况，无人响应则按顺序通知我，**以便**异常不会被拖延数小时才发现。

### 按时吃药

**作为**长者，**我希望**机器人在吃药时间提醒我并等我确认，也能直接对机器人说"每天早上八点提醒我吃药"来设置，**以便**不漏服、不用学习复杂界面；**作为**家属，**我希望**对话创建的计划能被通知到我核对，连续漏服时也通知我，**以便**及时关心并防止听错药名。

### 机器人陪伴聊天

**作为**长者，**我希望**机器人用我习惯的称呼、了解我的喜好和禁忌地陪我聊天，**以便**日常不孤单；聊天使用 AAF 助理，语音识别和合成也由 AAF 提供。

### 在线预约服务

**作为**长者或家属，**我希望**浏览服务项目并在线预约时间和地址，**以便**不用到处打电话。运营确认后，机器人在服务当天提醒长者。一期不在线支付，费用线下结算。

### 康复指导

**作为**运营，**我希望**把康复文档整理成康复指导并发布；**作为**长者或家属，**我希望**查看康复指导并就内容提问，得到带出处的回答，**以便**按资料了解康复知识，而不是凭空猜测。

### 机器人拍的照片

**作为**家属，**我希望**长者用机器人拍的照片自动同步到后台，我能查看并管理，**以便**了解长者的日常、分享美好时刻。

### AI 理解并操作养老业务

**作为**家属或运营，**我希望**通过对话查询长者概况、预警进展、用药情况、最近照片、可预约服务并起草预约，**以便**不用学习复杂界面。

### 二期以后的故事

- 服务执行闭环：运营派单给资质有效的护理员，护理员上门签到、服务、签退，家属确认并评价。
- 更多视觉预警：夜间离床与徘徊、卫生间滞留超时；入户人员识别需单独隐私评估。
- 体征与健康监测、能力评估。
- 补贴、分账与对账；短信渠道启用。
- 监管与运营全局视角：质控、投诉、报表、大屏。
- 个性化康复计划、家属周报、家属把照片同步到机器人。

## 功能点

> 以下为一期功能点。后置项见上文"各子域在一期的取舍"和"二期以后的故事"。

### 基础信息

- [ ] 长者档案：基本信息、居住地址、居住形态、称呼与偏好、禁忌
- [ ] 联系人与监护授权：紧急联系人、家属绑定账号、优先级、授权范围（查看健康、查看服务、代为预约）
- [ ] 健康条目：慢病、过敏、既往史
- [ ] 家属通过授权访问，访问关系使用 ReBAC
- [ ] 管理端维护以上数据，使用 EntityDef

### 预警（跌倒等）

- [ ] 设备配对与绑定：机器人未绑定时显示配对码，已登录的运营在管理端新建设备，填写配对码、选择长者和设备所有者完成绑定；机器人一次性取得设备凭据与 MQTT 接入参数
- [ ] 解绑：运营可解绑，解绑后凭据立即失效并断开连接；重新配对即换新凭据
- [ ] MQTT 设备通道（按既有通信设计的子集）：上行在线状态、心跳、预警事件、确认、结果；下行提醒、撤销、配置；下行指令签名、有效期、幂等
- [ ] 设备 REST 接口：机器人简报、照片上传
- [ ] 预警事件：跌倒疑似、一键求助、长时间无活动、设备离线
- [ ] 确认窗口 60 秒：跌倒疑似先等待长者确认无恙，超时才通知
- [ ] 通知运营值班（默认值班服务账号站内信，加钉钉值班群消息）和联系人（站内信），同时发出，不做逐级升级；各渠道结果写入响应记录，一个渠道失败不影响其他渠道
- [ ] 短信渠道只预留开关，默认关闭；服务号、小程序通知随家属端后置
- [ ] 运营在管理端认领预警，电话联系联系人后代记"已知晓"；运营填写结论（已处理、误报），备注写明处理人；未认领的预警在列表置顶高亮
- [ ] 设备离线、隐私模式、摄像头被遮挡时暂停无活动判定

### 用药提醒

- [ ] 用药计划：药名、剂量说明、服用时间点、起止日期、启停，管理端维护
- [ ] 对话创建：起草、复述确认、确认后创建；草稿 10 分钟过期；创建后通知联系人核对
- [ ] 到点向长者的机器人下发提醒
- [ ] 长者确认后记录"已服"，稍后提醒或超时记录"跳过"或"漏服"
- [ ] 连续漏服达到阈值时通知联系人
- [ ] 家属可查看服药记录

### 陪伴聊天

- [ ] 设备语音网关：语音识别、对话、语音合成三个出口，设备凭据鉴权
- [ ] 对话使用"长者陪伴"角色，注入机器人简报，只开放该角色的工具集
- [ ] 健康相关回复带免责声明，紧急词直接建议就医
- [ ] 断网时机器人回退到本机大脑（机器人端实现）

### 服务预约

- [ ] 服务项目：名称、说明、单位、价格说明、服务时长、分类（字典）
- [ ] 预约：长者或被授权家属选择项目、时间、地址、备注
- [ ] 预约状态：待确认、已确认、已完成、已取消
- [ ] 运营在管理端确认、取消、标记完成，并线下安排服务人员
- [ ] 预约确认后向长者的机器人下发提醒

### 康复指导

- [ ] 管理：标题、分类、摘要、适用人群说明、关联知识文档、草稿与已发布状态
- [ ] 关联文档的存在性在保存时校验
- [ ] 查看：已发布指导的列表与详情
- [ ] 问答：限定在已发布指导所关联的文档范围内检索并回答，带引用与免责声明

### 相册管理

- [ ] 设备上传照片：设备凭据鉴权，幂等，格式与大小校验
- [ ] 运营在管理端查看照片、添加说明、删除
- [ ] 原图通过受控地址访问，不生成永久公开链接；家属查看与可见性控制随家属端后置

### 智能层

- [ ] 工具：长者概况、预警进展、用药计划查询、用药计划起草与确认、可预约服务、起草预约、康复指导问答、最近照片
- [ ] 长者陪伴、家属服务、运营助手三个角色，工具按角色限定

## 验收标准

```gherkin
Feature: 养老业务模块（一期）

  Scenario: 家属只能查看被授权的长者
    Given 长者 A 授权家属甲查看健康与服务
    When 家属乙查询长者 A 的健康条目
    Then 返回无权访问
    When 家属甲查询长者 A 的健康条目
    Then 返回健康条目
```

## 约束条件

- 健康与身份信息属于敏感数据：字段集分级输出，导出需权限；调用第三方的工具参数不得包含姓名、证件号、手机号、病史。
- 监控视频、预警现场画面、人脸特征不上传；预警上行只有语义事件、置信度和区域。用户主动或经授权自动拍摄的照片可以上传，且需要长者或监护人同意并留痕。
- 预警是辅助手段，不能替代人工看护；系统不自动拨打急救电话；不提供诊断、处方、用药建议与个体化康复方案。
- 短信渠道关闭期间，紧急预警只有站内信和服务号两个渠道，站内信离线时不可见，这是已知风险。
- 设备凭据、设备语音网关是新的认证入口，MQTT 设备通道涉及证书与签名，进入开发前需要人类架构与安全审核。
- 设备通信按 AAF 已采纳的 [Qt 机器人通信设计](../../../design/apps/modbot/qt-robot-communication.md) 实现；一期不保留 REST 兜底路径。
- 摄像头与预警功能的启用需要长者或监护人同意并留痕。
- 租户与数据范围：长者数据对家属的可见性通过 ReBAC 关系控制。
- 遵循 AGENTS.md 的硬规则：不加兼容层、不做任务外重构、复用已有模式、管理端使用 EntityDef。
- 子域之间只能通过 `api/` 接口与领域事件交互，禁止跨域访问 entity 与 repository。
- 错误码使用 `10_000_000 ~ 10_999_999` 段，按子域再分段，见设计文档。

## 分期

| 期 | 内容 | 目标 |
|----|------|------|
| 一期 | `profile`、`guard`、`mall`（精简）、`album`、`rehab`、`agent`（最小集） | 七个核心场景。内部按四个里程碑交付：M0 通信基础（EMQX 部署、客户端库、设备模拟器）；M1 基础信息、设备配对与 MQTT 通道、预警、用药提醒（管理端创建）和通知；M2 相册、服务预约；M3 助理与语音接入、对话创建用药、康复指导 |
| 二期 | `provider`、`workorder`；`guard` 的夜间离床与卫生间滞留；`profile` 体征与能力评估；`settle`；`mall` 套餐与支付；短信启用 | 服务履约闭环；固定摄像头节点预警；支付与补贴 |
| 三期 | `ops`；入户人员识别；个性化康复计划；家属周报 | 监管运营；高隐私场景 |

分期是建议，需人类确认。每期单独拆技术任务，进入各自的迭代。

## 待确认问题

无阻塞开发的待确认问题。已确认的决定：

- 设计整体于 2026-10-15 通过人类审核。
- 运营管理端先做，家属端不做；代绑定时设备所有者必须指定为一个用户账号；运营 7x24 值班用一个默认统一的服务账号，一期不做排班。
- 预警同时通知运营值班（站内信加钉钉群，与新用户注册通知共用现有的机器人和群）和联系人站内信，不做逐级升级；确认窗口 60 秒；短信预留开关默认关闭。
- 语音计费主体为设备所有者用户；对话创建的用药计划立即生效并通知联系人核对；康复指导不设审核；相册不限总容量与保留期限；预警事件与响应记录一期不清理；阈值默认值（无活动 4 小时、连续漏服 2 次）按默认实现，全局配置可调。
- broker 使用 EMQX 单节点，与 Java 服务同机独立运行；一期一台测试设备，不做压测与容量规划，不考虑私有化交付。
- 下行指令的租约字段对提醒和配置这类非物理能力暂不实现，物理能力启用前补齐。
- 设备通信按既有通信设计实现；一期以实现功能为主，不提前扩展（不做凭据轮换、批量导入序列号、排班、逐级升级、直传对象存储）。
