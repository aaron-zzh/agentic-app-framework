## 1. 问题

**现象**（用户或 CI 可观察到的表现）：

- 用一两句话描述"什么在坏掉"
- 举一个具体的用户报告、日志片段或测试失败输出

**影响面**：

- 影响哪些模块 / 用户场景 / 接口
- blocker 还是 major（按 [协作规范 问题分级](../../reference/team/collaboration-standard.md)）

## 2. 根因

### 代码定位

列出相关文件 + 行号，**不是猜测，是读过代码的定位**：

- `apps/service/src/main/java/.../XxxService.java:42-58` — 责任描述
- `apps/webui/src/app/xxx/page.tsx:15-30` — 责任描述

### 根因分析

不只是 "bug 在这里"，而是解释"为什么这个 bug 会出现"。常见切入角度：

- **对称性分析**：生产者 vs 消费者、创建 vs 删除、加密 vs 解密、事务开启 vs 提交、注册 vs 注销。缺一侧就是 bug 温床。
- **时序/并发**：多个 onSuccess 回调顺序不确定、race condition
- **假设失效**：某个默认值、某个 fallback、某个 staleTime 在边缘场景破功
- **架构分层违反**：domain 反向依赖 infrastructure、service 层越界调 controller

## 3. 复现步骤

**可操作的复现路径**，让任何人都能按步骤验证问题存在：

```text
1. 环境准备：...
2. 操作：...
3. 观察：... （浏览器 console / 后端日志 / 数据库状态）
4. 预期：...
5. 实际：...
```

如果本地复现需要特殊条件（如网络层丢包、NAT、睡眠），说明推荐方法：

- 方法 A：pfctl / tc 丢包（最接近真实场景）
- 方法 B：临时改代码吞消息（模拟效果）
- 方法 C：E2E 注入（适合 CI 回归）

## 6. 验证方法

### 自动化验证

- 新增/修改的单测：路径 + 用例
- 新增/修改的验收测试：路径 + 对应 AC
- ArchUnit 规则（如涉及分层）：规则描述

### 手动验证

- 按第 3 节"复现步骤"验证修复后不再出现
- 回归检查：相邻功能是否被破坏

### 验证通过标准

- [ ] 所有新增测试通过
- [ ] `pnpm check:affected` 全绿
- [ ] `pnpm acceptance:affected` 全绿
- [ ] 手动复现不再触发问题
