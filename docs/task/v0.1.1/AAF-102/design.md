# 设计：PromptEnvelope 逐次物理调用冻结与技能动态加载（AAF-102）

## 参考文档

- 目标合同：[core/prompt.md](../../../design/framework/intelligent/core/prompt.md)（`PromptEnvelope` 字段与冻结时机的唯一真理源）
- 运行时契约：[runtime.md](../../../design/framework/intelligent/runtime.md)

## 问题陈述

`prompt.md` 已定义 `PromptEnvelope` 对应**一次物理模型请求**、append-only、不回写 `ExecutionProfileSnapshot`，但代码中该类型不存在。当前实现只在**一次执行开始时**冻结一份 `ExecutionProfileSnapshot`（`AssistantApplicationService:1523` 调 `executionProfiles.freeze`），此后 Harness ReAct 循环内的全部模型调用共用这一份。

由此产生两个后果：

- 恢复时要求画像与开始时完全一致（`AssistantApplicationService.resolveExecutionProfile:1100-1145` 有六处一致性断言），把"每次请求前必须决定这次请求的内容"过度放大为"整个执行期不许变"。
- 运行时动态加载被完全排除。`AgentScopeSpecCompiler` 关掉 harness 全部内置能力有其正确性理由，但连带使 `ai_skill_reference.load_mode = ON_DEMAND` 与 `SkillActivationMode.ON_DEMAND` 无法表达"运行中按需拉取"，`ai_skill_reference` / `ai_skill_knowledge_binding` 两张表因此零接线。

## 关键约束与已核实的事实

| 事实 | 依据 |
|---|---|
| 只有"本次请求带哪些工具 schema 与哪些正文"无法事后补记，其余画像字段都是已发生事实 | HTTP 请求发出即不可变 |
| AAF 逻辑全部在 AgentScope 外部，仅 ReAct 循环、模型调用、工具 schema 解析在内部 | `AgentScopeSpecCompiler` 全量 `disable*()` |
| 边界仅三个穿越点 | `PortBackedAgentTool.callAsync`（内→外）、`streamEvents`（内→外）、`ToolSuspendException`（外→内控制信号） |
| AgentScope 提供 raw model call 拦截 | `MiddlewareBase.onModelCall(agent, ctx, ModelCallInput, next)`，`ModelCallInput(messages, tools, options, model)`；经 `ReActAgent.Builder.middleware(...)` 注册 |
| 挂起—外部处理—续跑已是成熟在用模式 | `PortBackedAgentTool` 已对人工授权与转人工抛 `ToolSuspendException`；AgentScope 侧转 `ToolResultBlock.suspended`，循环以 `GenerateReason.TOOL_SUSPENDED` 干净退出 |
| 有副作用动作的真实闸门是运行时授权记录，不是冻结画像 | `DefaultToolGateway.invoke` 每次调用查 `grants.findActive(...)`，按 `MissingGrantBehavior` 决定 DENY / 要求预授权 / 发起 `HumanApproval` |
| AAF 不依赖 AgentScope 持久历史 | `requireNoHiddenPersistentHistory` 强制 `agent_state` 为空，历史始终由 AAF 在 `command.messages()` 中携带 |

`MiddlewareBase.onModelCall` 是本方案成立的关键：它使 AAF 能在 `prompt.md` 要求的冻结点（provider 适配之后、请求发送之前）捕获**真实**请求内容，而无需接管 ReAct 循环。

## 设计决策（ADR）

| 决策 | 选择 | 原因 |
|---|---|---|
| 快照拆分方式 | `ExecutionProfileSnapshot` 保留为执行不变量；新增 `PromptEnvelope` 承载逐次可变部分 | 与 `prompt.md` 既有契约一致（前者只能被引用，不能被后者修改）；避免把不变量重复写入每份 envelope |
| envelope 捕获点 | 注册 `MiddlewareBase.onModelCall` 中间件 | 唯一能拿到真实 messages / tools / options / model 的外部切点；旁观 `MODEL_CALL_START` 只能记录"AAF 授予的边界"，不等于实际请求 |
| 动态加载实现 | 新增 `skill.load` / `skill.reference.load` 工具，抛 `ToolSuspendException` 挂起后追加新 envelope 续跑 | 完全复用现有挂起—续跑链路，不引入新架构概念，不接管循环 |
| 恢复语义 | 取该 execution 最大 `envelope_seq` 继续 | 恢复应回到真实最新状态，而非开始时的预判 |
| 授权一致性 | 继续依赖 `grants` 表 + `MissingGrantBehavior`，不依赖画像不变 | 运行时闸门已存在且更精确；可见工具集本就应按次请求计算 |
| 存量数据 | 不写数据迁移 | 遵循 `v7__aigc_schema.sql:2`「所有环境必须清空后按 Flyway 顺序重建」+ dev `aaf.flyway.clean-on-start` |

## 数据模型

`ExecutionProfileSnapshot` 保留，`(tenant_id, execution_id)` 唯一约束不变，`snapshot_payload` 移出四个可变字段：`skillExecutionProfile`、`compiledSystemPrompt`、`toolAuthorizationRules`、`contextCompression`。其余 15 个字段构成执行不变量。

新增表：

```sql
CREATE TABLE ai_prompt_envelope (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id VARCHAR(128) NOT NULL,
    task_id VARCHAR(128) NOT NULL,
    execution_id VARCHAR(128) NOT NULL,
    envelope_seq INTEGER NOT NULL,
    attempt_no INTEGER NOT NULL DEFAULT 1,
    prompt_sha256 VARCHAR(64) NOT NULL,
    trigger VARCHAR(32) NOT NULL,
    envelope_payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    CONSTRAINT uk_prompt_envelope UNIQUE (tenant_id, execution_id, envelope_seq),
    CONSTRAINT ck_prompt_envelope_seq CHECK (envelope_seq >= 1),
    CONSTRAINT ck_prompt_envelope_attempt CHECK (attempt_no >= 1)
);
```

| 列 | 合同 |
|---|---|
| `envelope_seq` | 每 execution 从 1 严格递增，一次 provider 发送一份，重试不复用 |
| `attempt_no` | 同一逻辑调用的传输重试次数，与 `envelope_seq` 正交 |
| `prompt_sha256` | 从 payload 提列，供查询与去重，不作为唯一键 |
| `trigger` | `INITIAL` / `SKILL_LOADED` / `REFERENCE_LOADED` / `COMPACTED` / `RETRY` |
| `envelope_payload` | 实际发送的 messages、tool schemas、生成参数、模型快照、系统提示词编译结果、逐条 hash |

正文按 `prompt.md:141` 要求只进访问受控存储；本表存 hash 与引用，受限正文快照的落地位置沿用该文档定义，不在本任务扩展。

## 接口定义

```java
/** 逐次物理调用的请求信封；append-only，不回写执行画像。 */
public interface PromptEnvelopePort {
    PromptEnvelope append(PromptEnvelope envelope);

    Optional<PromptEnvelope> findLatest(TenantId tenantId, ExecutionId executionId);

    List<PromptEnvelope> findAll(TenantId tenantId, ExecutionId executionId);
}

/** 在 provider 发送前捕获真实请求并落 envelope。 */
public final class PromptEnvelopeCaptureMiddleware implements MiddlewareBase {
    @Override
    public Flux<AgentEvent> onModelCall(
            Agent agent, RuntimeContext ctx, ModelCallInput input,
            Function<ModelCallInput, Flux<AgentEvent>> next);
}

/** 画像升级请求：技能或参考资料需要在下一次物理调用生效。 */
public record ProfileUpgradeRequest(
        ExecutionId executionId, UpgradeKind kind, String targetKey) {
    public enum UpgradeKind { SKILL, SKILL_REFERENCE }
}
```

## 类结构

| 类 | 包 | 职责 |
|---|---|---|
| `PromptEnvelope` | `intelligent.core.prompt` | 逐次请求信封记录，字段按 `prompt.md` 目标结构 |
| `PromptEnvelopePort` | `intelligent.assistant.port` | append / findLatest / findAll 边界 |
| `JpaPromptEnvelopeAdapter` | `intelligent.infrastructure.assistant.persistence` | `ai_prompt_envelope` 持久化，seq 由 DB 唯一约束保序 |
| `PromptEnvelopeCaptureMiddleware` | `intelligent.infrastructure.agentscope.middleware` | `onModelCall` 捕获真实请求并 append |
| `SkillLoadToolHandler` | `intelligent.assistant.application` | `skill.load` / `skill.reference.load` 工具语义，抛画像升级挂起 |
| `ProfileUpgradeResumeDispatcher` | `intelligent.assistant.application` | 挂起后追加新 envelope 并续跑，形状对齐 `ApprovalRecoveryDispatcher` |

## 模块交互

第一步（结构）时序：

```text
AssistantApplicationService  → 冻结执行不变量（ExecutionProfileSnapshot）
  → HarnessAgentExecutionAdapter 启动 Harness
    → [AgentScope 内] ReAct 循环第 N 次模型调用
      → PromptEnvelopeCaptureMiddleware.onModelCall
        → PromptEnvelopePort.append(envelope_seq = N, trigger = INITIAL|RETRY|COMPACTED)
        → next.apply(input)  // 原请求继续发送
```

第二步（动态加载）时序：

```text
[AgentScope 内] LLM 调 skill.load(code)
  → PortBackedAgentTool.callAsync → ToolGateway → SkillLoadToolHandler
    → 抛 ToolSuspendException（画像升级）
  → [AgentScope 内] ToolExecutor 转 suspended → 循环以 TOOL_SUSPENDED 退出
→ HarnessAgentExecutionAdapter 收到终态事件
→ ProfileUpgradeResumeDispatcher
    → 解析技能正文 / 参考资料（按 max_tokens 预算）
    → PromptEnvelopePort.append(trigger = SKILL_LOADED|REFERENCE_LOADED)
    → 以同一 taskId、新 executionId 续跑，工具结果作为 tool result 消息带入
```

## 恢复语义改造

`resolveExecutionProfile` 的六处断言按不变量 / 可变量拆分：

| 断言 | 处置 |
|---|---|
| `taskId` / `assistantId` 与命令一致 | 保留 |
| `invocationPolicy` 与命令一致 | 保留 |
| `compiledSystemPrompt.verify()` 与完全相等 | 删除 |
| `contextCompression` 必须存在 | 删除；缺失表示尚未压缩，是合法中间态 |
| `skillExecutionProfile` 激活集与请求路由一致 | 删除；激活集允许随后续调用增长 |

> **实施偏离记录（2026-08-27）**：原方案设想"`PerCallProfile` 迁入 `PromptEnvelope`，恢复取最新 envelope 拼回完整快照"。
> 实施时发现 `PromptEnvelope` 按 `core/prompt.md` 披露约束只存 hash/长度投影（`MessageSnapshot`/`ToolSchemaSnapshot`），
> 不持有可直接使用的正文对象；而恢复续跑需要的是可直接使用的完整 `SkillExecutionProfile`/`CompiledSystemPrompt`/
> `Map<String,ToolAuthorizationRule>`。把两者合并会让 `PromptEnvelope` 同时承载"审计 hash 投影"与"续跑完整对象"两种
> 语义，字段混杂。改为**职责分离**：`PromptEnvelope`（`core.prompt`）保持只服务审计捕获，不参与恢复；
> `ExecutionProfileSnapshotPort` 改为追加式（`freeze` 不再做相同性校验，`find` 取同一 `execution_id` 下
> `frozen_at` 最新一条），`PerCallProfile` 仍是 `ExecutionProfileSnapshot` 内部记录，未额外拆出新表。
> `resolveExecutionProfile` 未命中最新记录（`find` 返回空）时，判定为"该执行尚未完整开始过一次物理调用"，
> 直接走"未命中"分支重新构造，不抛错——对应 `existing.isPresent()` 为 false 的既有路径，无需新增分支。
> 请求 `resolvedRoute` 与冻结路由一致的断言核实后确认原方案就没有保留，一并删除（该断言依赖的是
> `skillExecutionProfile` 内的激活集比较，随激活集允许增长而失去意义）。

`requireNoHiddenPersistentHistory` 保留不动——它防的是 AgentScope 私自携带历史，与本改造正交。

## 分步范围

| 步 | 范围 | 验收 |
|---|---|---|
| 第一步 | 拆分快照为 `PerCallProfile`；`PromptEnvelope`/端口/表/捕获中间件（审计用途）；`ExecutionProfileSnapshotPort` 改追加式；恢复取最新记录、删除三条失效断言 | 行为不变（写入路径与 accessor 兼容）；`ai_execution_profile_snapshot` 同一 execution 可多行；恢复不再因画像变化失败 |
| 第二步 | `skill.load` / `skill.reference.load` 工具、画像升级挂起与续跑、references 按 `max_tokens` 注入 | `ON_DEMAND` 与 `ai_skill_reference.load_mode` 具备真实语义；`ai_skill_reference` 接入生产链 |

第二步依赖第一步完成。`ai_skill_knowledge_binding`（限定知识库检索范围）不在本任务范围，依赖 L1 读管道三通道接入后单独排期。

## 风险

| 风险 | 应对 |
|---|---|
| `onModelCall` 中间件在响应式链路上阻塞写库 | append 走 `Mono.fromCallable(...).subscribeOn(boundedElastic())`，对齐 `JpaExecutionEventStoreAdapter` 既有做法 |
| envelope 写入量随 ReAct 迭代线性增长 | payload 只存 hash 与引用，受限正文另存；必要时按 execution 保留窗口清理 |
| 第二步每次加载重启 Harness 需重发完整 prompt | token 成本可接受（历史本就每轮全量发送）；逻辑成本为零，与审批挂起同路径 |
| 拆分快照改动 `ExecutionProfileSnapshot` 字段，存量 JSONB 无法反序列化 | 按既有约定清空重建，不写数据迁移 |
| 文档跨三份真理源 | 第一步同步改 `prompt.md` 实现态；第二步同步改 `skill-tool-resolution.md` 的 `ON_DEMAND` 语义与 references 三级加载 |
