# 需求管理规范

> 先写需求，再写代码。让需求成为人类和 AI 的共同真理来源。

- SDD 理念详见 [规范驱动开发（SDD）](../../explanation/spec-driven-development.md)
- 开发实现时须遵循 [开发规范](development-standard.md)
- 实现过程中若发现规范与实际需求冲突，可提出调整申请并说明理由，经评审通过后更新规范

## 核心原则

1. **文档是唯一真理**：代码是文档的实现结果，当代码与文档不一致时，以文档为准并修正代码
2. **需求先行**：任何功能开发前，先在 `docs/prd/` 完成需求编写与评审
3. **可验证**：需求必须能映射到测试用例或验收标准
4. **可演进**：需求随系统一起版本化管理，不是一次性产物

## 需求来源

| 来源 | 说明 | 录入方式 |
|------|------|---------|
| 需求收集 | `requirements.md` 中评估通过的业务需求 | 评估后转入 backlog |
| 路线图拆解 | 版本规划中的功能点 | 协调者拆分后写入 backlog |
| 用户反馈 | `user-feedback.md` 中的有效反馈 | 评估后转入 backlog |
| 改进意见 | `improvements.md` 中采纳的建议 | 评估后转入 backlog |
| 开发过程发现 | 开发中发现的缺失功能或优化点 | 直接写入 backlog |

## 需求生命周期

```
提出 → 评估 → 排期 → 细化 → 设计 → 开发 → 验收 → 完成
```

- **提出**：任何人可提出，写入 backlog 待排期区
- **评估**：协调者评估价值和优先级，决定是否纳入
- **排期**：纳入当前或下一迭代
- **细化**：product agent 输出需求文档（用户故事 + 验收标准）
- **设计**：涉及架构决策时，在 `docs/design/` 中完成设计文档
- **开发**：根据需求规格编码（AI 生成或手写）
- **验收**：按验收标准逐项检查

## 需求拆分

路线图里程碑 → 一级用户故事 → backlog 任务。

### 拆分流程

1. **从路线图提取里程碑**：每个版本的里程碑模块（如"Agent 核心接口"）是拆分起点
2. **拆分为用户故事**：每个里程碑拆分为 1-N 个一级用户故事，每个故事是一个独立可交付的业务价值单元
3. **创建需求文件**：每个用户故事对应一个需求文件 `docs/prd/{module-name}/{feature-name}.md`
4. **写入 backlog**：每个用户故事在 backlog 中创建一条任务（AAF 编号），链接到需求文件

### 拆分原则

- 每个用户故事可独立验收（有明确的 AC）
- 粒度适中：一个迭代内可完成，但不至于琐碎到失去业务含义
- 有依赖关系时在 backlog 中标注 `(依赖: AAF-XXX)`

### 示例

路线图 v0.1 里程碑"Agent 核心接口"拆分为：
- 用户故事 1：Agent 生命周期管理 → `docs/prd/agent/agent-lifecycle.md` → AAF-001
- 用户故事 2：Agent 异常体系 → `docs/prd/agent/agent-exception.md` → AAF-018

## 需求优先级

| 级别 | 含义 | 处理方式 |
|------|------|---------|
| P0 | 阻塞性，不做无法继续 | 立即处理 |
| P1 | 当前迭代必须完成 | 排入当前迭代 |
| P2 | 重要但不紧急 | 排入下一迭代 |
| P3 | 锦上添花 | 待排期 |

## 需求评估

新需求进入评估时，必须对照 [产品概述 #需求评估原则](../../explanation/product-overview.md#需求评估原则) 进行分析，回答以下问题：

1. **是否符合产品定位**：是 AI 原生能力还是传统功能？
2. **框架层 vs 业务层**：该能力应该在框架层通用提供，还是作为业务示例？
3. **核心能力依赖**：需要哪些框架核心能力支撑？是否已具备？
4. **部署模式影响**：是否影响部署模式选择？有无离线要求？
5. **数据安全要求**：是否有数据不出域、本地化等特殊要求？
6. **用户接受度**：如果需要在线部署，如何让用户接受？

评估结论记录在需求详情中，作为排期和设计的依据。

## 需求层级

采用三级结构：**Epic** → **Story** → **Spec**。

### Level 1：Epic（史诗）

描述业务目标和范围，面向版本规划。准备阶段由 product 产出，录入 backlog（AAF 编号）。

```markdown
## Epic

**目标**：<业务目标>

**范围**：<包含哪些能力，不包含什么>
```

### Level 2：Story（用户故事）

描述可独立交付的功能切片，面向业务价值。执行阶段入口由 product 从 Epic 拆分。

```markdown
## 用户故事

**作为** <角色>，**我希望** <功能>，**以便** <价值>

**完成条件**：<做到什么程度算完成>
```

### Level 3：Spec（需求规格）

描述"具体怎么做"，面向实现。执行阶段由 product + architect 协作完成，包含精确 AC 和技术细节。

```markdown
## 需求规格

### 验收标准（Gherkin）
Given <前置条件>
When <操作>
Then <预期结果>

### 数据模型

#### 概念登记表

每个产品概念必须对应唯一数据实体，禁止一个概念散落在多张表或多个概念共用一张表：

| 产品概念 | 数据实体 | 主表 | 说明 |
|---------|---------|------|------|
| {概念名} | {Entity 类名} | {表名} | {一句话说明} |

**规则**：
- 一个概念 = 一个 Entity = 一张主表（1:1 映射）
- 发现一个概念需要多张表 → 拆分为多个概念
- 发现多个概念共用一张表 → 合并为一个概念或拆表

（实体、字段、关系）

### 接口定义
（API 路径、参数、响应）

### 约束与边界
（校验规则、异常处理、性能要求）

### 测试要点
- **验收测试**：JUnit 5 `*AcceptanceTest.java`（AC 用 `@DisplayName` 引用）
- **单元测试**：JUnit 5 + Mockito
- **关键场景**：（边界条件、异常路径）
```

## 开发流程

```text
Epic（Level 1）→ Story 拆分（Level 2）→ Spec + 技术设计（Level 3）→ 评审 → 实现 → 验证
   准备阶段                    执行阶段入口
```

1. **编写 Epic（Level 1）**：准备阶段由 product 完成，描述业务目标和范围，录入 backlog
2. **拆分 Story（Level 2）**：执行阶段入口由 product 将 Epic 拆分为可独立交付的 Story
3. **细化 Spec + 技术设计（Level 3）**：product 补充精确 AC、数据模型、业务规则、约束；architect 完成接口定义、类结构、模块交互、ADR；architect 将 Story 拆分为技术任务（`#XXXNN`）
4. **评审**：🔴 高风险设计必须人类审核
5. **实现**：根据规范编码（AI 生成或手写）
6. **验证**：对照 Spec 中的 AC 和测试要点验收

## 需求变更

变更不可避免，但需要受控。

| 时机 | 流程 |
|------|------|
| 细化前 | 直接修改 backlog 描述 |
| 细化后、开发前 | 更新需求文档，通知 architect 评估设计影响 |
| 开发中 | 协调者评估影响范围，决定：①当前迭代吸收 ②推迟到下一迭代 ③拆分为新任务 |
| 开发后 | 作为新需求重新走流程 |

变更记录在对应任务的需求文档底部追加「变更记录」：

```markdown
## 变更记录

| 日期 | 变更内容 | 原因 | 影响评估 |
|------|---------|------|---------|
```

## 与设计文档的关系

需求文档描述"做什么"，设计文档描述"怎么做"。需求文档是该 Epic/Story 所有相关文档的**统一查询入口**，所有相关设计文档必须在需求文档的"相关设计"章节中维护链接。

```markdown
## 相关设计

- 迭代架构设计：[v{version} 架构设计方案](../design/v{version}-design.md)
- 产品设计：[{功能名称}产品设计](../design/{module}/{feature}-product-design.md)
- 技术设计：[{功能名称}技术设计](../task/{version}/{AAF-XXX}/design.md)
```

**维护规则：**

| 时机 | 操作 | 负责人 |
|------|------|--------|
| 创建 Epic（一级用户故事） | 链接迭代架构设计文档 | product / 协调者 |
| 细化 Story（执行阶段 2.1） | 链接产品设计文档（如有） | product |
| 完成技术设计（执行阶段 2.1） | 链接技术设计文档（ADR） | architect |
| 新增任何相关设计文档 | 同步更新需求文档的"相关设计"章节 | 文档创建者 |

设计文档统一存放在 `docs/design/` 目录下，详见 [架构设计方法论](../../design/Readme.md)。

## 与任务管理的关系

需求文档在 [任务管理](../../task/Readme.md) 中被引用：

```markdown
⏳ 实现 XXX 功能 → spec: `docs/prd/{module-name}/xxx.md`
```

任务开发前，确认对应需求已编写并评审通过。
