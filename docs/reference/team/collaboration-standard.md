# 协作规范

> 本文档定义每个流程环节中人、AI、系统三方**如何协作**。流程定义见 [过程规范](process-standard.md)。

## 协作哲学

### 问题求解的本质：迭代递归 MapReduce

```text
人类提出问题
 ↓ AI 分析，优先设计系统方案
 ↓ 分解（Map）
子问题1  子问题2  子问题3
 ↓ 每个子问题递归重复此过程
 ↓ 系统并行执行
 ↓ AI 汇总（Reduce）
结果 → 人类评估 → 未达目标则迭代 → 每轮迭代让系统能力更强
```

### 三方专长

| 角色     | 擅长                                                               | 不擅长     | 在循环中的作用                                         |
| -------- | ------------------------------------------------------------------ | ---------- | ------------------------------------------------------ |
| **人类** | 创意、价值判断、情感感知、突破性洞察                               | 重复和精确 | 发现有价值的问题，定义成功标准，判断是否继续迭代       |
| **AI**   | 理解推理、模式识别、生成组织；**将模糊意图转化为清晰可执行的表达** | 执行和存储 | 理解问题，拆解任务，优先设计系统方案，汇总结果供人判断 |
| **系统** | 精确执行、持久存储、规模化计算、通信集成                           | 理解和判断 | 并行执行，承载每次迭代的优化成果，越迭代越强           |

### 核心原则

- **系统优先**：能系统化的不交给 AI，能 AI 的不交给人。优先设计/优化系统去解决问题
- **AI 主动**：AI 不等待指令，主动感知上下文、发现模式、组织任务、推荐方案
- **意图优先**：澄清意图优先于执行，宁可多问一句，不猜测执行后再回滚
- **渐进提交**：执行结果先暂存，确认后提交，低置信度操作不直接生效
- **各司其职**：人类聚焦创造性和价值判断，从重复劳动中解放
- **文档对应**：每项开发活动必须有对应的规范文档（指导怎么做）和产出文档（记录做了什么），无规范则先建规范，无产出则活动未闭环

## 协作模式

```text
人类（价值 + 决策）──目标/反馈──→ AI（理解 + 组织）──方案──→ 系统（执行 + 存储）
       ↑                              ↑                           |
       |                              └── 异常/不确定分支回调 ←───┘
       └──────────── 风险升级 / 度量报告 / 异常接管 ←─────────────┘
```

### 人类：发现价值、做出决策

**核心职责**：发现问题、定义目标、创意输入、价值判断、关键确认、纠偏校正

**可以放手**：标准实现、重复性流程、知识检索、格式转换、数据汇总

**介入触发**：

| 类型 | 触发条件                                        |
| ---- | ----------------------------------------------- |
| 主动 | 发现问题 / 定义目标 / 创意输入 / 价值判断       |
| 被动 | 置信度 < 0.7 / 不可逆操作 / 规范冲突 / 异常告警 |

### AI：理解意图、组织执行

AI 的核心价值是**将模糊意图转化为系统可执行的方案**，优先思考"能否让系统来解决"。

**主动行为（无需用户触发）**：

- 感知上下文变化，发现重复劳动和潜在任务
- 识别可系统化的重复模式，主动提议优化系统而非重复执行
- 主动建立任务、推荐方案、引导用户聚焦高价值决策
- 与用户协作优化提示词，持续改进生成质量
- 持续学习用户偏好，在用户设置基础上主动改进自己

**响应行为（用户触发后）**：

- 意图理解：识别目标、约束、优先级，不清晰则主动澄清
- 方案设计：优先设计系统方案（工作流、规则、自动化），其次才是 AI 直接处理
- 任务拆解：将复杂问题递归分解为系统可并行执行的子任务（Map）
- 结果汇总：聚合系统执行结果，生成人类可读的洞察（Reduce）
- 结果评估：执行后自评，置信度不足主动上报，不静默输出

**不能做**：自行决定目标和优先级 / 置信度不足时静默执行 / 绕过人类确认直接提交不可逆操作

### 系统：精确执行、持续运转

系统始终在运转，承载每轮迭代的优化成果，为 AI 和人类提供计算底座。

- 精确执行、持久存储、并行计算、任务调度、流程编排
- 定时触发、通信集成、数据同步、外部接入
- CI 自动编译、运行测试、静态分析
- 质量门控自动统计并阻断不达标的提交
- 记录所有交互数据，供 AI 感知和人类审计

## 主导权切换

主导权根据任务确定性和置信度实时切换，不是静态分配。

### 切换规则

| 任务特征           | 主导方          | 另一方角色            |
| ------------------ | --------------- | --------------------- |
| 发现问题、创新探索 | 人类            | AI 辅助分析、提供方案 |
| 目标明确、可系统化 | AI 设计系统方案 | 人类确认，系统执行    |
| 流程确定、重复执行 | 系统            | 人类监督，AI 处理异常 |
| 置信度跌破阈值     | 强制转人类      | AI 提供状态快照和建议 |

### 置信度门控

```text
> 0.9  → 自动执行，结果暂存，异步通知
0.7-0.9 → 展示执行计划，等待确认
< 0.7  → 暂停，说明原因，转人工处理
```

### 切换协议

- 人 → AI：人类提出问题后，AI 分析并优先设计方案，人类进入监督态
- AI → 系统：方案确定且置信度高，转交系统/工作流执行
- 系统 → AI：遇到不确定分支或异常，回调 AI 处理
- AI → 人：置信度跌破阈值 / 不可逆操作 / 规范冲突，交还控制权，附带状态快照和建议选项

### 防退化约束

- AI 不允许在置信度不足时降低标准静默执行
- 人类未响应不自动超时执行，保持等待态
- 每次主导权切换记录日志，支持事后审计

## 风险等级与审核

| 风险等级 | 人类响应 | 示例                                   |
| -------- | -------- | -------------------------------------- |
| 🟢 低     | 可跳过   | 修复 typo、增加日志、小重构            |
| 🟡 中     | 建议抽查 | 新增接口、修改业务逻辑、依赖升级       |
| 🔴 高     | 必须审查 | 架构调整、接口删除、权限变更、数据迁移 |

> 🔴 高风险设计必须等人类审核后再进入开发环节。

**审核产出规范**：每个需要人类审核的环节，AI 必须输出对应的文档作为审核交付物。无文档则审核无法闭环。

## 异常处理

当出现置信度跌破阈值、沙箱告警、规范冲突时：

1. 立即暂停当前执行
2. 保存执行现场快照
3. 向人类说明原因 + 提供建议选项
4. 等待人类决策后继续或回滚

## 3. 执行阶段

### 3.1 需求细化

| 维度              | 说明                                               |
| ----------------- | -------------------------------------------------- |
| **人类**          | 可审核，不阻塞。提供业务判断和优先级               |
| **AI（product）** | 结构化用户故事（功能点、约束、AC），标注非功能需求 |
| **系统**          | 文档模板                                           |
| **审核**          | 🟢 可跳过，人类有意见随时反馈                       |

### 3.2 技术设计

| 维度                | 说明                                                               |
| ------------------- | ------------------------------------------------------------------ |
| **人类**            | 🔴 高风险设计必须审核后再进入开发                                   |
| **AI（architect）** | 接口定义（完整签名）、类结构设计、模块交互、数据建模（ER 关系、表结构、约束、索引）、性能架构设计、设计决策记录 |
| **系统**            | 文档模板、Git 版本管理                                             |
| **审核**            | 🔴 高风险必审，🟡 中风险建议审，🟢 低风险可跳过                       |

### 3.3 UI/交互设计

> 涉及前端界面的任务触发，纯后端任务跳过。

| 维度               | 说明                                                               |
| ------------------ | ------------------------------------------------------------------ |
| **人类**           | 主导创意和交互决策，审核设计稿                                     |
| **AI（designer）** | 界面布局和交互流程设计，组件规范和设计 token，响应式和多端适配方案 |
| **系统**           | 设计工具、组件库                                                   |
| **审核**           | 🟡 人类审核设计稿和交互方案                                         |

### 3.4 编码实现

| 维度                  | 说明                                                   |
| --------------------- | ------------------------------------------------------ |
| **人类**              | 处理复杂逻辑和跨端协调                                 |
| **AI（developer-*）** | 按技术设计和 UI 设计编码，按端并行，输出源码和开发日志 |
| **系统**              | IDE、Git 分支、CI 编译检查                             |
| **审核**              | 人类按需介入                                           |

### 3.5 验证（单元测试/自测）

| 维度                  | 说明                                                 |
| --------------------- | ---------------------------------------------------- |
| **人类**              | —                                                    |
| **AI（developer-*）** | 编写单元测试（覆盖核心逻辑），自测冒烟（主流程跑通） |
| **系统**              | CI 自动运行测试、Testcontainers、静态分析            |
| **审核**              | 系统自动（CI 通过/失败）                             |

### 3.6 代码审查

| 维度                | 说明                                                           |
| ------------------- | -------------------------------------------------------------- |
| **人类**            | 🟡 可抽查中高风险变更                                           |
| **AI（architect）** | 规范合规检查（命名、结构、异常处理），设计符合性检查，安全审查 |
| **系统**            | CI lint / 静态分析                                             |
| **审核**            | architect 审技术，人类按风险抽查                               |

### 3.7 代码重构

> 审查发现结构性问题时触发，非每次必须。

| 维度                  | 说明                                         |
| --------------------- | -------------------------------------------- |
| **人类**              | 🟡 大范围重构需审核方案                       |
| **AI（developer-*）** | 消除重复代码和坏味道，优化模块结构和依赖关系 |
| **系统**              | CI 确保重构后测试全部通过                    |
| **审核**              | 🟢 小重构可跳过，🟡 大重构建议审               |

### 3.8 确认（验收测试）

| 维度             | 说明                                             |
| ---------------- | ------------------------------------------------ |
| **人类**         | 设计边界场景和异常路径                           |
| **AI（tester）** | 对照 AC 逐条编写验收测试，集成测试，需求覆盖验证 |
| **系统**         | CI 自动运行测试                                  |
| **审核**         | 人类可审核测试覆盖度                             |

### 3.9 过程审计

| 维度         | 说明                                                           |
| ------------ | -------------------------------------------------------------- |
| **人类**     | 审计关键节点                                                   |
| **AI（qa）** | 检查流程合规（是否按流水线执行），检查规范遵守，检查文档完整性 |
| **系统**     | 度量数据采集                                                   |
| **审核**     | qa 审过程，人类审计关键节点                                    |

### 3.10 质量门控

| 维度             | 说明                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| **人类**         | 🔴 高风险需确认通过                                                       |
| **AI（协调者）** | 统计 blocker/major/minor 数量，判定通过或回退                            |
| **系统**         | CI 门控自动阻断（编译失败、测试不通过）                                  |
| **通过条件**     | blocker = 0 且 major ≤ 2                                                 |
| **不通过**       | 回退：需求→product，设计→architect，实现→developer，测试→tester，过程→qa |

## 接口契约

- 模块间通过 Java 接口交互，接口由提供方定义，使用方只依赖接口
- 改接口签名 → 协调者同步所有使用方
- 加新接口 → 定义方自行添加
- 改 common/ → 必须通过协调者评估影响

## 变更规则

| 变更类型     | 流程                          |
| ------------ | ----------------------------- |
| 需求变更     | 按需求管理规范走变更流程      |
| 规范变更     | 协调者评估后更新              |
| 架构变更     | architect 出方案 + 🔴 人类审核 |
| 接口签名变更 | 协调者同步所有使用方          |

## 反馈方式

| 方式                             | 适用场景           | 响应速度 |
| -------------------------------- | ------------------ | -------- |
| 直接在对话中告知协调者           | 紧急事项、即时决策 | 最快     |
| 修改对应文档后告知协调者重新读取 | 需求/设计变更      | 中等     |
| 写入反馈文档                     | 非紧急改进建议     | 异步     |
