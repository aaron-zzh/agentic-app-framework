# 人机协作规范

## 核心原则

- 充分发挥专长
- AI 不等待人类审批，完成即提交；人类不被阻塞，按需检查。

## 协作流程

```
想法 → product(requirement.md) → [人类可审核] → architect(design.md) → [🔴 必须审核] → developer(代码) → tester(test-report.md) → reviewer(review.md) → [人类按风险等级审核] → 质量门控
```

1. 人类描述想法，协调者拆解任务
2. product 输出 requirement.md — 人类可审核，不阻塞
3. architect 输出 design.md — 🔴 高风险设计必须审核后再开发
4. developer 实现代码 — AI 发现需人类决策的事项标注 `🔴 需人类决策`，继续推进其他任务
5. tester 输出 test-report.md
6. reviewer 输出 review.md，标注风险等级 — 人类按等级决定是否审查
7. 质量门控通过后交付（blocker=0 且 major≤2）

所有文档产出到 `docs/task/{版本}/{任务名}/`。

## 风险等级

| 等级 | 含义 | 人类响应 |
|------|------|---------|
| 🟢 低风险 | 常规变更 | 可跳过 |
| 🟡 中风险 | 有设计取舍 | 建议抽查 |
| 🔴 高风险 | 架构/破坏性/安全变更 | 必须审查 |

## 人类侧职责

- 按需查看工作日志和 review.md，优先关注高风险项
- 对 `🔴 需人类决策` 的事项给出决策
- 版本发布前做最终验收

## 反馈方式

- 直接在对话中告知协调者（最快）
- 修改对应文档后告知协调者重新读取
- 写入 `docs/user-feedback.md`（非紧急）


## 协作模型

人类负责**决策和判断**，AI 负责**执行和检查**。两者通过文档沟通，通过风险等级决定审查深度。

## 任务流水线

每个任务按以下流水线推进，协调者自动编排：

```text
人类想法
  → product(requirement.md) → [人类可审核]
    → architect(design.md) → [🔴 高风险必须审核]
      → developer-*(代码 + 单元测试)
        → architect(代码审查)
          → tester(test-report.md)
            → qa(过程审计)
              → 质量门控 → 交付
```

### 各环节说明

| 环节 | AI 智能体 | 产出 | 人类参与 |
|------|-----------|------|---------|
| 需求细化 | product | requirement.md | 可审核，不阻塞 |
| 技术设计 | architect | design.md | 🔴 高风险必须审核后再开发 |
| 编码实现 | developer-* | 源码 + 单元测试 | 复杂逻辑可介入 |
| 代码审查 | architect | 审查意见 | 可抽查 |
| 验收测试 | tester | test-report.md | 可审核 |
| 过程审计 | qa | 审计记录 | 关键节点审计 |
| 质量门控 | 协调者 | 通过/回退 | 🔴 高风险需确认 |

### 回退规则

质量门控不通过时，按问题类型回退对应环节：

| 问题类型 | 回退到 |
|---------|--------|
| 需求理解偏差 | product |
| 设计缺陷 | architect |
| 实现问题 | developer |
| 测试不足 | tester |
| 过程违规 | qa |

## 风险等级

| 等级 | 含义 | 人类响应 |
|------|------|---------|
| 🟢 低风险 | 常规变更 | 可跳过 |
| 🟡 中风险 | 有设计取舍 | 建议抽查 |
| 🔴 高风险 | 架构/破坏性/安全变更 | 必须审查 |

## AI 侧规则

- 完成任务后立即提交代码并记录到工作日志
- 发现需人类决策的事项标注 `🔴 需人类决策`，继续推进其他任务
- 批量修改文件（≥5 个）前需向人类申请
- 所有文档产出到 `docs/task/{版本}/{任务名}/`

## 人类侧规则

- 按需查看工作日志和审查报告，优先关注 🔴 高风险项
- 对 `🔴 需人类决策` 的事项给出决策
- 版本发布前做最终验收

## 反馈方式

| 方式 | 适用场景 |
|------|---------|
| 直接在对话中告知协调者 | 最快，紧急事项 |
| 修改对应文档后告知协调者重新读取 | 需求/设计变更 |
| 写入 `docs/user-feedback.md` | 非紧急改进建议 |

## 质量门控标准

- **通过条件**：blocker=0 且 major≤2
- **不通过**：回退对应环节修复后重新进入门控

## 接口契约

- 模块间通过 Java 接口交互，接口由提供方定义，使用方只依赖接口
- 改接口签名 → 协调者同步所有使用方
- 加新接口 → 定义方自行添加
- 改 common/ → 必须通过协调者评估影响

## 变更规则

- 需求变更按[需求管理规范](../../spec/README.md)走变更流程
- 规范变更由协调者评估后更新
- 架构变更需架构师出方案 + 人类审核
