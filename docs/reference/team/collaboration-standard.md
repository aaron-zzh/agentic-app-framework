# 协作规范

> 本文档定义每个流程环节中人、AI、系统三方**如何协作**。流程定义见 [过程规范](process-standard.md)。

## 协作哲学

### 问题求解的本质：迭代递归 MapReduce

```text
人类提出问题
 ↓ AI 分析，优先设计系统方案
 ↓ 分解（Map）
子问题1  子问题2  子问题3
 ↓ 每个子问题递归重复此过程
 ↓ 系统并行执行
 ↓ AI 汇总（Reduce）
结果 → 人类评估 → 未达目标则迭代 → 每轮迭代让系统能力更强
```

### 三方专长

| 角色     | 擅长                                                               | 不擅长     | 在循环中的作用                                         |
| -------- | ------------------------------------------------------------------ | ---------- | ------------------------------------------------------ |
| **人类** | 创意、价值判断、情感感知、突破性洞察                               | 重复和精确 | 发现有价值的问题，定义成功标准，判断是否继续迭代       |
| **AI**   | 理解推理、模式识别、生成组织；**将模糊意图转化为清晰可执行的表达** | 执行和存储 | 理解问题，拆解任务，优先设计系统方案，汇总结果供人判断 |
| **系统** | 精确执行、持久存储、规模化计算、通信集成                           | 理解和判断 | 并行执行，承载每次迭代的优化成果，越迭代越强           |

### 核心原则

- **系统优先**：能系统化的不交给 AI，能 AI 的不交给人。优先设计/优化系统去解决问题
- **AI 主动**：AI 不等待指令，主动感知上下文、发现模式、组织任务、推荐方案
- **意图优先**：澄清意图优先于执行，宁可多问一句，不猜测执行后再回滚
- **渐进提交**：执行结果先暂存，确认后提交，低置信度操作不直接生效
- **各司其职**：人类聚焦创造性和价值判断，从重复劳动中解放
- **文档对应**：每项开发活动必须有对应的规范文档（指导怎么做）和产出文档（记录做了什么），无规范则先建规范，无产出则活动未闭环

## 协作模式

```text
人类（价值 + 决策）──目标/反馈──→ AI（理解 + 组织）──方案──→ 系统（执行 + 存储）
       ↑                              ↑                           |
       |                              └── 异常/不确定分支回调 ←───┘
       └──────────── 风险升级 / 度量报告 / 异常接管 ←─────────────┘
```

### 人类：发现价值、做出决策

**核心职责**：发现问题、定义目标、创意输入、价值判断、关键确认、纠偏校正

**可以放手**：标准实现、重复性流程、知识检索、格式转换、数据汇总

**介入触发**：

| 类型 | 触发条件                                        |
| ---- | ----------------------------------------------- |
| 主动 | 发现问题 / 定义目标 / 创意输入 / 价值判断       |
| 被动 | 置信度 < 0.7 / 不可逆操作 / 规范冲突 / 异常告警 |

### AI：理解意图、组织执行

AI 的核心价值是**将模糊意图转化为系统可执行的方案**，优先思考"能否让系统来解决"。

**主动行为（无需用户触发）**：

- 感知上下文变化，发现重复劳动和潜在任务
- 识别可系统化的重复模式，主动提议优化系统而非重复执行
- 主动建立任务、推荐方案、引导用户聚焦高价值决策
- 与用户协作优化提示词，持续改进生成质量
- 持续学习用户偏好，在用户设置基础上主动改进自己

**响应行为（用户触发后）**：

- 意图理解：识别目标、约束、优先级，不清晰则主动澄清
- 方案设计：优先设计系统方案（工作流、规则、自动化），其次才是 AI 直接处理
- 任务拆解：将复杂问题递归分解为系统可并行执行的子任务（Map）
- 结果汇总：聚合系统执行结果，生成人类可读的洞察（Reduce）
- 结果评估：执行后自评，置信度不足主动上报，不静默输出

**不能做**：自行决定目标和优先级 / 置信度不足时静默执行 / 绕过人类确认直接提交不可逆操作

### 系统：精确执行、持续运转

系统始终在运转，承载每轮迭代的优化成果，为 AI 和人类提供计算底座。

- 精确执行、持久存储、并行计算、任务调度、流程编排
- 定时触发、通信集成、数据同步、外部接入
- CI 自动编译、运行测试、静态分析
- 质量门控自动统计并阻断不达标的提交
- 记录所有交互数据，供 AI 感知和人类审计

## 主导权切换

主导权根据任务确定性和置信度实时切换，不是静态分配。

### 切换规则

| 任务特征           | 主导方          | 另一方角色            |
| ------------------ | --------------- | --------------------- |
| 发现问题、创新探索 | 人类            | AI 辅助分析、提供方案 |
| 目标明确、可系统化 | AI 设计系统方案 | 人类确认，系统执行    |
| 流程确定、重复执行 | 系统            | 人类监督，AI 处理异常 |
| 置信度跌破阈值     | 强制转人类      | AI 提供状态快照和建议 |

### 置信度门控

```text
> 0.9  → 自动执行，结果暂存，异步通知
0.7-0.9 → 展示执行计划，等待确认
< 0.7  → 暂停，说明原因，转人工处理
```

### 切换协议

- 人 → AI：人类提出问题后，AI 分析并优先设计方案，人类进入监督态
- AI → 系统：方案确定且置信度高，转交系统/工作流执行
- 系统 → AI：遇到不确定分支或异常，回调 AI 处理
- AI → 人：置信度跌破阈值 / 不可逆操作 / 规范冲突，交还控制权，附带状态快照和建议选项

### 防退化约束

- AI 不允许在置信度不足时降低标准静默执行
- 人类未响应不自动超时执行，保持等待态
- 每次主导权切换记录日志，支持事后审计

## 风险等级与审核

| 风险等级 | 人类响应 | 示例                                   |
| -------- | -------- | -------------------------------------- |
| 🟢 低     | 可跳过   | 修复 typo、增加日志、小重构            |
| 🟡 中     | 建议抽查 | 新增接口、修改业务逻辑、依赖升级       |
| 🔴 高     | 必须审查 | 架构调整、接口删除、权限变更、数据迁移 |

> 🔴 高风险设计必须等人类审核后再进入开发环节。

**审核产出规范**：每个需要人类审核的环节，AI 必须输出对应的文档作为审核交付物。无文档则审核无法闭环。

## Agent 派发触发条件

基于风险等级决定**派发哪些 subagent**。每次派发都有独立成本（上下文加载、任务执行、输出聚合），低风险任务不应强制走完整派发链。

**核心原则**：

- 产出物是派发链的自然产物——派发了哪个 agent 就有哪个 agent 的产出
- 不被派发的 agent 对应的产出物**自然省略**（不是"要不要写"，是"要不要派发"）
- 风险等级决定派发链长度，不是产出物数量

### 触发规则

| 风险 | 派发链 | 跳过的环节 | 典型产出物 | 协调者兼任 |
|------|-------|----------|----------|----------|
| 🟢 低 | kiro_default 协调者全程兼任 | 全部 subagent 派发 | `dev-log.md`（可选） | 全程 |
| 🟡 中 | developer (+ tester) | product 细化、qa 审计 | `dev-log.md` + `test-report.md` | product / architect / qa 工作由协调者人工对照 |
| 🔴 高 | product → architect → developer → tester → qa 全链路 | 无 | 全套 6-7 份（requirement / design / tasks / dev-log / test-report / review / audit） | 仅协调派发与衔接 |

### 触发条件细化

| 维度 | 🟢 低 | 🟡 中 | 🔴 高 |
|------|------|------|------|
| 改动文件数 | 单文件 | 跨文件，同模块 | ≥5 文件或跨模块 |
| 改动规模 | <50 行 | <300 行 | 不限 |
| 接口签名 | 不改 | 改但非破坏性 | 删除/破坏性变更 |
| 数据 schema | 不改 | 不改 | 改 |
| 架构约束 | 不触及 | 不触及 | 触及 |
| 安全 / 权限 | 不涉及 | 不涉及 | 涉及 |
| 示例 | 修 typo、加日志、规范微调、小重构、CI 配置小改 | 新增接口、修改业务逻辑、依赖升级、模块扩展、前端小模块改造 | 架构调整、接口删除、权限变更、数据迁移、跨模块重构 |

**等级判定规则**：

- 只要**任一维度**触发高风险条件 → 🔴
- 其余情况触发中风险 → 🟡
- 所有维度都在低风险范围 → 🟢
- 边界模糊时**就高不就低**，协调者保守判定

### 派发决策流程

```text
任务到达协调者
  ↓
协调者按"触发条件"判定风险等级（🟢/🟡/🔴）
  ├─ 🟢 → 协调者全程兼任，不派发 subagent
  │       产出 dev-log（如改动值得记录）→ 交付
  ├─ 🟡 → 协调者简写 AC → 派发 developer（+ tester）
  │       跳过 product 细化、qa 审计
  │       协调者验收 dev-log + test-report → 交付
  └─ 🔴 → 🔴 高风险设计必须人类审核后才能开发
          完整派发 product → architect → developer → tester → qa
          协调者仅负责衔接与进度跟踪 → 人类最终确认 → 交付
```

### 强制升级条件

任何任务执行过程中出现以下情况，**立即升级为 🔴**（即使初判为 🟢/🟡）：

- 改动文件数超过 5 个
- 发现接口签名需要变更
- 发现架构约束需要调整
- 发现涉及权限 / 安全 / 数据隐私
- 发现涉及跨模块影响
- 置信度跌破 0.7（见 [置信度门控](#置信度门控)）

升级后由协调者重新编排派发链，已执行的工作作为输入传递。

### 执行记录

协调者每次派发决策记录到 `docs/task/{版本}/{AAF-XXX}/dispatch-log.md`（如存在），内容：

- 判定风险等级 + 理由（触发了哪个条件维度）
- 派发链
- 跳过的环节
- 升级记录（如有）

**反思记录**：本规则修正了 2026-05-05 初版 AAF-024 #11 "产出物按风险分级"的误判。详见 [AAF-024 dev-log #2](../../task/v0.1.0/AAF-024/dev-log.md#2-过度工程化判断的反思记录)。

### 产出物契约（🔴 高风险派发链适用）

下游 agent 启动前，协调者校验上游产出物存在且完整。不满足则拒绝派发，回退到上游补齐。

| 上游 | 必须产出 | 下游 | 启动前校验项 |
|------|---------|------|------------|
| product | `requirement.md`（含 Gherkin AC） | architect | requirement.md 存在 + AC ≥ 1 条 |
| architect | `design.md`（接口签名 + 数据模型 + 模块交互）+ `tasks.md` | developer | design.md 存在 + 接口定义非空 + tasks.md 有 `#N` 编号 |
| designer | `ui-design.md`（页面结构 + 交互流程） | developer-webui / developer-uniapp | ui-design.md 存在（仅涉及前端时校验；纯后端跳过） |
| developer | 源码 + `dev-log.md` + `pnpm check:affected` 全绿 | architect(review) | dev-log.md 存在 + check 全绿日志 |
| architect | `review.md`（代码审查结论） | tester | review.md 存在 + 无未修复 blocker |
| developer | check 全绿（review 后修复轮次） | tester | check 全绿（tester 发现编译挂/单测红立即退回） |
| tester | `test-report.md`（含 AC 覆盖矩阵） | qa | test-report.md 存在 + 每条 AC 有对应结果 |
| architect | `review.md` | qa | review.md 存在 + blocker/major 计数明确 |

**校验失败处理**：

- 协调者不派发下游，直接回退上游补齐
- 回退时附带缺失项清单，上游只需补齐缺失部分
- 🟡 中风险派发链简化：仅校验 developer → tester 的 dev-log + check 全绿

### 模型分配策略

不同角色可配置不同 LLM，在 `.kiro/agents/<role>.json` 的 `"model"` 字段指定：

| 角色 | 推荐模型特征 | 理由 |
|------|------------|------|
| developer-* | 强推理、大上下文 | 需理解架构约束、生成完整代码 |
| architect | 强推理、**与 developer 不同** | 对抗性审查，避免盲点共振 |
| product | 中等推理 | 需求分析和文档输出为主 |
| tester | 强推理 | 需理解边界条件、生成测试用例 |
| qa | 轻量快速 | 流程检查、文档完整性校验 |
| designer | 中等推理 | 设计方案输出 |

**硬规则**：🔴 高风险变更中，architect(review) 必须配置与 developer 不同的 model。

**配置方式**：在 agent json 中添加 `"model": "<model-id>"`，未指定则使用系统默认。

## 异常处理

当出现置信度跌破阈值、沙箱告警、规范冲突时：

1. 立即暂停当前执行
2. 保存执行现场快照
3. 向人类说明原因 + 提供建议选项
4. 等待人类决策后继续或回滚

### 3.9 质量门控

**问题分级**：

| 级别 | 定义 | 示例 |
|------|------|------|
| **blocker** | 阻塞发布，必须修复 | 编译失败、运行时崩溃、安全漏洞、数据丢失、接口签名与设计不符 |
| **major** | 严重问题，应当修复 | 缺少异常处理、未覆盖关键路径测试、违反架构分层、性能隐患 |
| **minor** | 建议改进，可延后 | 命名不规范、缺少注释、代码风格不一致、可读性改进 |

**门控流程**：

| 维度             | 说明                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| **人类**         | 🔴 高风险需确认通过                                                       |
| **AI（协调者）** | 统计 blocker/major/minor 数量，判定通过或回退                            |
| **系统**         | CI 门控自动阻断（编译失败、测试不通过）                                  |
| **通过条件**     | blocker = 0 且 major ≤ 2                                                 |
| **不通过**       | 回退：需求→product，设计→architect，实现→developer，测试→tester，过程→qa |

## 接口契约

- 模块间通过 Java 接口交互，接口由提供方定义，使用方只依赖接口
- 改接口签名 → 协调者同步所有使用方
- 加新接口 → 定义方自行添加
- 改 common/ → 必须通过协调者评估影响

## 变更规则

| 变更类型     | 流程                          |
| ------------ | ----------------------------- |
| 需求变更     | 按需求管理规范走变更流程      |
| 规范变更     | 协调者评估后更新              |
| 架构变更     | architect 出方案 + 🔴 人类审核 |
| 接口签名变更 | 协调者同步所有使用方          |

## dev-log 记录规范

> dev-log.md 是 developer 的核心产出物之一，记录任务完成情况、关键决策、可复用知识。

### 格式

```markdown
## #N 任务标题

✅ 日期 — 负责人

- 明细（≤5 条，涵盖：完成内容、重要决策、关键变更）

> **问题**：现象 → 根因 → 解法（仅高复用价值时记录）

> **沉淀**：结论（仅高复用价值时记录）
```

### 写作原则

- 精炼：每条 ≤20 字为佳，可用简化文言缩短，只记结果不记过程
- ≤5 条明细涵盖：做了什么 + 选了什么（决策） + 改了什么（关键变更）
- 问题/沉淀非必填，仅可复用价值高时记录
- 决策类条目若已有 ADR，仅写结论 + 链接，不重复论证

### 示例

```markdown
## #17 Maven 多模块拆分

✅ 05-07 — developer-service

- 拆为 dependencies/common/framework/auto-dev/api 五模块
- 建完整包目录，含占位 package-info.java
- 五模块独立编译通过

## #30 框架基础能力脚手架

✅ 05-09 — developer-service

- common：Result<T> / 错误码 / BaseEntity / 分页
- framework：Security JWT 骨架 + ActorContext
- 决策：common 依赖用 provided scope，避免污染下游

> **沉淀**：provided scope 不传递——common 用 provided 引 Spring Web，下游不引 starter-web 则无此类
```

## 反馈方式

| 方式                             | 适用场景           | 响应速度 |
| -------------------------------- | ------------------ | -------- |
| 直接在对话中告知协调者           | 紧急事项、即时决策 | 最快     |
| 修改对应文档后告知协调者重新读取 | 需求/设计变更      | 中等     |
| 写入反馈文档                     | 非紧急改进建议     | 异步     |
