# Skill 规范

[Agent Skills 标准](https://agentskills.io/specification)

- .kiro/skills/ 是内置的默认协调者可见的技能
- team/skills/ 下是自定义智能体的技能需要指定

## Skill 目录结构

```text
skill-name/
├── SKILL.md          # 必需：元数据 + 指令
├── scripts/          # 可选：可执行代码
├── references/       # 可选：文档
├── assets/           # 可选：模板、资源
└── ...               # 任何其他文件或目录
```

### `SKILL.md` 格式

`SKILL.md` 文件必须包含 YAML 前置元数据，后跟 Markdown 内容。

### 前置元数据

| 字段            | 必需 | 约束                                                                 |
| --------------- | ---- | -------------------------------------------------------------------- |
| `name`          | 是   | 最多 64 个字符。仅限小写字母、数字和连字符。不能以连字符开头或结尾。 |
| `description`   | 是   | 最多 1024 个字符。非空。描述技能的功能和使用场景。                   |
| `license`       | 否   | 许可证名称或对捆绑许可证文件的引用。                                 |
| `compatibility` | 否   | 最多 500 个字符。指示环境要求（目标产品、系统包、网络访问等）。      |
| `metadata`      | 否   | 用于附加元数据的任意键值映射。                                       |
| `allowed-tools` | 否   | 技能可使用的预批准工具的空格分隔字符串。（实验性）                   |

**示例：**

```markdown SKILL.md
---
name: pdf-processing
description: 提取 PDF 文本、填写表单、合并文件。处理 PDF 时使用。
license: Apache-2.0
metadata:
  author: example-org
  version: "1.0"
---
```

#### `name` 字段

必需的 `name` 字段：

- 必须是 1-64 个字符
- 只能包含 Unicode 小写字母数字字符（`a-z`）和连字符（`-`）
- 不能以连字符（`-`）开头或结尾
- 不能包含连续连字符（`--`）
- 必须与父目录名称匹配

#### `description` 字段

必需的 `description` 字段：

- 必须是 1-1024 个字符
- 应该描述技能的功能和使用场景
- 应该包含帮助智能体识别相关任务的特定关键词

**好的示例：**

```yaml
description: 从 PDF 文件中提取文本和表格，填写 PDF 表单，合并多个 PDF。在处理 PDF 文档或用户提到 PDF、表单或文档提取时使用。
```

**不好的示例：**

```yaml
description: 帮助处理 PDF。
```

#### `compatibility` 字段

可选的 `compatibility` 字段：

- 如果提供，必须是 1-500 个字符
- 仅在技能有特定环境要求时包含
- 可以指示目标产品、所需系统包、网络访问需求等

**示例：**

```yaml
compatibility: 为 Claude Code（或类似产品）设计，需要 git、docker、jq 和互联网访问，需要 Python 3.14+ 和 uv
```

> 大多数技能不需要 `compatibility` 字段。

#### `metadata` 字段

可选的 `metadata` 字段：

- 从字符串键到字符串值的映射
- 客户端可以使用它来存储 Agent Skills 规范未定义的附加属性
- 建议使用相当独特的键名以避免意外冲突

**示例：**

```yaml
metadata:
  author: example-org
  version: "1.0"
```

#### `allowed-tools` 字段

```yaml
allowed-tools: Bash(git:*) Bash(jq:*) Read
```

### 正文内容

前置元数据后的 Markdown 正文包含技能指令。没有格式限制。编写任何有助于智能体有效执行任务的内容。

章节推荐：

- 分步指令
- 输入和输出示例
- 常见边缘情况

注意，智能体一旦决定激活技能就会加载整个文件。考虑将较长的 `SKILL.md` 内容拆分到引用文件中。

### 可选目录

### `scripts/`

包含智能体可以运行的可执行代码。脚本应该：

- 自包含或清楚地记录依赖项
- 包含有用的错误消息
- 优雅地处理边缘情况

支持的语言取决于智能体实现。常见选项包括 Python、Bash 和 JavaScript。

### `references/`

包含智能体在需要时可以阅读的附加文档：

- `REFERENCE.md` - 详细技术参考
- `FORMS.md` - 表单模板或结构化数据格式
- 特定领域文件（`finance.md`、`legal.md` 等）

保持单个引用文件的专注性。智能体按需加载这些文件，因此较小的文件意味着更少的上下文使用。

### `assets/`

包含静态资源：

- 模板（文档模板、配置模板）
- 图像（图表、示例）
- 数据文件（查找表、模式）

### 渐进式披露

智能体*渐进式*加载技能，仅在任务需要时才获取更多详细信息。技能应该结构化以利用这一点：

1. **元数据**（~100 个令牌）：所有技能的 `name` 和 `description` 字段在启动时加载
2. **指令**（建议 < 5000 个令牌）：激活技能时加载完整的 `SKILL.md` 正文
3. **资源**（按需）：文件（例如 `scripts/`、`references/` 或 `assets/` 中的文件）仅在需要时加载

将主要的 `SKILL.md` 保持在 500 行以下。将详细的参考材料移到单独的文件中。

### 文件引用

在技能中引用其他文件时，使用从技能根目录的相对路径：

```markdown SKILL.md
详情请参见[参考指南](references/REFERENCE.md)。

运行提取脚本：
scripts/extract.py
```

保持文件引用从 `SKILL.md` 一级深度，避免深度嵌套的引用链。

## 技能创建者最佳实践指南

如何编写范围界定合理且与任务难度相匹配的技能。

### 从真实的专业知识出发

技能创建中的一个常见陷阱是在未提供特定领域上下文的情况下就让 LLM 生成技能——仅仅依赖 LLM 的通用训练知识。结果往往是得到模糊、通用的流程，而不是让技能真正有价值的特定 API 模式、边缘情况和项目约定。

有效的技能扎根于真实的专业知识。关键在于将特定领域的上下文输入到创建过程中。

#### 从实际任务中提取

在与智能体的对话中完成一个真实的任务，在此过程中提供上下文、纠正和偏好，然后将可复用的模式提取为技能。重点关注：

- **行之有效的步骤** —— 导向成功的操作序列
- **你做出的纠正** —— 你引导智能体改变方向的地方（例如，“用库 X 代替 Y”，“检查边缘情况 Z”）
- **输入/输出格式** —— 进出数据的样子
- **你提供的上下文** —— 智能体原本不知道的项目特定事实、约定或约束

#### 从现有项目工件中综合

当你拥有现有的知识体系时，可以将其输入 LLM，让其综合出一个技能。由团队实际的问题报告和运行手册综合而来的数据管道技能，表现会优于由通用的“数据工程最佳实践”文章综合而成的技能，因为它捕捉到了*你们自己的*模式、故障模式和恢复流程。关键是使用项目特定的材料，而非通用参考。

良好的素材来源包括：

- 内部文档、运行手册和风格指南
- API 规范、架构和配置文件
- 代码审查评论和问题追踪器（捕捉反复出现的问题和审查者的期望）
- 版本控制历史，特别是补丁和修复（通过实际变更揭示模式）
- 现实世界的故障案例及其解决方案

### 通过真实执行进行优化

技能的初稿通常需要优化。针对真实任务运行技能，然后将结果——不仅仅是失败案例——反馈到创建过程中。询问：什么导致了误报？遗漏了什么？什么可以被删减？

即使是一次“执行-修订”的循环也能显著提升质量，而复杂的领域往往能从多次迭代中受益。

> **提示**
> 阅读智能体的执行轨迹，而不仅仅是最终输出。如果智能体在非生产性步骤上浪费时间，常见原因包括：指令过于模糊（智能体在找到可行方案前尝试了多种方法）、指令不适用于当前任务（智能体仍照做不误），或者提供的选项过多而没有明确的默认项。

### 明智地使用上下文

一旦技能被激活，其完整的 `SKILL.md` 正文将与对话历史、系统上下文和其他活动技能一起加载到智能体的上下文窗口中。你技能中的每一个 token 都在与该窗口中的所有其他内容争夺智能体的注意力。

#### 添加智能体缺乏的内容，省略它已知的内容

专注于如果没有你的技能，智能体*不会*知道的内容：项目特定的约定、特定领域的流程、不明显的边缘情况，以及要使用的具体工具或 API。你不需要解释 PDF 是什么、HTTP 如何工作等。

````markdown
<!-- 过于冗长 —— 智能体已经知道 PDF 是什么 -->
## 提取 PDF 文本

PDF（便携式文档格式）是一种常见的文件格式，包含文本、图像和其他内容。要从 PDF 中提取文本，你需要使用一个库。推荐使用 pdfplumber，因为它能很好地处理大多数情况。

<!-- 更好 —— 直奔主题，讲智能体靠自己不会知道的内容 -->
## 提取 PDF 文本

使用 pdfplumber 进行文本提取。对于扫描文档，回退到 pdf2image 配合 pytesseract。

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

针对每一条内容问自己：“如果没有这条指令，智能体会搞错吗？”如果答案是否定的，就删掉它。如果不确定，就测试一下。如果发现没有技能智能体也能很好地处理整个任务，那么这个技能可能没有增加价值。关于如何系统地测试这一点，请参阅/skill-creation/evaluating-skills。

#### 设计连贯的单元

决定一个技能应该覆盖什么，就像决定一个函数应该做什么一样：你希望它封装一个连贯的工作单元，并能与其他技能良好组合。范围过窄的技能会迫使单个任务加载多个技能，带来开销和指令冲突的风险。范围过宽的技能则难以精准激活。一个用于查询数据库并格式化结果的技能可能是一个连贯的单元，而一个还涵盖数据库管理的技能可能试图做得太多。

#### 追求适中的细节

过于全面的技能带来的坏处可能多于好处——智能体难以提取相关内容，并可能追求由不适用于当前任务的指令引发的非生产性路径。带有工作示例的简洁、分步指南往往优于详尽的文档。当你发现自己试图涵盖每一个边缘情况时，请考虑是否大部分可以由智能体自己的判断来处理。

#### 使用渐进式披露构建大型技能

建议将 `SKILL.md` 保持在 500 行和 5,000 token 以内——仅包含智能体每次运行所需的核心指令。当一个技能确实需要更多内容时，将详细的参考资料移动到 `references/` 或类似目录下的独立文件中。

关键是要告诉智能体*何时*加载每个文件。“如果 API 返回非 200 状态码，则读取 `references/api-errors.md`”比泛泛的“详见 references/”更有用。这让智能体按需加载上下文，而不是预先加载。

### 校准控制力

技能的每一部分都不需要相同程度的规范性。根据你指令的脆弱性来调整其具体程度。

#### 将具体性与脆弱性相匹配

**给予智能体自由**，当多种方法都有效且任务允许变化时。对于灵活的指令，解释*为什么*往往比僵化的指令更有效——理解指令背后目的的智能体能做出更好的情境相关决策。代码审查技能可以描述要寻找什么，而无需规定确切的步骤：

```markdown
## 代码审查流程

1. 检查所有数据库查询是否存在 SQL 注入风险（使用参数化查询）
2. 验证每个端点的身份验证检查
3. 寻找并发代码路径中的竞态条件
4. 确认错误消息不会泄露内部细节
```

**保持规范性**，当操作很脆弱、一致性很重要或必须遵循特定顺序时：

````markdown
## 数据库迁移

严格按照此顺序运行：

```bash
python scripts/migrate.py --verify --backup
```

请勿修改命令或添加额外标志。
````

大多数技能都是混合体。请独立校准每个部分。

#### 提供默认值，而非菜单

当有多种工具或方法可行时，选择一个默认值并简要提及替代方案，而不是将它们作为平等选项列出。

````markdown
<!-- 选项太多 -->
你可以使用 pypdf, pdfplumber, PyMuPDF, 或 pdf2image...

<!-- 清晰的默认值带逃生舱 -->
使用 pdfplumber 进行文本提取：

```python
import pdfplumber
```

对于需要 OCR 的扫描版 PDF，改用 pdf2image 配合 pytesseract。
````

#### 倾向于流程而非声明

技能应该教导智能体*如何处理*一类问题，而不是为特定实例*生产什么*。对比一下：

```markdown
<!-- 特定答案 —— 仅对此确切任务有用 -->
将 `orders` 表通过 `customer_id` 连接到 `customers`，过滤
`region = 'EMEA'` 的行，并对 `amount` 列求和。

<!-- 可复用的方法 —— 适用于任何分析查询 -->
1. 从 `references/schema.yaml` 读取架构以查找相关表
2. 使用 `_id` 外键约定连接表
3. 将用户请求中的任何过滤器应用为 WHERE 子句
4. 根据需要聚合数值列并格式化为 markdown 表格
```

这并不意味着技能不能包含特定细节——输出格式模板（见#templates-for-output-format）、像“从不输出 PII”这样的约束，以及特定于工具的指令都是有价值的。关键在于*方法*应该具有通用性，即使个别细节是具体的。

### 有效指令的模式

这些是构建技能内容的可复用技术。并非每个技能都需要全部这些模式——使用适合你任务的部分。

#### Gotchas（坑点）章节

许多技能中价值最高的内容是一份 gotchas（坑点）列表——即违背合理假设的环境特定事实。这些不是一般性建议（如“适当处理错误”），而是对智能体如果不被告知就会犯的错误的具体纠正：

````markdown
## Gotchas（坑点）

- `users` 表使用软删除。查询必须包含
  `WHERE deleted_at IS NULL`，否则结果将包含已停用的账户。
- 用户 ID 在数据库中为 `user_id`，在认证服务中为 `uid`，
  在计费 API 中为 `accountId`。这三者指代同一个值。
- `/health` 端点只要 Web 服务器在运行就会返回 200，
  即使数据库连接已断开。使用 `/ready` 检查完整的
  服务健康状况。
````

将 gotchas 保留在 `SKILL.md` 中，以便智能体在遇到这种情况之前就能读到。如果你告诉智能体何时加载，单独的参考文件也可以使用，但对于不明显的错误，智能体可能无法识别触发条件。

> **提示**
> 当智能体犯了你必须纠正的错误时，请将纠正措施添加到 gotchas 部分。这是迭代改进技能的最直接方法之一（见#refine-with-real-execution）。

#### 输出格式模板

当你需要智能体以特定格式生成输出时，请提供一个模板。这比用散文描述格式更可靠，因为智能体擅长对具体结构进行模式匹配。短模板可以内联在 `SKILL.md` 中；对于较长的模板，或仅在特定情况下需要的模板，请将它们存储在 `assets/` 中并从 `SKILL.md` 引用，以便仅在需要时加载。

````markdown
## 报告结构

使用此模板，根据具体分析调整各部分内容：

```markdown
# [分析标题]

## 执行摘要
[关键发现的单段概述]

## 主要发现
- 发现 1 及支持数据
- 发现 2 及支持数据

## 建议
1. 具体的可操作建议
2. 具体的可操作建议
```
````

#### 多步骤工作流的检查清单

明确的检查清单有助于智能体跟踪进度并避免跳过步骤，特别是当步骤存在依赖关系或验证关卡时。

```markdown
## 表单处理工作流

进度：
- [ ] 步骤 1：分析表单（运行 `scripts/analyze_form.py`）
- [ ] 步骤 2：创建字段映射（编辑 `fields.json`）
- [ ] 步骤 3：验证映射（运行 `scripts/validate_fields.py`）
- [ ] 步骤 4：填写表单（运行 `scripts/fill_form.py`）
- [ ] 步骤 5：验证输出（运行 `scripts/verify_output.py`）
```

#### 验证循环

指示智能体在继续之前自行验证其工作。模式是：执行工作，运行验证器（脚本、参考检查清单或自检），修复任何问题，并重复直到验证通过。

```markdown
## 编辑工作流

1. 进行编辑
2. 运行验证：`python scripts/validate.py output/`
3. 如果验证失败：
   - 查看错误信息
   - 修复问题
   - 再次运行验证
4. 仅当验证通过时才继续
```

参考文档也可以充当“验证器”——指示智能体在定稿前对照参考检查其工作。

#### 计划-验证-执行

对于批量或破坏性操作，让智能体以结构化格式创建中间计划，对照真相源进行验证，然后再执行。

```markdown
## PDF 表单填写

1. 提取表单字段：`python scripts/analyze_form.py input.pdf` → `form_fields.json`
   （列出每个字段名称、类型以及是否为必填项）
2. 创建 `field_values.json`，将每个字段名称映射到其预期值
3. 验证：`python scripts/validate_fields.py form_fields.json field_values.json`
   （检查每个字段名是否存在于表单中，类型是否兼容，以及
   必填字段是否缺失）
4. 如果验证失败，修改 `field_values.json` 并重新验证
5. 填写表单：`python scripts/fill_form.py input.pdf field_values.json output.pdf`
```

关键的成分是第 3 步：一个对照真相源（`form_fields.json`）检查计划（`field_values.json`）的验证脚本。像“字段 'signature_date' 未找到 —— 可用字段：customer_name, order_total, signature_date_signed”这样的错误为智能体提供了足够的信息进行自我纠正。

#### 捆绑可复用脚本

当/skill-creation/evaluating-skills时，比较跨测试用例的智能体执行轨迹。如果你注意到智能体每次运行都独立重构相同的逻辑——构建图表、解析特定格式、验证输出——这是一个信号，表明你应该编写一次经过测试的脚本并将其捆绑在 `scripts/` 中。

关于设计和捆绑脚本的更多信息，请参阅/skill-creation/using-scripts。

## 优化技能描述指南

如何改进技能的 `description`（描述）字段，使其在相关提示词下能够可靠触发。

技能只有在被激活时才有用。你的 `SKILL.md` 文件前置元数据（frontmatter）中的 `description` 字段，是智能体（Agent）决定是否针对给定任务加载某个技能的主要机制。描述过于简略会导致技能该触发时未触发；描述过于宽泛则会导致不该触发时误触发。

本指南将介绍如何系统性地测试和改进技能描述，以提高触发的准确率。

### 技能触发机制

在启动时，仅加载 `name`（名称）和 `description`（描述）——当用户任务与描述匹配时，智能体会将完整的 `SKILL.md` 读入上下文并遵循其指令。

这意味着描述承担了触发的所有重任。如果描述未能传达技能的适用场景，智能体就不会知道要去调用它。

一个重要的细微差别在于：智能体通常只在任务需要超出其自身处理能力范围的知识或工具时，才会咨询技能。涉及专业知识（如不熟悉的 API、特定领域的工作流或不常见的格式）的任务，才是好的描述能够发挥关键作用的地方。

### 编写有效的描述

在测试之前，了解什么是好的描述很有帮助。这里有几个原则：

- **使用祈使语气。** 将描述构建为给智能体的指令：“当……时使用此技能”（Use this skill when...），而不是“此技能用于……”（This skill does...）。智能体正在决定是否采取行动，所以要明确告诉它何时行动。
- **关注用户意图，而非实现细节。** 描述用户试图达成的目标，而不是技能的内部工作机制。智能体是根据用户的提问进行匹配的。
- **倾向于“强势引导”。** 明确列出技能适用的上下文，包括用户没有直接提及该领域的场景：“即使用户没有明确提到‘CSV’或‘分析’。”
- **保持简洁。** 通常几句话到一段简短的文字即可——长到足以涵盖技能的范围，短到不会因为多个技能的描述而让智能体的上下文负担过重。 1024 个字符的硬性限制。

### 设计触发评估查询（Trigger Eval Queries）

要测试触发效果，你需要一组评估提示词——即一系列标记了是否应该触发技能的真实用户提示词。目标大约是 20 条查询：8-10 条应该触发的，8-10 条不应该触发的。

```json eval_queries.json
[
  { "query": "我有一个 ~/data/q4_results.xlsx 的电子表格，C列是收入，D列是支出——你能帮我加一列利润率并把低于10%的标出来吗？", "should_trigger": true },
  { "query": "把json文件转成yaml最快的方法是什么", "should_trigger": false }
]
```

#### 应触发查询（Should-trigger queries）

这些查询用于测试描述是否涵盖了技能的范围。请在以下几个维度上进行变化：

- **措辞（Phrasing）：** 有些正式，有些随意，有些包含拼写错误或缩写。
- **显性（Explicitness）：** 有些直接点名技能领域（“分析这个 CSV”），有些则在不提名称的情况下描述需求（“老板想让我根据这个数据文件做个图表”）。
- **细节（Detail）：** 混合简短提示词和富含上下文的长提示词——从简短的“分析我的销售 CSV 并做图表”到包含文件路径、列名和背景故事的长消息。
- **复杂度（Complexity）：** 改变步骤数和决策点。将单步任务与多步工作流结合起来，测试当任务被埋在较长的链条中时，智能体是否能辨别出相关性。

最有价值的应触发查询是那些技能会有帮助但仅凭查询本身联系并不明显的场景。这些情况下，描述的措辞至关重要——如果查询已经明确要求了技能的功能，任何合理的描述都会触发。

#### 不应触发查询（Should-not-trigger queries）

最有价值的负面测试用例是**擦边球（near-misses）**——与你的技能共享关键词或概念，但实际上需要完全不同处理的查询。这些测试检验的是描述的精确性，而不仅仅是广度。

对于一个 CSV 分析技能，较弱的负面例子是：

- `"写一个斐波那契函数"` —— 明显无关，测不出东西。
- `"今天天气怎么样？"` —— 无关键词重叠，太简单。

强有力的负面例子：

- `"我需要更新Excel预算电子表格里的公式"` —— 共享了“电子表格”和“数据”概念，但需要的是Excel编辑，而非CSV分析。
- `"你能写个python脚本读取csv并把每一行上传到postgres数据库吗"` —— 涉及CSV，但任务是数据库ETL，不是分析。

#### 真实性技巧

真实的用户提示词包含通用测试查询所缺乏的上下文。请包含：

- 文件路径（`~/Downloads/report_final_v2.xlsx`）
- 个人上下文（`"经理让我..."`）
- 具体细节（列名、公司名、数据值）
- 口语化表达、缩写和偶尔的拼写错误

### 测试描述是否触发

基本方法：通过你的智能体运行每条查询，并观察智能体是否调用了该技能。确保技能已注册并且能被你的智能体发现——具体方式因客户端而异（例如技能目录、配置文件或CLI标志）。

大多数智能体客户端都提供某种形式的可见性——执行日志、工具调用历史或详细输出——让你看到运行过程中咨询了哪些技能。请查阅客户端的文档以获取详情。如果智能体加载了你技能的 `SKILL.md`，则说明技能已触发；如果智能体在未咨询它的情况下继续处理，则说明未触发。

一个查询“通过”测试的条件是：

- `should_trigger` 为 `true` 且技能被调用，或
- `should_trigger` 为 `false` 且技能未被调用。

#### 多次运行

模型行为具有非确定性——同一查询可能在一次运行中触发技能，但在下一次没有。每条查询运行多次（3次是一个合理的起点）并计算**触发率（trigger rate）**：技能被调用的运行次数占比。

应触发查询如果触发率高于阈值（默认 0.5 比较合理）则通过。不应触发查询如果触发率低于该阈值则通过。

对于 20 条查询，每条运行 3 次，总共是 60 次调用。你需要为此编写一个脚本。以下是通用结构——请将 `claude` 调用和 `check_triggered` 中的检测逻辑替换为你使用的智能体客户端所提供的功能：

```bash
#!/bin/bash
QUERIES_FILE="${1:?用法: $0 <queries.json>}"
SKILL_NAME="my-skill"
RUNS=3

# 此示例使用 Claude Code 的 JSON 输出来检查 Skill 工具调用。
# 将此函数替换为你的智能体客户端的检测逻辑。
# 如果技能被调用，应返回 0（成功），否则返回 1。
check_triggered() {
  local query="$1"
  claude -p "$query" --output-format json 2>/dev/null \
    | jq -e --arg skill "$SKILL_NAME" \
      'any(.messages[].content[]; .type == "tool_use" and .name == "Skill" and .input.skill == $skill)' \
      > /dev/null 2>&1
}

count=$(jq length "$QUERIES_FILE")
for i in $(seq 0 $((count - 1))); do
  query=$(jq -r ".[$i].query" "$QUERIES_FILE")
  should_trigger=$(jq -r ".[$i].should_trigger" "$QUERIES_FILE")
  triggers=0

  for run in $(seq 1 $RUNS); do
    check_triggered "$query" && triggers=$((triggers + 1))
  done

  jq -n \
    --arg query "$query" \
    --argjson should_trigger "$should_trigger" \
    --argjson triggers "$triggers" \
    --argjson runs "$RUNS" \
    '{query: $query, should_trigger: $should_trigger, triggers: $triggers, runs: $runs, trigger_rate: ($triggers / $runs)}'
done | jq -s '.'
```

> **提示**：如果你的智能体客户端支持，一旦结果明确——即智能体要么已经咨询了技能，要么已经开始在没有它的情况下工作——你可以提前停止运行。这可以显著减少运行全套评估集的时间和成本。

## 使用训练/验证拆分避免过拟合

如果你针对所有查询优化描述，可能会面临过拟合的风险——即炮制出一个仅适用于这些特定措辞但在新查询上失效的描述。

解决方案是将查询集拆分：

- **训练集（Train set，约 60%）：** 用于识别失败案例并指导改进的查询。
- **验证集（Validation set，约 40%）：** 你预留出来的查询，仅用于检查改进是否具有泛化能力。

确保两组都包含成比例的应触发和不应触发查询——不要不小心把所有正面案例都放进一个集合里。随机打乱并保持每次迭代的拆分固定，以便进行同类比较。

如果你使用上述脚本，可以将查询拆分为两个文件——`train_queries.json` 和 `validation_queries.json`——并分别针对这两个文件运行脚本。

### 优化循环

1. **评估（Evaluate）：** 在*训练集和验证集*上评估当前描述。训练结果指导你的更改；验证结果告诉你这些更改是否正在泛化。
2. **识别失败（Identify failures）：** 在*训练集*中找出：哪些应触发查询没有触发？哪些不应触发查询却触发了？
    - 仅使用训练集的失败案例来指导更改——无论你是自己修改描述还是提示 LLM，都要让验证集的结果脱离改进过程。
3. **修改描述（Revise the description）：** 专注于泛化：
    - 如果应触发查询失败了，说明描述可能太窄。扩大范围或添加关于技能何时有用的上下文。
    - 如果不应触发查询发生了误触发，说明描述可能太宽。增加关于技能*不*做什么的具体说明，或澄清此技能与相邻能力的边界。
    - 避免添加来自失败查询的特定关键词——那是过拟合。相反，找到这些查询代表的通用类别或概念并加以解决。
    - 如果你在几次迭代后仍然卡住，尝试结构上完全不同的描述方法，而不是渐进式调整。不同的框架或句式结构可能会突破瓶颈。
    - 检查描述是否保持在 1024 个字符的限制内——描述往往在优化过程中变长。
4. **重复（Repeat）：** 重复步骤 1-3，直到所有*训练集*查询通过或你不再看到有意义的改进。
5. **选择最佳迭代（Select the best iteration）：** 通过其验证通过率——即*验证集*中通过的查询比例——来选择最佳描述。注意，最好的描述可能不是你生成的最后一个；早期迭代的验证通过率可能高于后来过拟合训练集的版本。

五次迭代通常就足够了。如果性能没有改善，问题可能出在查询本身（太简单、太难或标签错误），而不是描述上。

> **提示**
> <https://github.com/anthropics/skills/tree/main/skills/skill-creator> 技能自动化了这一全流程：它拆分评估集，并行评估触发率，使用 Claude 提出描述改进建议，并生成一个实时的 HTML 报告供你在运行时查看。

### 应用结果

一旦选定了最佳描述：

1. 更新 `SKILL.md` 前置元数据中的 `description` 字段。
2. 验证描述是否在 /specification#description-field内。
3. 验证描述是否按预期触发。尝试几个提示词手动测试作为快速健全性检查。对于更严格的测试，编写 5-10 个全新的查询（混合应触发和不应触发）并通过评估脚本运行它们——由于这些查询从未参与优化过程，它们能诚实地检验描述是否泛化。

**优化前后对比：**

```yaml
# 优化前
description: Process CSV files.

# 优化后
description: >
  Analyze CSV and tabular data files — compute summary statistics,
  add derived columns, generate charts, and clean messy data. Use this
  skill when the user has a CSV, TSV, or Excel file and wants to
  explore, transform, or visualize the data, even if they don't
  explicitly mention "CSV" or "analysis."
```

改进后的描述更具体地说明了技能的功能（汇总统计、派生列、图表、清洗），并更广泛地说明了何时适用（CSV、TSV、Excel；即使没有明确的关键词）。
