## 铁律

**无调查不修复。** 修症状制造打地鼠式调试。每个不针对根因的修复都让下一个 bug 更难找。

## Phase 1: 收集证据

在形成任何假设前先收集上下文。

1. **收集症状**：错误信息、堆栈、复现步骤。信息不足时一次只问一个问题。
2. **读代码**：从症状追溯代码路径到潜在原因。用搜索找所有引用，读懂逻辑。
3. **查最近变更**：
   ```bash
   git log --oneline -20 -- <affected-files>
   ```
   之前能用吗？什么改了？回归意味着根因在 diff 里。
4. **复现**：能确定性触发 bug 吗？不能则继续收集证据。

产出：**"根因假设：..."** —— 一个具体的、可测试的关于什么错了以及为什么的断言。

## Phase 2: 模式匹配

检查是否匹配已知模式：

| 模式 | 特征 | 排查方向 |
|------|------|----------|
| 竞态条件 | 间歇性、时序相关 | 共享状态的并发访问 |
| 空值传播 | NPE、TypeError | 可选值缺少守卫 |
| 状态腐败 | 数据不一致、部分更新 | 事务、回调、钩子 |
| 集成失败 | 超时、意外响应 | 外部 API、服务边界 |
| 配置漂移 | 本地正常、staging 挂 | 环境变量、feature flag、DB 状态 |
| 缓存过期 | 显示旧数据 | Redis、CDN、浏览器缓存 |

同时检查：
- git log 中同一区域的历史修复——**同一文件反复出 bug 是架构味道**，不是巧合

## Phase 3: 假设验证

写任何修复前先验证假设。

1. **确认假设**：在疑似根因处加临时日志/断言/调试输出。跑复现。证据匹配吗？
2. **假设错误**：回到 Phase 1 收集更多证据。不要猜。
3. **三振出局**：3 个假设都失败 → **停下**。向协调者/用户报告：
   ```
   3 个假设已测试，均不匹配。可能是架构问题而非简单 bug。
   A) 继续调查——新假设：[描述]
   B) 升级人工审查
   C) 加日志观察——埋点后等下次触发
   ```

**红旗**——看到这些就慢下来：
- "先临时修一下" → 没有"临时"。修对或升级。
- 没追踪数据流就提修复方案 → 在猜。
- 每次修复暴露新问题 → 错误的层，不是错误的代码。

## Phase 4: 实施修复

根因确认后：

1. **修根因，不修症状。** 消除实际问题的最小改动。
2. **最小 diff**：最少文件、最少行数。抵制顺手重构的冲动。
3. **写回归测试**：
   - 没有修复时**失败**（证明测试有意义）
   - 有修复后**通过**（证明修复有效）
4. **跑完整测试套件**：`pnpm check:affected`。无回归。

## 升级条件

以下情况必须停下升级：
- 连续 3 次尝试未成功
- 涉及安全敏感变更且不确定
- 工作范围超出可验证范围

升级格式：
```
状态：BLOCKED | NEEDS_CONTEXT
原因：[1-2 句]
已尝试：[做了什么]
建议：[用户下一步该做什么]
```

## Gotchas

- AAF 后端用 Spring Boot + WebFlux，异步链路中的异常容易被吞掉——检查 `.onErrorResume` 和 `.doOnError`
- Flyway 迁移失败后数据库可能处于半迁移状态——先检查 `flyway_schema_history` 表
- Nx monorepo 中 `affected` 计算依赖 git base，确认 base 分支正确
