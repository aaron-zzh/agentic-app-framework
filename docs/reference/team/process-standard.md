# 迭代过程规范

> 融合敏捷开发 + CMMI5 过程域 + 人机协作的迭代过程。迭代周期 2-4 周。


四阶段：计划 → 迭代开发 → 测试 → 交付。迭代周期 2-4 周。

| 阶段 | 关键产出 | 负责人 |
|------|---------|--------|
| 计划 | 可行性报告、立项报告、业务需求、项目计划、风险分析 | 项目经理/产品经理 |
| 迭代开发 | PRD/用户故事、系统设计、数据库设计、源码、需求跟踪 | 产品经理/架构师/开发 |
| 测试 | 测试方案、测试报告、用户手册 | 测试工程师 |
| 交付 | 用户培训、系统上线、验收报告、项目总结、运维方案 | 项目经理/测试 |


## 迭代全景

```text
准备 → 启动 → 执行 → 发布 → 总结
                ↑        |
                └── 回退 ←┘（质量门控不通过）
```

## 五阶段详述

### 1. 准备

**目标**：明确迭代范围，确保可行性。

| 活动 | 负责人 | 产出 |
|------|--------|------|
| 需求调研与可行性分析 | 产品经理 + product | 业务需求列表 |
| 细化排序用户故事 | 产品经理 + product | 优先级排序的用户故事 |
| 技术方案与风险评估 | 架构师 + architect | 技术方案、风险清单 |
| 选取迭代范围 | 协调者 | 迭代需求列表（从 backlog 选取） |

### 2. 启动

**目标**：对齐目标，分解任务，明确验收标准。

| 活动 | 负责人 | 产出 |
|------|--------|------|
| 启动会议（对齐目标和范围） | 协调者 + 人类 | 会议记录 |
| 任务拆分与工作量评估 | 协调者 | 任务列表（关联 backlog） |
| 确认验收标准 | 产品经理 + 人类 | 每个故事的 AC |
| 识别依赖与风险 | 架构师 | 依赖关系图、风险应对 |

### 3. 执行

**目标**：按任务流水线推进，人机并行协作。

每个任务按以下流水线执行：

```text
product(requirement.md)
  → architect(design.md) → [🔴 高风险需人类审核]
    → developer(代码 + 单元测试)  ← 验证（Verification）
      → architect(代码审查)
        → tester(验收测试)         ← 确认（Validation）
          → qa(过程审计)
            → 质量门控
```

| 活动 | 负责人 | 产出 | 说明 |
|------|--------|------|------|
| 需求细化 | product | requirement.md | AI 结构化，人类审核 |
| 系统设计 | architect | design.md | 🔴 高风险必须人类审核后再开发 |
| 编码实现 | developer-* | 源码 | AI 按端并行，人类处理复杂逻辑 |
| 验证（单元测试/自测） | developer-* | 测试代码、自测报告 | 开发自己验证 |
| 代码审查 | architect | 审查意见 | 技术层面同行评审 |
| 确认（验收测试） | tester | test-report.md | 独立于开发，对照 AC 逐条验证 |
| 过程审计 | qa | 审计记录 | 检查流程合规、规范遵守 |
| 质量门控 | 协调者 | 通过/回退 | blocker=0 且 major≤2 |

**回退规则**：质量门控不通过时，按问题类型回退——需求问题→product，设计缺陷→architect，实现问题→developer，测试不足→tester，过程违规→qa。

**人机协作要点**：

- AI 完成即提交，不等待人类审批
- 人类按风险等级按需审查（🟢跳过 / 🟡抽查 / 🔴必审）
- AI 发现需人类决策的事项标注 `🔴 需人类决策`，继续推进其他任务
- 批量修改文件（≥5 个）前需向人类申请

### 4. 发布

**目标**：部署验证，收集反馈。

| 活动 | 负责人 | 产出 |
|------|--------|------|
| 测试环境部署 | 协调者 + developer | 部署记录 |
| 客户演示/用户验收 | 产品经理 + 人类 | 反馈记录 |
| 编写发布说明 | 协调者 | Release Note |
| 数据库迁移（如有） | developer-api | 迁移脚本 |

### 5. 总结

**目标**：回顾改进，沉淀知识。

| 活动 | 负责人 | 产出 |
|------|--------|------|
| 迭代回顾（做得好/待改进/行动项） | 协调者 + 全员 | 回顾记录 |
| 度量分析（需求完成率、缺陷密度、周期时间） | qa + 协调者 | 度量报告 |
| 过程改进（更新规范/流程） | 协调者 | 规范变更记录 |
| 知识沉淀（设计决策、踩坑记录） | 全员 | 知识库更新 |
| backlog 归档与整理 | 协调者 | 归档到 `docs/task/archive/` |

## 文档产出规则

- 所有任务文档产出到 `docs/task/{版本}/{任务名}/`
- 模板在 `docs/task/_template/` 下
- 文档流：requirement.md → design.md → dev-log.md → test-report.md → qa-report.md

## 版本交付检查清单

发布前协调者逐项确认：

- [ ] 所有 P0/P1 任务已完成
- [ ] 质量门控通过（blocker=0，major≤2）
- [ ] 编译通过，测试全部通过
- [ ] 接口变更有破坏性变更说明
- [ ] 数据库迁移脚本就绪（如有）
- [ ] 文档已更新
- [ ] 发布说明已编写
- [ ] backlog 已归档
