# 迭代过程规范

> 本文档定义开发过程的**流程和原则**。各环节人+AI+系统如何协作见 [协作规范](collaboration-standard.md)。

## 核心原则

- **一句话开发**：人类给出目标 → AI 全流程执行 → 系统自动化保障 → 人类异步审核
- **规范驱动**：先写规范再写代码，规范是人类和 AI 的共同真理来源
- **质量内建**：验证与确认分离，系统自动化门控，问题按类型回退修复

### 规范驱动

> 先写规范，再写代码。规范是人类和 AI 的共同真理来源。

**规范不是描述性文档，而是可验证的技术合同**——明确规定系统应该做什么、不应该做什么，以及如何验证。代码是规范的实现结果，当代码与规范不一致时，以规范为准并修正代码。

**规范的特征要求**：

| 特征 | 说明 |
|------|------|
| 明确性 | 对系统行为、约束、边界条件有明确描述，避免歧义 |
| 结构化 | 可被工具或 AI 稳定解析（Markdown / DSL / Schema） |
| 可验证 | 能映射到测试、校验规则或自动化验证 |
| 可演进 | 支持版本化、Diff、回滚，随系统一起成长 |
| 面向实现 | 能直接指导代码生成或人工实现 |

**AAF 采用 Spec-Anchored（规范锚定）模式**：规范长期保留，与代码持续同步维护。人和 AI 都可以修改代码，但必须与规范保持对齐。

**规范流转与验证闭环**：

```text
需求规格 → 设计规格 → 代码实现 → 测试验证 → 过程审计
   ↓          ↓          ↓          ↓          ↓
 product   architect   developer   tester      qa
   ↑          ↑          ↑          ↑          ↑
   └──────────┴──────────┴──────────┴──────────┘
              发现偏离 → 向上游反馈修正
```

**一致性规则**：
- 下游发现与上游规范矛盾时，必须向上游反馈修正，不得自行偏离
- 发现源码与规范不一致时，必须提出并记录，由协调者评估是修正代码还是更新规范
- 规范变更时，同步触发下游重新验证（规范→代码→测试的联动）

**三方角色**：

| 角色 | 在规范驱动中的作用 |
|------|-------------------|
| 人类 | 定义业务规范和验收标准，审核高风险规范变更，判断规范演进方向 |
| AI | 生成和维护规范文档，检查规范一致性，发现偏离时主动提出，辅助规范演进 |
| 系统 | 存储规范版本（Git），自动检查规范合规（lint、静态分析、合约测试），阻断不合规提交，规范变更时触发下游验证 |

> 详见 规范驱动开发

## 迭代全景

```text
准备 → 启动 → 执行 → 发布 → 总结
                ↑        |
                └── 回退 ←┘（质量门控不通过）
```

周期 2-4 周。融合敏捷开发 + CMMI5 过程域 + 人机协作。

## 阶段切换规则

### 推进模式

| 模式 | 说明 | 触发方 |
|------|------|--------|
| **交互模式** | 人类与 AI 实时对话协作 | 每个阶段完成后等待人类指令，不自动推进 |
| **批量模式** | 人类授权 AI 自动执行多步骤 | 协调者按流程自动推进，关键节点异步通知 |

默认为**交互模式**。人类明确说"自动执行"或"批量完成"时切换为批量模式。

**全局规则**：所有阶段和步骤均异步推进，不阻塞等待。人类可随时介入审核任意环节，发现问题直接反馈，协调者回退对应步骤处理。

### 各阶段入口条件与负责人

| 阶段 | 入口条件 | 推进负责人 |
|------|---------|-----------|
| 准备 | 人类提出版本目标 | 人类触发，product 执行 |
| 执行 | Epic 已通过审核并录入 backlog | 协调者自动派发，阶段内自动流转 |
| 发布 | 质量门控通过，人类确认发布 | 🔴 人类触发 |
| 总结 | 发布完成 | 协调者执行，人类参与回顾 |

## 1. 准备

**目标**：明确迭代范围，确保可行性。

### 步骤顺序

```text
版本规划（product，人类触发）
  → 需求调研（product）
    → 用户故事拆分（product 根据业务需求分析调研，划分一级用户故事并输出需求文档）
      → architect 评估是否需要迭代级架构设计文档
        → 需要（首个迭代/新模块/重大技术选型）→ architect 输出迭代级设计文档
        → 不需要（纯功能扩展）→ 跳过
      → 协调者审核（格式完整性 + 规范一致性，输出审核意见到需求文档）
        → 不通过 → product 调整 → 重新审核
        → 通过 → 录入 backlog（分配 AAF 编号）
          → 选取迭代范围（协调者建议）→ 进入执行阶段
```

### 1.1 版本规划

- 确定版本目标和交付范围
- 评估资源和时间约束
- product 对照 [产品概述](../../explanation/product-overview.md) 确认版本方向，更新 [路线图](../../prd/roadmap.md) 里程碑
- 输出版本计划

### 1.2 需求调研

- 收集业务需求和用户反馈
- 分析可行性和投入产出比
- 输出业务需求列表

需求来源：
- [需求收集](../../prd/requirements.md) — 未评估的业务需求和点子
- [用户反馈](../../prd/user-feedback.md) — 产品使用体验反馈
- [改进意见](../../prd/improvements.md) — 内部流程/规范/技术改进

> 适用规范：[需求管理规范](../dev/requirement-standard.md)

### 1.3 用户故事拆分

product 输出文档 → 协调者审核 → 通过后录入 backlog：

1. product 将业务需求拆分为一级用户故事
2. product 为每个用户故事创建需求文件（`docs/prd/{module}/{feature}.md`），标注优先级（P0/P1/P2），定义初步验收标准
3. 协调者审核用户故事：检查格式完整性、验收标准可测性、与架构约束一致性，将审核意见写入需求文件底部的「审核记录」区块；根据风险等级决定是否需要人类参与：
   - 🟢 低风险（范围清晰、无架构影响）：协调者自审通过即可录入 backlog
   - 🟡 中风险（涉及新模块、接口变更）：建议人类抽查
   - 🔴 高风险（架构调整、权限变更、跨模块影响）：必须人类审核后才能录入 backlog
4. 不通过：product 根据意见调整，重新提交审核
5. 通过：协调者将用户故事录入 backlog（分配 AAF 编号），并更新迭代文件中对应业务需求的需求链接

审核记录格式：

```markdown
## 审核记录

| 日期 | 审核人 | 结论 | 意见 |
|------|--------|------|------|
| MM-DD | 协调者 | ✅ 通过 / ❌ 不通过 | 具体意见 |
```

### 1.4 技术预研

- 评估技术方案可行性
- 识别技术风险和依赖
- 输出技术方案和风险清单

### 1.5 选取迭代范围

- 根据优先级和容量从 backlog 选取用户故事（建议 3-7 个/迭代）
- 确认迭代目标
- 协调者更新迭代文件中的业务需求（迭代文件在版本规划阶段已创建，此时补充选取结果）

> 适用规范：[任务管理规范 — 迭代文件格式](../../task/Readme.md#迭代文件格式)

## 2. 执行

**目标**：按任务流水线交付。

### 任务流水线

```text
product(Epic→Story 拆分 + Spec 细化)
  + architect(技术设计 + 任务拆分)
    → designer(UI/交互设计)           ← 涉及前端时
      → developer(编码 + 单元测试)    ← 验证
        → architect(代码审查)
          → tester(验收测试)          ← 确认
            → qa(过程审计)
              → 质量门控
```

### 2.1 需求细化与技术设计

每个 Epic 进入执行前，product 先将其拆分为 Story，再由 product + architect 协作完成 Spec 和设计文档：

- product 将 Epic 拆分为可独立交付的 Story，每个 Story 有完成条件概述
- product 为每个 Story 补充 Spec：数据模型、业务规则、约束与边界、精确 AC（Gherkin）、测试要点
- product 编写**产品设计文档**（功能流程复杂或多步骤交互时）：用户旅程、功能流程、交互逻辑，存放在 `docs/design/{module}/`
- architect 完成**技术设计文档**：接口定义（完整签名）、类结构、模块交互、ADR，存放在 `docs/design/{module}/`
- architect 将 Story 拆分为技术任务（`#XXXNN`），标注依赖，记录在迭代文件中
- 🔴 高风险设计必须人类审核后再进入开发

**设计文档触发条件**：

| 类型 | 负责人 | 触发条件 |
|------|--------|---------|
| 系统/模块架构设计 | architect | 新模块、跨模块影响、重大技术选型（准备阶段完成） |
| 产品设计（功能流程） | product | 功能流程复杂、多步骤交互、用户旅程不明确 |
| UI/交互设计 | designer | 涉及前端界面（执行阶段 2.2） |
| 技术方案设计（ADR） | architect | 每个 Story 的接口、类结构、模块交互 |

> 适用规范：[需求管理规范](../dev/requirement-standard.md)、[架构设计方法论](../../design/README.md)、[领域建模规范](../dev/apps/service/domain-modeling-standard.md)、[架构约束](../dev/architecture-constraints.md)

### 3.2 UI/交互设计
>
> 涉及前端界面的任务触发，纯后端任务跳过。

- 界面布局和交互流程设计
- 组件规范和设计 token 定义
- 响应式和多端适配方案
- 输出设计稿和交互说明

> 适用规范：[UI 设计规范](../../design/ui/Readme.md)

### 3.3 编码实现

- 按技术设计和 UI 设计编码
- 遵循编码规范和项目约定
- 输出源码，并在 `docs/task/{版本}/{AAF-XXX}/dev-log.md` 记录开发日志

**dev-log.md 写作规范**：

| 时机 | 内容 |
|------|------|
| 编码过程中 | 遇到与设计不符的情况随时记录，说明原因 |
| 编码完成后 | 补充实现文件列表、关键决策、后续开发者需要知道的注意事项 |

写什么：
- **实现文件**：列出新增/修改的主要文件路径和说明
- **实现决策**：与设计文档不同的地方及原因（设计变更、技术限制等）
- **注意事项**：依赖关系、配置要求、已知问题、后续待办

> 适用规范：[编码风格规范](../dev/apps/service/coding-style-standard.md)、[架构约束](../dev/architecture-constraints.md)

### 3.3.1 AI 自验证循环（developer 强制内循环）

developer 在编码过程中按场景分层决定验证力度。这是 `check` target 与 `acceptance` target 分离设计的核心依据——developer 自己确认代码"能跑起来、符合规范"，tester 只负责验证"满足需求"。

**分层验证决策**：

| 场景 | 验证要求 | 说明 |
|------|----------|------|
| 🟢 对话中小改动（探索/试错/文档） | 可跳过 | 自行判断，不阻塞对话节奏 |
| 🟡 单文件/单模块改动 | 跑对应项目 test | `pnpm nx test service` 或 `pnpm nx test webui` |
| 🔴 任务完工汇报前 / PR 前 | `pnpm check:affected` 全绿 | 失败即未完工，不得汇报 |
| 🔴 迭代交付前 | `pnpm check` + `pnpm acceptance` 全绿 | 见交付清单 |

**完工汇报循环伪代码**（🔴 场景）：

```text
编写代码满足需求
  ↓
运行 pnpm check:affected     ← 一键跑完 lint + typecheck + 单测 + build
  ↓
全部通过？
  ├─ 否 → 读错误输出 → 修复代码 → 回到顶部
  └─ 是 → 汇报给协调者，进入代码审查环节
```

**硬规则**：

1. `check` 失败状态下直接汇报视为未完工，协调者有权直接驳回。
2. 不得通过以下手段"碰运气通过"：
   - 给测试加 `@Disabled` / `it.skip` 绕过失败
   - 降低测试期望值迁就实现
   - 在代码里加 try-catch 吞掉异常
3. 遇到无法修复的 blocker（如依赖工具缺失、规范冲突），记录到 `dev-log.md` 并转人工，不强行跳过。

**developer 与 tester 的分工边界**：

| 项 | developer（check） | tester（acceptance） |
|------|-------------------|-------------------|
| 入口命令 | `pnpm check:affected` | `pnpm acceptance:affected` |
| 验证目标 | 代码技术正确性 | 代码需求正确性 |
| 对标物 | 编码规范、架构约束、单测用例 | 需求文件的 Gherkin AC |
| 测试命名 | `XxxTest.java`、`*.test.ts(x)` | `XxxIT.java` / `XxxAcceptanceTest.java`、`*.accept.test.ts(x)` |
| 失败处理 | 自己内循环修复 | 退回 developer 重新走 check |

**前置依赖**：`acceptance` 执行前 `check` 必须全绿。tester 发现"编译不过"或"单测挂了"这类问题应**立刻退回 developer**，不在 acceptance 阶段修构建问题。

> 适用规范：[编码规范 #硬约束 5-9](../../../.kiro/skills/coding-standards/SKILL.md)

- 编写单元测试（覆盖核心逻辑）
- 自测冒烟（主流程跑通）
- 静态分析通过
- 输出测试代码和自测报告

> 适用规范：[单元测试规范](../dev/test/unit-test-standard.md)

### 3.5 代码审查

- 规范合规检查（命名、结构、异常处理）
- 设计符合性检查（是否按设计实现）
- 安全审查（注入、权限、敏感数据）
- 输出审查意见

> 适用规范：[代码审查规范](../dev/code-review-standard.md)（含安全审查）

### 3.6 代码重构
>
> 审查发现结构性问题时触发，非每次必须。

- 消除重复代码和坏味道
- 优化模块结构和依赖关系
- 确保重构后测试全部通过

> 适用规范：[编码风格规范](../dev/apps/service/coding-style-standard.md)、[架构约束](../dev/architecture-constraints.md)

### 3.7 确认（验收测试）

- 对照 AC 逐条编写验收测试
- 集成测试（模块间交互）
- 边界场景和异常路径测试
- 需求覆盖验证（每条需求有对应测试）
- 输出测试报告

> 适用规范：[验收测试规范](../dev/test/acceptance-test-standard.md)

### 3.7.1 Bug 处理

测试过程中发现的 Bug 按以下流程处理：

```text
tester 发现 Bug
  → 登记到 docs/task/{版本}/{AAF-XXX}/bugs.md
    → developer 修复
      → developer 运行 check:affected 确认修复
        → tester 验证修复
          → 移到"已修复"表格，关联提交
```

**Bug 分级**：

| 级别 | 定义 | 处理要求 |
|------|------|---------|
| P0 | 阻塞主流程、数据丢失、安全漏洞 | 立即修复，阻塞发布 |
| P1 | 功能不可用但有绕过方案 | 当前迭代必须修复 |
| P2 | 体验问题、边界场景异常 | 视情况修复或延后 |

**与质量门控的关系**：
- P0 Bug 未修复 = blocker，阻塞发布
- P1 Bug 计入 major，超过 2 个阻塞发布
- P2 Bug 计入 minor，不阻塞发布但需记录

> 适用规范：[任务管理规范 #Bug 管理](../../task/Readme.md#bug-管理)

### 3.8 过程审计

- 检查流程合规（是否按流水线执行）
- 检查规范遵守（编码、设计、测试规范）
- 检查文档完整性（每个环节产出是否齐全）
- 输出审计记录

> 适用规范：[过程审计规范](process-audit-standard.md)

### 3.9 质量门控

- 统计 blocker/major/minor 数量
- 判定通过或回退
- 通过条件：blocker = 0 且 major ≤ 2
- 不通过则按问题类型回退对应环节

> 问题分级定义见 [协作规范](collaboration-standard.md)

### 3.10 进度跟踪（贯穿执行全程）

- 监控各任务流水线进度
- 识别阻塞和延期风险
- 协调资源和优先级调整

> 适用规范：[任务管理规范](../../task/Readme.md)

### 3.11 集成验证

- 多任务/多模块集成后的整体验证
- 确认模块间接口对接正确
- 回归测试（已有功能未被破坏）

> 适用规范：[集成测试规范](../dev/test/integration-test-standard.md)

## 4. 发布

**目标**：部署验证，收集反馈。

### 4.1 测试环境部署

- 构建部署包
- 部署到测试环境
- 验证部署成功（冒烟测试）

> 适用规范：[部署规范](../dev/deployment-standard.md)

### 4.2 数据库迁移
>
> 有 schema 变更时触发。

- 编写迁移脚本
- 测试环境验证迁移
- 回滚方案准备

> 适用规范：[数据库迁移规范](../dev/apps/service/database-migration-standard.md)

### 4.3 用户验收

- 演示已完成功能
- 收集用户反馈
- 记录遗留问题和改进建议

### 4.4 发布说明

- 汇总本版本变更内容
- 标注破坏性变更和升级指引
- 输出 Release Note

> 适用规范：[发布规范](../dev/git/release-standard.md)

### 4.5 正式发布

- 部署到生产环境
- 生产冒烟验证
- 打 Git Tag

> 适用规范：[部署规范](../dev/deployment-standard.md)、[发布规范](../dev/git/release-standard.md)、[分支管理规范](../dev/git/branch-manage-standard.md)

## 5. 总结

**目标**：回顾改进，沉淀知识。

### 5.1 迭代回顾

- 做得好的（继续保持）
- 待改进的（分析根因）
- 行动项（落实到下个迭代）

### 5.2 度量分析

- 需求完成率（计划 vs 实际）
- 缺陷密度（blocker/major/minor 分布）
- 周期时间（从需求到交付）
- 回退次数和原因分布
- 输出度量报告

> 适用规范：[度量标准](measurement-standard.md)

### 5.3 过程改进

- 基于度量数据和回顾结论，识别改进点
- 更新规范和流程
- 输出规范变更记录

### 5.4 规范制定/更新
>
> 迭代中发现规范缺失或不合理时触发。

- 编写或修订编码规范、设计规范、测试规范
- 团队评审规范变更
- 发布新版规范

### 5.5 知识沉淀

- 记录设计决策和理由
- 记录踩坑经验和解决方案
- 更新知识库

### 5.6 backlog 归档

- 已完成和已取消的任务移入归档
- 整理待排期任务
- 更新 backlog 状态

> 适用规范：[任务管理规范](../../task/Readme.md)
