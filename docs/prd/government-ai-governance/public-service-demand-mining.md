# “‘小切口’民生服务需求挖掘”完整解决方案

> **一句话定位**：在合法授权和隐私保护前提下，融合群众诉求、政务服务与公共服务供给数据，用AI发现共性需求和服务短板，经人工研判后开展小规模服务试点与效果评估，实现从“办结一件事”向“解决一类需求”转变。

## 1. 方案摘要与设计结论

| 议题 | 设计结论 |
|---|---|
| 治理对象 | 分析对象是区域、时段、主题和服务供需关系，不是对具体居民进行隐性评分 |
| 建设闭环 | 必须贯通“数据治理—需求信号—证据研判—服务试点—效果评估—规则改进”，不止于热词大屏 |
| AI定位 | AI负责分类、聚类、趋势识别、相似案例检索和材料辅助起草；资源配置和政策决定由有权人员作出 |
| 证据原则 | 每条洞察需展示样本范围、来源、时间、代表性、质量、置信度和反例；相关性不得表述为因果 |
| 小切口方法 | 从范围可控、责任明确、可在8—12周验证的服务问题起步，再决定推广、调整或停止 |
| 隐私策略 | 默认去标识、聚合分析、最小必要使用和小样本抑制；个案回访须回到有权限的原业务系统 |

## 2. 背景、目标与原则

### 2.1 现状痛点

1. 12345、网格走访、政务办件、部门热线和线下服务数据分散，同一需求难以跨渠道识别。
2. 诉求办理以单件及时办结为主，共性问题、潜在需求和服务供给不足缺少持续分析。
3. 不同部门分类口径、区域粒度和时间尺度不一致，简单词频容易放大噪声。
4. 沉默群体、数字鸿沟和服务可及性难从投诉数量直接体现，易出现“声音大等于需求大”。
5. 分析报告与服务设计、预算安排、试点实施和效果评估脱节。

### 2.2 建设目标

- **看见需求**：识别跨渠道、跨时段的民生共性主题、增长趋势和异常信号。
- **定位短板**：将需求与服务网点、容量、时段、办理难度和人群覆盖进行供需对照。
- **辅助决策**：形成有证据、可解释、可追溯的“小切口”服务建议。
- **验证成效**：通过小范围、可逆试点验证服务可达性、满意度和需求变化。
- **守住底线**：保护个人信息和群体权益，避免标签化、歧视性分配和算法替代行政决策。

### 2.3 原则

需求导向而非技术导向；聚合洞察而非个体画像；证据充分而非唯模型结论；普惠公平而非唯诉求量；先试点后推广；全过程留痕、可申诉、可退出。

## 3. Epic、用户与用户故事

### 3.1 Epic

**目标**：建立可持续的民生需求发现和服务优化能力，将多源数据转化为经人工审核的需求议题，并通过试点和评估改善公共服务供给。

**范围**：首期建议聚焦养老助餐、托育服务、基层医疗、公共交通接驳、政务办事便利化等1—3个主题；仅接入完成授权、目录登记和质量评估的数据。

### 3.2 用户角色

| 角色 | 主要职责 | 关键权限 |
|---|---|---|
| 民生平台主管 | 选择议题、组织跨部门研判、批准试点 | 议题立项、方案审批、推广/停止 |
| 业务分析员 | 验证需求信号、构建证据链、形成洞察 | 分析、标注、提交研判 |
| 部门业务专员 | 解释业务口径、供给能力和政策约束 | 数据确认、方案会签 |
| 街道/社区人员 | 补充现场信息、实施服务试点 | 现场核验、执行反馈 |
| 政策评估人员 | 设计指标和对照方法、评估成效 | 评估方案、结论签署 |
| 数据管理员 | 授权、质量、血缘、脱敏与期限管理 | 数据目录和访问审批 |
| 算法运营员 | 模型评测、漂移监测、偏差审查 | 模型发布、阈值、回滚 |
| 审计与安全员 | 监督用途、权限、导出和风险事件 | 审计、阻断、调查 |

### 3.3 用户故事

1. **作为业务分析员**，我希望系统将不同渠道的同义诉求归入统一主题，并保留原始来源，以便识别共性需求。
2. **作为民生平台主管**，我希望看到需求强度、增速、服务供给和区域差异，以便选择可验证的小切口。
3. **作为部门业务专员**，我希望修改错误分类并解释政策或季节因素，以便避免AI误判。
4. **作为街道人员**，我希望接收明确的试点对象范围、服务动作和反馈指标，以便实施并留痕。
5. **作为政策评估人员**，我希望比较试点前后及适当对照数据，以便判断变化是否可能由服务措施带来。
6. **作为数据管理员**，我希望每次分析都绑定用途、授权和保留期限，以便防止数据越界使用。

**完成条件**：试点主题形成从多源数据接入、需求洞察、联合研判、服务试点到效果评估的闭环，且个体信息不出现在聚合分析界面。

## 4. 业务闭环与核心方法

### 4.1 闭环流程

```text
数据目录与用途审批
  → 接入、去标识、质量校验、口径映射
  → NLP分类/聚类 + 趋势/异常检测
  → 形成候选需求信号
  → 样本、供给、公平性、反例和现场信息交叉验证
  → 联合研判并形成需求议题
  → 设计可逆的小切口服务试点
  → 有权人员审批与基层实施
  → 过程监测、居民反馈和效果评估
  → 推广 / 调整 / 停止，并回写分类、规则和知识库
```

### 4.2 议题状态

`候选信号 → 待验证 → 待联合研判 → 已立项 → 方案设计中 → 待审批 → 试点中 → 待评估 → 已推广/已调整/已停止/已归档`。

- 候选信号不得直接进入资源配置。
- 任何结论必须经过业务人员验证；跨部门议题须联合会签。
- 试点需明确假设、服务动作、覆盖范围、预算上限、风险和停止条件。
- 评估证据不足时只能给出“尚不能判断”，不得强行得出有效或无效结论。

### 4.3 小切口选择评分

候选议题按需求紧迫性、受益覆盖、服务缺口、实施可行性、责任清晰度、可测量性、公平影响、成本风险八个维度评分。评分用于排序，不替代决策；系统展示各维度证据和人工调整理由。

## 5. 总体架构

```text
数据源层：12345｜政务服务｜部门热线｜网格走访｜服务设施/资源｜人口统计｜GIS
  ↓ 数据目录、用途审批、交换接口
治理层：去标识｜主数据｜口径映射｜质量规则｜血缘｜时空网格｜小样本抑制
  ↓
分析层：文本分类｜主题聚类｜情感/紧迫度辅助识别｜趋势异常｜供需匹配｜公平性分析
  ↓
知识与智能层：政策知识库｜指标语义层｜证据检索｜洞察生成｜方案辅助起草｜评估引擎
  ↓
应用层：需求雷达｜议题工作台｜供需地图｜联合研判｜试点管理｜效果评估｜运营审计
  ↔ 统一身份、数据共享交换、协同办公、项目/预算及原业务系统
```

- 明细数据在安全计算区使用；业务应用优先消费聚合指标和经审批的证据摘要。
- 个人诉求原文和联系方式留在权威业务系统，本平台保存去标识文本或受控引用。
- 指标语义层统一主题、区域、服务、人群、时间和统计口径，避免部门各算一套。

## 6. 数据方案

### 6.1 数据来源

| 数据域 | 典型数据 | 用途 | 主要风险/控制 |
|---|---|---|---|
| 群众诉求 | 12345、部门热线、网上留言 | 主题、趋势、未满足需求 | 去标识、渠道偏差校正、原文受控 |
| 政务服务 | 办件、咨询、退件、等待时长 | 办事障碍和服务短板 | 不输出个体办件画像 |
| 基层治理 | 网格走访、社区调查、服务记录 | 补充沉默群体和现场证据 | 采集告知、最小字段、质量抽检 |
| 服务供给 | 网点、容量、时段、预约、服务目录 | 供需缺口与可达性 | 明确更新责任和有效期 |
| 统计人口 | 人口规模、年龄结构等聚合数据 | 分母、标准化和公平性分析 | 只使用法定授权粒度 |
| 空间交通 | GIS、路网、公交、步行可达性 | 服务半径与空间阻隔 | 防止精确住址反推 |
| 政策知识 | 政策、办事指南、服务标准 | 解释约束和形成引用 | 版本、效力范围、发布时间 |
| 反馈评估 | 满意度、服务使用、访谈、成本 | 效果和可持续性评估 | 自愿反馈、用途限制 |

### 6.2 数据治理规则

1. 数据接入前登记权属、用途、合法依据、字段、粒度、更新频率、共享范围和删除期限。
2. 身份标识采用不可逆去标识或受控映射；分析区原则上不保留姓名、电话、证件号和精确住址。
3. 统一诉求主题、服务目录、行政区划、时间和人群统计口径，保留源值和映射版本。
4. 聚合结果执行最小样本阈值（阈值由数据安全评估确定）、相邻区间合并、噪声或抑制策略，禁止通过多次查询反推小群体。
5. 所有比例必须展示分母、缺失率和覆盖渠道；跨期比较需确认口径未变化。
6. 质量低于阈值的数据可作为线索，不得生成高确定性结论或驱动自动处置。

### 6.3 公平性与代表性

系统同时显示诉求量、标准化需求率、服务覆盖率和渠道覆盖差异。对老年人、残障人士、低数字化参与群体等，只能基于合法授权的聚合统计开展服务可及性分析；不得生成可下载的敏感个体名单。必要的定向服务由原业务部门按照法定程序确定。

## 7. AI方案与人在回路

### 7.1 AI能力

| 能力 | 推荐方法 | 主要输出 | 控制要求 |
|---|---|---|---|
| 文本清洗与分类 | 规则 + 领域分类模型 | 主题、事项、紧迫度候选 | 多标签、置信度、人工修正 |
| 语义去重与聚类 | 向量检索、密度/层次聚类 | 相似诉求组、新主题候选 | 不以情绪替代事实，保留代表样本 |
| 趋势和异常 | 季节分解、统计检验、时序模型 | 增长、突变、持续性 | 显示基线、窗口和不确定性 |
| 供需缺口 | GIS可达性、容量比、排队指标 | 区域/时段缺口 | 不将“零投诉”等同“零需求” |
| 公平性分析 | 分组覆盖率、差异指标 | 可能的不均衡信号 | 仅聚合输出，需业务解释 |
| 政策检索 | 版本化RAG | 适用条款和来源 | 引用原文，不确定时拒答 |
| 洞察与方案起草 | 受约束生成式AI | 证据摘要、问题树、备选动作 | 只引用检索证据，人工审核发布 |
| 效果评估辅助 | 统计分析、匹配/差分等方法 | 效果区间、假设检查 | 方法由评估人员确认，不自动宣称因果 |

### 7.2 置信度与证据卡

每个需求信号必须生成“证据卡”：主题、时间窗、区域粒度、样本量、数据源覆盖、变化幅度、模型置信度、数据质量、供给对照、反例、可能解释、代表性限制和建议验证动作。综合分只用于排序，界面必须允许展开各项，不得以单一“民生指数”遮蔽不确定性。

### 7.3 人工决策门

| 决策点 | AI可做 | 必须由人做 |
|---|---|---|
| 信号发现 | 分类、聚类、趋势识别 | 确认是否为真实需求议题 |
| 议题排序 | 依据已发布权重计算建议分 | 调整优先级并记录理由 |
| 服务方案 | 检索案例、生成备选动作和风险清单 | 确定方案、预算、责任和覆盖范围 |
| 资源安排 | 提供容量和情景模拟 | 按法定程序批准配置 |
| 效果评估 | 计算描述统计和模型估计 | 选择方法、解释限制、签署结论 |
| 推广停止 | 汇总证据和预警 | 作出推广、调整或停止决定 |

### 7.4 模型治理

模型按主题、渠道、地区、语言表达和时间分层评测；至少监测分类宏/微F1、聚类纯度、趋势告警准确性、置信度校准、人工修正率和群体差异。新模型依次经过离线评测、偏差审查、影子运行、灰度发布；指标恶化或投诉发生时可回滚到稳定版本和人工规则。

### 8.1 关键业务规则

- “热点”至少同时考虑绝对量、人口/服务分母、环比/同比、渠道覆盖和持续时间。
- 新主题由模型发现后进入待审词表，未经业务审核不得自动改变历史统计口径。
- 需求议题只能引用在授权期内的数据；授权到期后停止刷新并按策略删除或匿名化。
- 生成式AI不得虚构政策、数字、访谈或案例，所有事实陈述必须绑定来源引用。
- 系统不得向普通用户提供明细个体筛选、敏感属性交叉钻取或精确住址热图。
- 服务试点对权益、收费或资格产生影响时，须执行额外法务、公平和公众沟通审查。

| 效果评估 | `InterventionEvaluation` | `intervention_evaluation` | 方法、指标、结果区间、限制和结论 |
| 模型发布 | `DemandModelRelease` | `demand_model_release` | 模型、数据集、阈值、指标和发布状态 |

原始个人信息由源系统管理，不在本产品新增“居民画像”概念；如需联系回访，由授权人员通过源系统发起并仅回传去标识结果。

## 10. 接口与集成

| 接口 | 方向 | 主要内容 | 关键控制 |
|---|---|---|---|
| `/api/v1/data-authorizations` | 双向 | 用途、字段、期限、审批 | 到期自动停用、变更留痕 |
| `/api/v1/requests/import` | 源系统→平台 | 去标识诉求、渠道、时间、区域 | 批次签名、质量报告、幂等 |
| `/api/v1/service-supplies` | 部门系统→平台 | 服务目录、网点、容量、时段 | 主体和有效期校验 |
| `/api/v1/demand-signals` | 平台内部/城运 | 信号查询、订阅、验证 | 聚合权限、小样本抑制 |
| `/api/v1/issues` | 双向 | 议题立项、会签、状态 | 状态机、乐观锁、审批权限 |
| `/api/v1/pilots` | 协同/项目系统 | 试点计划、进度、风险 | 预算和责任引用，不代替法定系统 |
| `/api/v1/evaluations` | 双向 | 指标、方法、结果和签署 | 版本化、评估人签名 |
| `/api/v1/policy-search` | 应用→知识库 | 查询、答案、条款引用 | 仅返回授权有效版本 |

接口详细字段在技术设计中定义；任何接口不得通过组合参数绕过聚合阈值，批量导出需单独授权。

## 11. 安全、隐私与算法治理

- 建立数据保护影响评估，特别审查诉求原文、健康、残障、家庭困难等敏感信息使用。
- 采用分区隔离：原始受控区、去标识分析区、聚合服务区；跨区操作均审计。
- 实施RBAC + 属性权限、行列级过滤、查询频控、动态脱敏、水印、导出审批和异常访问检测。
- 不向模型供应商发送未获授权的政务数据；本地/专有环境部署时仍需限制日志和缓存。
- 不公开内部推理链；公开的是来源、方法、规则、置信度、限制和人工决定。
- 建立算法影响评估、模型卡、数据集卡、偏差测试、申诉纠错和紧急停用机制。
- 对外发布统计产品前执行重识别风险评估；开放数据与内部研判数据分开管理。

## 12. 非功能需求

以下均为**建议目标**，最终在试点期核定基线：

| 类别 | 建议目标 |
|---|---|
| 数据时效 | 高频诉求T+1完成接入分析；服务供给按责任部门约定更新 |
| 查询性能 | 常用区域/主题聚合查询P95≤3秒；复杂专题分析异步反馈进度 |
| 可用性 | 核心工作台月可用性≥99.9% |
| 可追溯 | 洞察、方案和报告中的统计数字100%可回溯到口径、批次和来源 |
| 隐私 | 越权明细访问和未审批导出为0；授权到期处置完成率100% |
| 可解释 | 每个信号展示样本、基线、方法、置信度、限制和人工状态 |
| 无障碍 | 核心界面支持键盘操作、色弱友好和非颜色单一编码 |
| 灾备 | 建议RPO≤15分钟、RTO≤4小时；恢复后核验分析任务一致性 |

## 13. 部署运维

- 部署在政务云/城市云受控区域，数据计算与模型服务按敏感等级隔离；不需要原文的模型只接收去标识字段。
- 开发、测试、生产环境隔离，生产样本用于评测须执行审批、抽样和脱敏。
- 监控数据接入延迟、质量、分类分布、主题漂移、告警命中、人工修正、群体差异、知识引用和生成幻觉。
- 模型或知识库异常时降级为统计看板和人工分析；不影响原诉求系统正常办理。
- 月度开展主题口径与模型复盘，季度开展隐私、公平和服务成效审查，年度开展权限清理与灾备演练。

## 14. 实施路线

| 阶段 | 建议周期 | 主要产出 | 决策门 |
|---|---|---|---|
| 0. 议题与数据准备 | 4—6周 | 场景清单、数据目录、用途授权、主题口径、基线 | 数据可合法使用且责任部门参与 |
| 1. 需求雷达试点 | 8—12周 | 1—3个主题、多源分析、证据卡、影子研判 | 信号有效性和隐私控制达标 |
| 2. 服务闭环试点 | 8—12周 | 议题立项、服务方案、基层实施、过程监测 | 服务动作可执行且风险可控 |
| 3. 评估与推广 | 4—8周 | 评估报告、推广/调整/停止决定、模型反馈 | 改善具有实质意义且公平可接受 |
| 4. 常态化运营 | 持续 | 扩展主题、制度和年度评估 | 形成稳定数据、人员和运营预算 |

## 15. 指标体系

所有目标为**建议值**，基线由试点首期核定：

| 维度 | 指标 | 建议目标/口径 |
|---|---|---|
| 数据 | 授权数据按期到达率 | ≥95% |
| 质量 | 主题分类人工一致率 | 按主题核定，持续优于既有规则基线 |
| 发现 | 有效需求信号率 | 经人工验证为有效的信号占比≥70% |
| 效率 | 从信号到联合研判时长 | 较线下基线下降≥40% |
| 闭环 | 已立项议题进入试点或形成明确处置决定比例 | ≥90% |
| 服务 | 试点服务可达性/使用率 | 按场景较基线显著改善 |
| 体验 | 目标服务满意度 | 较基线提升，报告置信区间和样本结构 |
| 公平 | 重点群体服务覆盖差距 | 不扩大；扩大时必须解释并整改 |
| 治理 | 洞察证据完整率 | 100% |
| 隐私 | 小样本泄露、越权明细访问 | 0起 |
| 成本 | 单位有效议题分析与试点成本 | 形成可比基线并持续优化 |

## 16. 验收标准（Gherkin）

### AC-01 跨渠道主题归并

```gherkin
Given 12345、网格走访和部门热线存在表达不同但语义相近的养老助餐诉求
When 系统完成分类和语义聚类
Then 形成同一主题下的候选需求信号
And 保留各来源、口径版本、样本量、置信度和代表性限制
```

### AC-02 小样本保护

```gherkin
Given 用户查询的区域、时段和敏感维度组合低于最小样本阈值
When 用户请求查看结果或继续下钻
Then 系统抑制、合并或安全扰动结果且不得返回明细
And 记录查询及采用的隐私策略
```

### AC-03 证据化研判

```gherkin
Given 系统发现某区域托育诉求连续增长
When 分析员打开需求信号
Then 系统展示诉求趋势、人口分母、渠道覆盖、现有供给、可达性、反例和数据质量
And 不将增长直接表述为某一政策或因素造成
```

### AC-04 人工决策门

```gherkin
Given AI已生成服务缺口和资源调整建议
When 建议涉及新增预算、服务资格或资源重新分配
Then 系统只能提交有权人员会签审批
And 未审批前不得向执行系统下发配置变更
```

### AC-05 政策引用防幻觉

```gherkin
Given 用户要求生成某服务方案的政策依据
When 知识库不存在适用且有效的权威条款
Then 助手明确提示证据不足且不生成虚构依据
And 当存在依据时逐条返回文件名、版本和原文定位
```

### AC-06 试点评估

```gherkin
Given 服务试点已定义基线、过程、结果、公平和成本指标
When 试点到达评估时间点
Then 系统生成包含样本、方法、结果区间、假设检验和限制的评估草案
And 由评估人员签署后才能形成推广、调整或停止建议
```

### AC-07 授权到期

```gherkin
Given 某数据资源的用途授权已到期且未续期
When 调度任务尝试刷新相关需求指标
Then 系统拒绝读取并通知数据管理员
And 按授权策略停止展示、删除或匿名化衍生数据并保留审计
```

### AC-08 模型偏差与回滚

```gherkin
Given 新模型在特定渠道或区域的人工修正率超过发布阈值
When 监控触发偏差或漂移告警
Then 系统停止该范围自动推荐并切换稳定模型或人工模式
And 保留影响范围、处置过程和复评结果
```

## 17. 测试要点

- **验收测试**：按AC编号覆盖数据授权、分析、研判、试点、评估、权限和异常路径。
- **数据测试**：检查去标识、重复、缺失、口径映射、分母、时间穿越、授权到期和血缘。
- **AI测试**：按主题、渠道、区域、文本长度和表达方式分层评测，并构造方言、反讽、混合诉求和新主题样本。
- **隐私测试**：小样本、差分查询、关联推断、越权导出、缓存泄露和日志脱敏。
- **统计测试**：季节性、基线变化、选择偏差、样本不足、口径变更和伪因果结论。
- **安全测试**：提示注入、知识污染、恶意文件、权限提升、接口重放和供应链风险。
- **业务演练**：至少完成一个议题从信号到试点评估的桌面推演和真实小范围验收。

## 18. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 渠道偏差 | 投诉多不等于真实需求大 | 引入人口/服务分母、走访和多渠道交叉验证 |
| 分类口径漂移 | 跨期指标不可比 | 主题版本化、重算影响评估、变更说明 |
| 伪相关/伪因果 | 错误政策判断 | 证据卡、反例、专业评估和保守表述 |
| 敏感群体标签化 | 歧视和隐私风险 | 聚合分析、小样本抑制、禁止个体名单输出 |
| 模型幻觉 | 虚构政策或事实 | 受约束RAG、强制引用、无证据拒答、人工签发 |
| 部门协同不足 | 议题无法转化为行动 | 明确牵头部门、会签SLA和争议升级机制 |
| 只建平台不做试点 | 无法证明服务价值 | 验收绑定真实服务干预和效果评估 |
| 评估周期过短 | 无法判断长期效果 | 预设观察期、过程指标和后续追踪计划 |
| 供应商锁定 | 数据与模型难迁移 | 开放格式、模型可替换、导出和退出条款 |
