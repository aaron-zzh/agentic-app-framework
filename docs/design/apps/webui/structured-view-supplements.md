# 结构化交互模式补充设计

> 本文档是 [结构化交互模式设计](./interaction-mode-structured-view.md) 的补充，覆盖主文档 64 章之外的边缘场景能力。按需实现，非 MVP 必须。


## 一、数据脱敏展示

### 设计思路

B 端系统存储大量敏感信息（手机号、身份证、银行卡、邮箱）。合规要求（GDPR / 个人信息保护法）敏感字段在列表和非授权场景下必须脱敏展示，仅在明确授权后显示完整值。

### 字段配置

```typescript
interface BaseField {
  mask?: {
    enabled: boolean
    pattern: 'phone' | 'idCard' | 'bankCard' | 'email' | 'name' | 'custom'
    customPattern?: { show: number; hide: number; position: 'middle' | 'tail' }
    revealPermission?: string       // 查看完整值所需权限（默认 admin）
    revealAction?: 'click' | 'hover' | 'none'  // 触发方式（none=永不显示）
  }
}
```

### 脱敏规则

| pattern | 原始值 | 脱敏后 |
|---------|--------|--------|
| phone | 13800138000 | 138****8000 |
| idCard | 110101199001011234 | 1101\*\*\*\*\*\*\*\*1234 |
| bankCard | 6222021234567890 | 6222\*\*\*\*\*\*\*\*7890 |
| email | zhang@example.com | z\*\*\*\*@example.com |
| name | 张三丰 | 张\*丰 |

### 交互

```text
列表视图：
  手机号列显示 138****8000

表单视图：
  [138****8000] [👁 查看完整]
  点击 👁 → 权限校验 → 显示 13800138000（3 秒后自动恢复脱敏）
  无权限 → Toast "无权查看完整信息"
```

### 实现要点

- 脱敏在后端执行（API 返回脱敏值），非前端遮盖——防止 DevTools 查看
- 查看完整值走独立接口：`GET /api/{entity}/{id}/reveal?field=phone`
- 每次 reveal 记录到审计日志（谁在什么时间查看了谁的什么字段）
- 导出时默认导出脱敏值，管理员可选择导出完整值（需二次确认）


## 二、评论富文本与图片

### 设计思路

第二十章活动流评论当前为 Markdown 纯文本。实际场景中用户需要粘贴截图、插入图片来描述问题或反馈。

### 能力增强

| 能力 | 说明 |
|------|------|
| 粘贴截图 | Ctrl+V 粘贴剪贴板图片，自动上传并插入 |
| 拖拽图片 | 拖拽图片文件到评论框 |
| @提及 | 保持现有能力（第五十五章） |
| 表情 | Emoji 选择器 |
| 代码块 | 行内代码 + 代码块（语法高亮） |
| 引用 | 引用上一条评论 |

### 编辑器选择

轻量富文本编辑器（非 richText 字段的完整编辑器），推荐 Tiptap 的精简配置：

```text
工具栏：[B] [I] [代码] [链接] [图片] [表情] [@]
支持：粗体、斜体、链接、图片、代码块、引用、@提及
不支持：表格、标题层级、复杂排版（评论不需要）
```

### 图片处理

```text
粘贴/拖拽图片
  → 前端压缩（>1MB 时压缩到 1MB 以内）
  → 上传到文件服务
  → 插入为 inline image（缩略图）
  → 点击放大预览（lightbox）
```

### 配置

```typescript
interface EntityDef {
  chatter?: {
    // ...原有配置
    richComments?: boolean          // 启用富文本评论（默认 false，纯 Markdown）
    allowImages?: boolean           // 允许图片（默认 true when richComments）
    maxImageSize?: number           // 单张图片大小限制（默认 5MB）
  }
}
```


## 三、字段级并发编辑提示

### 设计思路

第十三章实现了记录级乐观锁和多人在线感知。本章细化到字段级——当多人同时编辑同一记录时，提示"张三正在编辑标题字段"，避免冲突。

### 感知粒度

| 粒度 | 第十三章（已有） | 本章（补充） |
|------|-----------------|-------------|
| 记录级 | "张三正在编辑此记录" | — |
| 字段级 | — | "张三正在编辑标题" |

### 交互

```text
表单视图：
  标题字段：[Q2 季度报告]  👤张三正在编辑...
  （标题字段边框变为蓝色虚线，右上角显示编辑者头像）

  当张三离开该字段 → 提示消失
  当张三保存 → 本地字段值自动更新（若无冲突）
```

### 实现机制

```text
用户聚焦字段 → WebSocket 广播 { entity, id, field: 'title', user: '张三' }
其他用户收到 → 对应字段显示编辑者标记
用户离开字段 → WebSocket 广播 { entity, id, field: 'title', action: 'leave' }
```

### 冲突处理

- 两人同时编辑同一字段 → 后提交者触发乐观锁冲突（复用第十三章机制）
- 字段级提示的目的是**预防**冲突，而非解决冲突
- richText 字段已有 Yjs CRDT 实时协同，不需要本机制

### 配置

```typescript
interface EntityDef {
  collaboration?: {
    enabled: boolean                // 启用实时协作感知
    fieldLevel?: boolean            // 启用字段级提示（默认 false，仅记录级）
  }
}
```


## 四、定时发布与延迟操作

### 设计思路

用户希望"这篇文档明天 9:00 自动发布""这条通知下周一发送"。虽然可通过第四十二章自动化规则的 delay 触发器实现，但缺少表单内的直观操作入口。

### 交互

```text
表单 FormHeader 操作按钮：
  [发布 ▾]
    ├── 立即发布
    └── 定时发布...
          → 弹出时间选择器
          ┌─────────────────────────────┐
          │ 定时发布                     │
          │ 日期：[2026-05-14]          │
          │ 时间：[09:00]               │
          │ 时区：[Asia/Shanghai ▾]     │
          │                             │
          │ [取消] [确认定时]            │
          └─────────────────────────────┘

设置后表单顶部显示：
  ⏰ 将于 2026-05-14 09:00 自动发布  [取消定时]
```

### 数据模型

```text
sys_scheduled_action 表：
  id | entity_type | entity_id | action_key | scheduled_at
     | timezone | status('pending'|'executed'|'cancelled') | created_by
```

### 行为规则

- 定时到达 → 后端执行对应 action（如修改 status 为 published）
- 定时前用户可随时取消
- 定时前用户手动执行了同一操作 → 自动取消定时
- 执行结果通知到消息中心

### 配置

```typescript
interface EntityAction {
  // ...原有配置（第三十一章）
  schedulable?: boolean             // 是否支持定时执行（默认 false）
}
```

### 适用场景

| 场景 | action | 定时 |
|------|--------|------|
| 文档定时发布 | publish | 指定时间 |
| 通知定时发送 | send | 指定时间 |
| 优惠券定时生效 | activate | 指定时间 |
| 记录定时归档 | archive | 指定时间 |


## 五、全局操作回放（Undo 栈）

### 设计思路

用户在列表中误操作（如批量修改了错误的记录、拖拽到了错误的看板列），需要全局 Undo 能力。不仅限于表单内的文本撤销，还包括数据操作的撤销。

### 可撤销操作

| 操作 | 撤销方式 |
|------|---------|
| 行内编辑 | 恢复原值 |
| 看板拖拽（状态变更） | 恢复原状态 |
| 批量修改字段 | 批量恢复原值 |
| 删除（软删除） | 恢复记录（第四十四章撤销） |
| 排序拖拽 | 恢复原排序 |

### 不可撤销操作

- 审批操作（流程已推进）
- 彻底删除
- 外部系统调用（Webhook 已发送）
- 文件上传/删除

### 交互

```text
操作后底部 Toast：
  "已将 3 条记录状态改为已完成"  [撤销 ⌘Z]  (5 秒倒计时)

快捷键：⌘Z / Ctrl+Z → 撤销最近一次可撤销操作
```

### 实现机制

```text
前端维护操作栈（最近 10 步）：
  operationStack = [
    { type: 'update', entity: 'order', ids: [...], before: {...}, after: {...} },
    { type: 'move', entity: 'task', id: '123', before: {status:'todo'}, after: {status:'done'} },
  ]

撤销时：
  → 取栈顶操作
  → 调用 API 恢复 before 值
  → invalidateQueries
  → Toast "已撤销"
```

### 限制

- 仅保留当前会话的操作栈（刷新页面清空）
- 超过 5 秒的操作不再支持 Toast 内撤销（但 ⌘Z 仍可用）
- 他人修改了同一记录后，撤销可能触发冲突（走乐观锁流程）


## 六、API 配额与用量展示

### 设计思路

多租户 SaaS 中，不同套餐有不同的资源配额（用户数、存储空间、API 调用量、记录数）。前端需要展示当前用量和剩余配额，接近上限时提醒升级。

### 配额维度

| 维度 | 免费版 | 专业版 | 企业版 |
|------|--------|--------|--------|
| 用户数 | 5 | 50 | 不限 |
| 存储空间 | 1GB | 50GB | 不限 |
| 记录总数 | 10,000 | 500,000 | 不限 |
| API 调用/月 | 10,000 | 1,000,000 | 不限 |
| 自定义实体数 | 3 | 20 | 不限 |
| 自动化规则数 | 5 | 50 | 不限 |

### UI

```text
/workspace/admin/usage → 用量与配额

┌─────────────────────────────────────────────────────┐
│ 当前套餐：专业版          [升级套餐]                  │
├─────────────────────────────────────────────────────┤
│                                                     │
│ 用户数        ████████████████░░░░  42 / 50         │
│ 存储空间      ██████░░░░░░░░░░░░░░  12GB / 50GB    │
│ 记录总数      ████░░░░░░░░░░░░░░░░  89,234 / 500K  │
│ API 调用/月   ██████████░░░░░░░░░░  523K / 1M      │
│ 自定义实体    ████████████████████  18 / 20  ⚠️    │
│                                                     │
│ 计费周期：2026-05-01 至 2026-05-31                  │
│ [查看历史用量] [导出用量报告]                        │
└─────────────────────────────────────────────────────┘
```

### 告警机制

| 用量比例 | 行为 |
|---------|------|
| < 80% | 正常展示（绿色进度条） |
| 80%-95% | 黄色进度条 + 管理员收到提醒 |
| > 95% | 红色进度条 + 顶部横幅警告 |
| 100% | 阻止新增操作 + 强制提示升级 |

### 前端感知

```text
API 响应头携带配额信息：
  X-Quota-Remaining: 477000
  X-Quota-Limit: 1000000
  X-Quota-Reset: 2026-06-01T00:00:00Z

接近上限时前端自动显示提示条：
  "本月 API 调用量已达 95%，请联系管理员升级套餐"
```

### 超限行为

- 记录数超限 → 禁止新建，允许编辑和删除
- 存储超限 → 禁止上传文件，允许其他操作
- 用户数超限 → 禁止邀请新成员
- API 超限 → 返回 429，前端显示"请求过于频繁，请稍后重试"
