## 过程域

整个模型可以分为五个层次

意图与价值层

回答“为什么做”和“什么结果才有价值”。

核心对象包括：

- Problem：要解决的问题；
- Intent：发起人的原始意图；
- ProjectGoal：项目目标；
- Outcome：希望产生的业务结果；
- SuccessMetric：成功指标；
- Constraint：约束；
- NonGoal：明确不做什么；
- Stakeholder：价值相关者；
- Assumption：当前假设。

这一层必须允许从模糊意图逐步澄清，而不是要求用户一开始就填写完整表单。

典型过程：

用户：帮我建设一个企业知识库

AI：
- 这个知识库服务哪些人？
- 主要解决搜索、问答还是知识沉淀？
- 现有资料在哪里？
- 怎样算建设成功？
- 有哪些权限和保密要求？

系统最终形成：
- 问题定义
- 目标
- 范围
- 成功指标
- 风险
- 初始项目章程

AI 在这里承担需求澄清和结构化工作，人类确认价值方向。

项目规范层

回答“这个项目遵循什么规则”。

项目规范不是一份静态说明，而是项目的可执行契约，包括：

- 项目章程；
- 范围基线；
- 业务规则；
- 交付物定义；
- 验收标准；
- 质量标准；
- 角色与责任；
- 权限边界；
- 风险控制要求；
- 成本与预算；
- 决策规则；
- 人工确认点；
- 变更规则；
- 完成定义。

规范应同时具备两种表达：

- 人类可读表达：项目章程、需求、设计和规则文档；
- 系统可执行表达：结构化目标、验收标准、质量门和权限策略。

关键是不能形成两个相互冲突的真理源。建议按事实归属拆分：

┌────────────────────────────────┬────────────────────────────┐
│ 内容                           │ 权威来源                   │
├────────────────────────────────┼────────────────────────────┤
│ 背景、原因、完整语义和设计解释 │ 版本化文档                 │
├────────────────────────────────┼────────────────────────────┤
│ 项目状态、对象关系和责任归属   │ 结构化项目模型             │
├────────────────────────────────┼────────────────────────────┤
│ 验收条件                       │ 结构化 AcceptanceCriterion │
├────────────────────────────────┼────────────────────────────┤
│ 实际检查结果                   │ Evidence                   │
├────────────────────────────────┼────────────────────────────┤
│ 重要取舍                       │ Decision                   │
├────────────────────────────────┼────────────────────────────┤
│ 规范采用版本                   │ ProjectBaselineVersion     │
└────────────────────────────────┴────────────────────────────┘

项目进入正式执行前，应冻结一个 ProjectBaselineVersion。后续变化不能直接覆盖，而要通过变更决策产生新版本。

交付工程层

回答“要产生什么可信结果”。

这是整个模型的中心。

Goal
└─ Deliverable
├─ AcceptanceCriterion
├─ WorkPackage
├─ ArtifactReference
├─ Evidence
└─ Gate

每个交付物必须回答：

- 它为哪个目标服务？
- 具体要交付什么？
- 谁对结果负责？
- 需要什么输入？
- 满足什么标准才算完成？
- 由什么证据证明？
- 有哪些依赖和风险？
- 哪些工作可以由 AI 执行？
- 哪些节点必须由人决策？

项目系统应建立以下强约束：

- 每个交付物必须追溯到目标；
- 每个工作项必须服务于交付物；
- 每个交付物必须有验收标准；
- 每条强制验收标准必须有证据；
- 每次基线变更必须有决策记录；
- 每个高风险动作必须有授权；
- 项目完成必须由交付物和证据推导，不能手工宣布。

这才是“从管人到管交付物”的工程化落地。

工作不应只是任务列表，而应是执行图

复杂事情的难点不是任务多，而是：

- 目标存在不确定性；
- 工作之间有复杂依赖；
- 方案存在多个候选；
- 执行过程中会发现新信息；
- 某些工作适合 AI，某些适合人；
- 风险会动态变化；
- 计划必须不断调整。

因此，核心不是传统 Task List，而是一个 Project Delivery Graph：

Goal
├─ contributesTo ← Deliverable
│                    ├─ dependsOn → Deliverable
│                    ├─ producedBy → WorkPackage
│                    ├─ validatedBy → Evidence
│                    └─ approvedBy → Decision
│
├─ measuredBy → SuccessMetric
└─ threatenedBy → Risk

执行层节点可以是：

- WorkPackage：可独立管理的一组工作；
- WorkItem：具体工作单元；
- Milestone：阶段性控制点；
- DecisionPoint：待决策节点；
- QualityGate：质量门；
- ExecutionRun：一次实际执行；
- Issue：执行中暴露的问题；
- ChangeRequest：对基线的变更请求。

这种图模型的价值是让 AI 能够：

- 自动检查遗漏；
- 发现循环依赖；
- 识别关键路径；
- 判断哪些工作可以并行；
- 分析阻塞传播；
- 发现目标与任务断链；
- 在条件变化时重新规划；
- 汇总真正需要人处理的决策。

这里的图不是为了画漂亮流程图，而是项目系统的可计算结构。

能力编排，而不是固定角色分工

传统项目把工作分给固定岗位：

产品经理 → 设计师 → 开发 → 测试

AI 原生项目应把任务匹配到“能力”：

WorkItem
→ 需要的能力
→ 候选执行者
├─ Human
├─ Agent
├─ Agent Team
├─ Workflow
├─ Tool
└─ External Service

每个执行者应有统一描述：

- 执行者类型；
- 能力；
- 可使用的工具；
- 可访问的上下文；
- 权限；
- 成本；
- 预计耗时；
- 可靠性；
- 当前负载；
- 风险等级限制。

任务分配不应只保存 assigneeId，还要表达：

executorType = HUMAN | AGENT | TEAM | WORKFLOW | SYSTEM
executorRef
requiredCapability
authorizationPolicy
budgetLimit
timeoutPolicy
validationPolicy

AI 可以选择执行者，但选择必须受权限、预算、风险和质量策略控制。

计划应被理解为“可验证假设”

传统项目往往把计划当承诺，导致实际情况变化后仍然维护一个已经失真的甘特图。

AI 原生项目中，计划应该是：

│ 基于当前信息，对实现目标的最佳路径假设。

计划必须具备：

- 版本；
- 假设；
- 输入依据；
- 依赖关系；
- 风险；
- 置信度；
- 预计成本；
- 可替代方案；
- 重规划触发条件。

触发重新规划的事件可以包括：

- 交付物验收失败；
- 关键假设被证伪；
- 工作项连续失败；
- 成本超过阈值；
- 依赖延期；
- 风险等级上升；
- 项目目标或约束变化；
- 新证据显示当前方案不是最优。

AI 可以自动提出重规划方案，但不能静默修改已经确认的项目基线。

建议使用：

当前计划
→ AI 发现偏差
→ 生成 ChangeProposal
→ 评估影响
→ 自动批准或人工决策
→ 产生新 BaselineVersion

项目控制必须从“汇报驱动”转向“事件和证据驱动”

传统项目管理依赖成员汇报：

- 今天做了什么；
- 完成了多少；
- 有什么问题。

AI 原生项目系统可以从真实事件推导状态：

- 文档版本已提交；
- Agent 执行完成；
- 自动化测试通过；
- 内容审核退回；
- 发布渠道返回失败；
- 成本超过预算；
- 依赖交付物变更；
- 验收证据缺失；
- 业务指标达到目标。

系统基于事件更新：

- 工作状态；
- 交付物成熟度；
- 风险；
- 阻塞关系；
- 预算消耗；
- 项目预测；
- 待决策事项。

项目经理和人类不需要阅读所有执行过程，只需要看到：

需要你决策的事项
当前最大的交付风险
缺失的验收证据
偏离基线的地方
预计无法按期完成的交付物
AI 建议的调整方案

进度应拆成三种，不再只有一个百分比

执行进度

工作进行了多少：

WorkItem / WorkPackage 的流转状态

交付进度

交付物距离可验收还有多远：

交付物完备度
验收标准覆盖率
证据完整率
质量门通过情况

价值进度

目标是否真正实现：

成功指标当前值
目标值
价值假设是否得到验证

三者可能完全不同：

执行进度：100%
交付进度：80%
价值进度：20%

这意味着所有工作都做了，但部分结果未验收，且真实价值尚未实现。

质量门是项目工程化的关键

复杂项目不能只依靠最后验收。应在交付链中设置质量门：

定义门
→ 方案门
→ 执行准备门
→ 交付门
→ 发布门
→ 价值验证门

每个质量门包含：

- 进入条件；
- 必需交付物；
- 必需证据；
- 自动检查；
- 风险阈值；
- 审批策略；
- 通过、退回、豁免规则。

不同风险等级使用不同治理力度：

┌──────────────────────────┬─────────────────────────┐
│ 风险                     │ 控制                    │
├──────────────────────────┼─────────────────────────┤
│ 低风险、可逆、可自动验证 │ 自动通过                │
├──────────────────────────┼─────────────────────────┤
│ 中风险、有明确证据       │ AI 审查，必要时人工抽检 │
├──────────────────────────┼─────────────────────────┤
│ 高风险、影响外部或不可逆 │ 人工批准                │
├──────────────────────────┼─────────────────────────┤
│ 低置信度或规范冲突       │ 阻断并转人工            │
└──────────────────────────┴─────────────────────────┘

项目系统应支持四种工程模式

“通用”不意味着所有项目使用同一流程，而是共享稳定内核、选择不同方法策略。

探索型

适合目标或方案不明确的复杂问题。

重点：

- 假设；
- 研究；
- 候选方案；
- 实验；
- 证据；
- 决策。

交付型

适合目标明确、需要形成完整成果的项目。

重点：

- 范围；
- 交付物；
- 依赖；
- 排期；
- 质量门；
- 验收。

生产型

适合结构稳定、可批量重复的项目。

重点：

- 模板；
- 工作流；
- 批量执行；
- 成本；
- 异常；
- 吞吐量。

高保障型

适合安全、权限、合规、生产发布等高风险项目。

重点：

- 规范；
- 审计；
- 职责分离；
- 强制证据；
- 人工审批；
- 回退方案。

项目可以从探索型逐步转为交付型，再将成熟部分转为生产型。

复杂事情如何被项目工程化

例如用户提出：

│ 建立一套企业 AI 获客系统。

系统不应直接创建几十个任务，而应依次进行：

项目框定

AI 澄清：

- 获客对象是谁；
- 当前渠道和基准数据；
- 希望提升什么指标；
- 时间、预算和合规约束；
- 哪些能力已经存在。

项目建模

形成：

Goal：三个月内新增 500 个有效线索
Outcome：线索获取成本降低 20%
Constraints：预算、品牌规范、隐私规则
NonGoals：暂不建设自有 CRM

交付物分解

Deliverable 1：目标客户画像
Deliverable 2：内容生产体系
Deliverable 3：投放与发布工作流
Deliverable 4：线索收集链路
Deliverable 5：数据分析看板
Deliverable 6：运营与优化机制

能力编排

客户画像 → Research Agent + 人工确认
内容生产 → AIGC Project
发布流程 → Workflow
线索收集 → Channel + CRM Adapter
数据分析 → Stats
品牌审核 → Human + Quality Agent

执行与控制

系统持续收集：

- 生成结果；
- 审核记录；
- 发布回执；
- 投放成本；
- 线索数据；
- 转化效果。

动态优化

如果某渠道成本过高，AI 提出：

- 调整内容方向；
- 修改受众；
- 暂停渠道；
- 增加实验；
- 重新分配预算。

人类只需要审批影响较大的调整。

这就是“把复杂事情通过项目工程化解决”，而不只是管理一张任务表。

建议的领域划分

新的项目模块内部可以先按六个稳定领域组织概念：

project/
├─ definition     项目、问题、目标、范围、基线
├─ delivery       交付物、验收标准、产物引用、证据
├─ planning       迭代、工作包、工作项、依赖、里程碑
├─ execution      执行委派、能力匹配、运行引用、事件
├─ governance     风险、问题、决策、变更、质量门
└─ learning       复盘、经验、模板候选、能力沉淀

这里的 execution 不自己实现 Agent、Workflow 或异步任务，只保存项目层面的委派和执行引用，真正执行仍由对应引擎负责。

AI 原生模型的系统不变量

我认为以下规则应该成为后续设计的核心硬约束：

- 每个项目必须有明确的问题或目标；
- 每个目标必须有可验证的结果或指标；
- 每个正式交付物必须关联目标；
- 每个工作项必须关联交付物、风险处理或项目治理活动；
- 每个交付物必须有完成定义；
- 每个强制验收标准必须有证据；
- AI 输出默认是候选，不是正式交付；
- 每次基线变化必须可追溯；
- 每个重要决策必须记录依据和影响；
- 每个执行者必须有明确权限和责任边界；
- 项目状态必须从事实和证据推导；
- 项目结束必须评估价值，而不仅是工作完成；
- 可复用经验必须沉淀为规范、模板、Skill、测试或工作流。

先打通一条“复杂意图到可信交付”的黄金路径：

用户描述复杂事项
→ AI 澄清并形成项目章程
→ AI 生成目标与交付物图
→ 人类确认项目基线
→ AI 拆分工作包并匹配执行能力
→ 人 / Agent / Workflow 执行
→ 系统持续收集产物和证据
→ AI 发现偏差、风险并提出调整
→ 质量门验收交付物
→ 验证业务价值
→ 复盘并沉淀可复用能力
