# 文档引擎设计

## 设计哲学

> 一切皆文档——文档不只是富文本，而是结构化的知识容器，有语义、有关系、有历史、有空间位置。

文档引擎是 AAF 的内容基础设施，承载所有制品的存储、版本、协同、检索。用户编辑的内容、Agent 的执行过程、工作流的定义、组件的元数据，都以文档形式存储，由文档引擎统一管理。

## 文档模型

文档是系统的基本单元，不只是富文本，而是结构化的知识容器：

```
文档（Document）
  ├─ 元数据：标题、标签、空间坐标、时间戳、版本、权限、org_id
  ├─ 内容块：虚拟块（引用 / 嵌入）+ 实体块（文本 / 表格 / 图表 / 代码 / 组件）
  ├─ 视图配置：图层、分页、布局、模式（浏览 / 编辑 / VR / 语音）
  ├─ 插件声明：挂载点 + DSL 定义的业务规则
  └─ 关系：链接、包含、引用（软硬链接）
```

### 文档类型

| 类型     | 说明                                   | 生产者    |
| -------- | -------------------------------------- | --------- |
| 业务文档 | 用户创建的内容（笔记、规范、设计文档） | 用户      |
| DSL 文档 | 工作流、实体、组件定义                 | AI / 用户 |
| 执行文档 | Agent 执行链路、工具调用记录、中间状态 | Agent     |
| 规范文档 | 用户故事、设计方案、验收标准           | AI / 用户 |
| 日志文档 | 审计记录、操作历史                     | 系统      |

所有类型共享同一套文档引擎能力，通过文档类型字段区分处理逻辑。

## 版本控制设计

### 核心问题

AAF 文档的特殊性决定了单一技术无法完整覆盖：

- 结构化块（段落、表格、代码、组件），不是纯文本文件
- 需要实时多人协同（用户 + Agent 同时写入）
- 需要操作级粒度回放（不只是版本快照）
- 需要长期版本管理（标签、分支、历史追溯）

### 三种方案对比

|              | Git                       | OT/CRDT                | 自己设计   |
| ------------ | ------------------------- | ---------------------- | ---------- |
| 实时协同     | ❌ 不支持                  | ✅ 天然支持             | 取决于设计 |
| 操作粒度     | 文件级                    | 操作级                 | 取决于设计 |
| 版本管理     | ✅ 成熟（分支、标签、DAG） | ❌ 需要额外实现         | 取决于设计 |
| 冲突处理     | 需人工解决                | 自动合并               | 取决于设计 |
| 块结构支持   | ❌ 文件系统阻抗不匹配      | ✅ 操作针对块           | ✅          |
| 长期存储成本 | 低（增量存储）            | 高（操作日志无限增长） | 取决于设计 |
| 实现复杂度   | 低（直接用）              | 中（需集成）           | 高         |

**Git 不适合的原因：**
- 操作的是文件系统，AAF 文档是数据库中的块结构，阻抗不匹配
- 没有实时协同能力，需要额外引入 CRDT，两套系统并存复杂度高
- 合并冲突需要人工解决，不适合 Agent 频繁写入的场景

**纯 CRDT 不够的原因：**
- 操作日志无限增长，长期存储成本高
- 没有"版本"概念，需要在上面加快照层
- 历史回溯性能差（需要重放所有操作）

### 建议方案：分层组合

```
协同层（实时）     Yjs（CRDT）
                  多人实时编辑、操作日志、冲突自动合并
                  操作回放天然支持（重放操作序列）

版本层（快照）     自实现（基于 Yjs 快照 API）
                  定期或手动触发快照
                  快照存 PostgreSQL，附带元数据（作者、时间、描述）
                  版本对比基于块级 diff

归档层（长期）     参考 Git DAG 思想，针对块结构自实现
                  重要版本打标签（tag）
                  分支概念用于实验性修改
                  DAG 结构存储版本关系
```

### 技术选型

| 层次                | 技术        | 工作量 | 说明                                         |
| ------------------- | ----------- | ------ | -------------------------------------------- |
| 实时协同 + 操作日志 | Yjs（CRDT） | 低     | 成熟方案，Notion / Linear 在用，有 Java 绑定 |
| 版本快照            | 自实现      | 低     | 基于 Yjs 快照 API，存 PostgreSQL             |
| 版本对比            | 自实现      | 中     | 块级 diff，比文本 diff 更精确                |
| 版本标签 / 分支     | 自实现      | 中     | 参考 Git DAG，针对块结构简化                 |
| Agent 执行文档      | 自实现      | 低     | 结构化存储，不需要 CRDT                      |

### 分层架构

```
用户 / Agent 操作
      ↓
协同层（Yjs）
  - 实时同步操作到所有在线用户
  - 记录操作日志（Op Log）
  - 自动合并冲突
      ↓
版本层
  - 定期快照（每 N 次操作 或 手动触发）
  - 快照 = Yjs 文档状态序列化 + 元数据
  - 块级 diff 生成版本对比视图
      ↓
归档层
  - 重要版本打 tag（发布、里程碑、审核通过）
  - 分支用于实验性修改，合并回主线
  - DAG 结构记录版本关系
      ↓
存储层（PostgreSQL）
  - 快照内容（JSONB）
  - 版本元数据（作者、时间、描述、tag）
  - DAG 边（parent_id → child_id）
  - Op Log 归档（定期压缩）
```

### 操作回放

基于 Yjs 操作日志，支持两种回放模式：

- **完整回放**：从文档创建时刻重放所有操作，还原任意历史状态
- **快照回放**：从最近快照开始，只重放快照后的操作，性能更好

Agent 执行文档的回放：结构化存储每个执行步骤（工具调用入参/出参/耗时），按时间线顺序展示，不依赖 CRDT。

### 版本防抖策略

不是每次编辑都创建版本——通过 Debounce 合并短时间内的多次编辑为一个 Revision：

```text
用户编辑 → 重置 debounce 计时器（默认 5 分钟）
  → 计时器到期 → 创建 Revision 快照
  → 或：用户手动保存 / 关闭文档 / 切换页面 → 立即创建 Revision
```

协作者归属：通过 Redis Set（`collaborators:{docId}`）追踪当前编辑会话的所有参与者，创建 Revision 时将 Set 内容写入 `collaboratorIds` 字段并清空 Set。

### Op Log 压缩策略

Yjs 操作日志无限增长，定期压缩：

```
在线操作（热数据）  → Yjs 内存 + Redis 缓存
  ↓ 定期（每日 / 每次快照后）
Op Log 归档（温数据）→ PostgreSQL 压缩存储
  ↓ 超过保留期（如 90 天）
Op Log 清理（冷数据）→ 只保留快照，删除原始 Op Log
```

快照保留策略：
- 最近 30 天：保留所有快照
- 30-180 天：每周保留一个快照
- 180 天以上：只保留打了 tag 的版本

## 实时协同设计

### 多维度并发

工作区支持四个维度并发，文档引擎负责协同层的隔离：

| 维度   | 隔离边界              | 文档引擎职责                   |
| ------ | --------------------- | ------------------------------ |
| 多端   | 会话状态同步          | 向各端推送 Yjs 更新            |
| 多用户 | 工作区状态共享        | CRDT 自动合并，冲突升级处理    |
| 多助理 | 各 Assistant 会话独立 | 不跨 Session 直接写入          |
| 多对话 | 会话间内容隔离        | 支持显式跨会话引用（只读快照） |

### 冲突处理

- **文档内容冲突**：Yjs CRDT 自动合并，无需人工干预
- **结构冲突**（两人同时删除同一块）：CRDT 按时间戳决策，记录冲突日志
- **语义冲突**（两个 Agent 写入矛盾内容）：升级到置信度门控器，暂停并展示对比卡片

### 在线感知

- 实时显示其他用户的光标位置和选区
- 显示当前文档的在线用户列表
- Agent 写入时显示"AI 正在编辑"状态指示

## 嵌套结构与排序

### 导航树冗余存储

文档通过 `parentDocumentId` 形成树，但递归查询性能差。采用冗余 JSON 树存储在 Collection 级别：

```text
Collection 表
  └── documentStructure: JSONB  → NavigationNode[] 树形结构

NavigationNode {
  id: string          // 文档 ID
  title: string
  index: string       // fractional-index 排序键
  children: NavigationNode[]
}
```

- 侧边栏导航直接读取 JSON 树，零递归查询
- 文档标题变更时通过 BeforeSave hook 同步更新对应节点
- 文档移动/删除时同步更新树结构

### fractional-index 排序

文档和块的拖拽排序使用分数索引（fractional-index），支持任意位置插入而不需要重排所有节点：

```text
文档 A: index = "a0"
文档 B: index = "a1"
文档 C: index = "a2"

在 A 和 B 之间插入 D → D.index = "a0V"（介于 "a0" 和 "a1" 之间）
无需更新 A、B、C 的 index
```

适用场景：文档树排序、看板卡片排序、块级拖拽排序。

## 关系管理

文档之间的关系类型：

| 关系类型        | 说明                          | 示例                   |
| --------------- | ----------------------------- | ---------------------- |
| 链接（Link）    | 软引用，源文档删除不影响目标  | `[[用户管理设计]]`     |
| 包含（Contain） | 父子关系，父删除子跟随        | 工作区包含文档         |
| 引用（Embed）   | 虚拟块，内容同步更新          | 嵌入另一文档的某个块   |
| 派生（Derive）  | 从模板或规范派生              | 代码从 DSL 规范派生    |
| 执行（Execute） | 执行文档关联触发它的任务/对话 | Agent 执行文档关联对话 |

关系存储在 Neo4j，支持图查询（如"找出所有依赖此规范的代码文件"）。

## 全文检索

- **关键词检索**：PostgreSQL 全文索引（tsvector），支持中文分词
- **语义检索**：文档内容向量化，存向量库，支持相似度检索
- **结构检索**：按文档类型、标签、作者、时间范围过滤
- **关系检索**：通过 Neo4j 图查询，按关系类型检索关联文档

## 与其他引擎的关系

```
文档引擎
  ← DSL 引擎：DSL 文档的解析和执行由 DSL 引擎负责，文档引擎只负责存储
  ← 空间引擎：文档的空间坐标由空间引擎管理，文档引擎存储坐标元数据
  ← 权限引擎：文档的访问控制由权限引擎负责，文档引擎在查询时注入权限过滤
  ← 知识库引擎：文档内容向量化后存入知识库引擎，文档引擎触发向量化
  ← 记忆引擎：Agent 执行文档写入后，关键信息提取存入记忆引擎
```
