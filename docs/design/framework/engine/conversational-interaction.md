# 对话式交互设计

## 设计哲学

> 参考 更多参考资料.md中的## 模型部分及当前文档 设计哲学部分 补充。一切皆文档+DSL的模型设计，应用结构设计，不同场景的多端交互示例：任务管理、在线开发

传统界面是预先设计的固定结构，用户适应界面。对话式交互反转这一关系：**界面是对话的投影**，根据意图和上下文动态生成，用户始终处于自然表达状态。

- 多端自适应、界面生成、流式展示
- DSL+文档模型：语义组件、模板、插件、会话... 一切皆文档，通过DSL描述，通过画板渲染文档的（模板（组件插件）与内容），画板本身也是通过文档定义。
- 前端应用结构：交互区(工作区（同时开5个）、助理区、命令区、检索区、属性区、工具箱)
- 一页纸项目管理模板
- 知识地图插件
- 日程管理插件

## 本质模型

一切皆 DSL，一切皆文档、自定义、多视图

```text
用户意图（自然语言 / DSL 指令）
        ↓
   意图理解层（语义解析 + 上下文融合）
        ↓
   DSL 中间表示（结构化意图）
        ↓
   元引擎执行（路由 + 调度 + 状态管理）
        ↓
   界面投影（语义组件动态组装 + 工作区）
        ↓
   用户感知 → 新一轮意图
```

对话是循环，不是线性流程。每一轮输出都是下一轮输入的上下文。

## 一切皆文档 + DSL 的模型设计

> 语义构成知识，知识说明语义，文档承载知识，知识描述文档，画板展示文档，文档定义画板。

系统的核心是一套统一的语义模型，所有制品——界面、工作流、组件、插件、知识、对话——都以文档形式存储，以 DSL 描述，以语义组件呈现。

### 核心关系

```text
语义 ←→ 知识 ←→ 文档 ←→ 画板 ←→ 空间
```

- **语义**：最小单元，构成概念，驱动组件行为和内容理解
- **知识**：信息 + 用户 + 场景目的，存储于知识库，由语义引擎索引
- **文档**：知识的有形载体，记录内容、描述视图、定义交互逻辑和状态
- **画板**：文档的可视化投影，支持多用户 / 多助理实时协作，组件在此组装呈现
- **空间**：画板的容器，带有时间、坐标、权限维度，支持 3D 虚拟空间扩展

### 文档模型

文档是系统的基本单元，不只是富文本，而是结构化的知识容器：

```text
文档
  ├─ 元数据：标题、标签、3D 坐标、时间戳、版本、权限
  ├─ 内容块：虚拟块（引用/嵌入）+ 实体块（文本/表格/图表/代码）
  ├─ 视图配置：图层、分页、布局、模式（浏览/编辑/VR/语音）
  ├─ 插件声明：挂载点 + DSL 定义的业务规则
  └─ 关系：链接、包含、组合、聚合（软硬链接）
```

- **虚拟文档（块）**：引用其他文档的内容，不复制，随源文档更新
- **实体文档**：独立存储，有版本历史，可被多个画板引用
- **模板**：预定义的组件 + 插件 + 内容组合，特定场景的交互规则载体

### DSL 的角色

DSL 是文档与引擎之间的协议，同时面向三类消费者：

| 消费者 | 用途 |
|--------|------|
| 人类 | 直接编写或阅读，表达意图和结构 |
| AI | 生成 DSL 作为执行指令，解析 DSL 理解上下文 |
| 系统 | 前端引擎解析渲染，后端引擎调度执行 |

DSL 描述的内容涵盖：知识格式化、组件定义、插件规则、工作流编排、对话流协议。一个组件本身也是一份文档，通过 DSL 定义其接口、行为和约束。

### 应用模型

```text
空间（Space）
  └─ 工作区（Workspace）          ← 多用户共享，持久化
       ├─ 画板（Board）            ← 文档的可视化容器
       │    ├─ 组件组装            ← 前端引擎按 DSL 动态组装
       │    ├─ 数据绑定            ← 内容注入到组件
       │    └─ 插件增强            ← 按声明挂载插件
       ├─ 助理（Assistant）        ← 会话级，绑定用户
       └─ 我的（Profile）          ← 用户画像、偏好、记忆
```

## 交互空间结构

共享同一套语义组件和 DSL，工作区是对话结果的持久化投影，对话区是意图的实时通道。

一个工作区支持四个维度的并发：

| 维度 | 说明 | 隔离边界 |
|------|------|----------|
| **多端** | 同一用户在桌面、移动、微信、CLI 同时接入 | 会话状态同步，渲染层各自适配 |
| **多用户** | 多个用户共享同一工作区协同编辑 | 用户私有记忆隔离，工作区状态共享 |
| **多助理** | 工作区内同时存在多个 Assistant（如「规划助理」「代码助理」） | 各 Assistant 持有独立会话上下文，通过 Team 层协调 |
| **多对话** | 同一用户可开启多个并行对话会话（如同时讨论两个模块） | 会话间上下文隔离，可显式引用跨会话内容 |

### 工作区状态模型

```text
Workspace（持久化，多用户共享）
  ├─ 文档 / 代码 / 工作流（共享，有版本和权限控制）
  ├─ 在线用户列表（实时同步）
  └─ 会话列表（Session[]）
        ├─ Session A：用户甲 × 规划助理（对话历史 + 工作区快照引用）
        ├─ Session B：用户甲 × 代码助理（独立上下文）
        └─ Session C：用户乙 × 审查助理（独立上下文）
```

- **工作区层**：文档、代码、工作流等制品持久化，多用户实时共享，变更通过 OT/CRDT 合并
- **会话层**：每个 Session 绑定「一个用户 × 一个 Assistant」，上下文独立，生命周期与对话绑定
- **跨会话引用**：用户可在对话中显式引用另一个会话的结论（`@会话B的设计方案`），引用内容只读快照，不合并上下文
- **多用户感知**：工作区实时显示其他用户的光标位置、当前对话的 Assistant 状态，避免操作冲突

### 冲突处理

- **文档冲突**：OT/CRDT 自动合并，无法自动合并时高亮冲突区域，由用户手动选择
- **意图冲突**：两个用户同时向同一 Assistant 发出矛盾指令，Assistant 暂停并在工作区以对比卡片呈现，等待任一用户确认或 Team 层仲裁
- **会话隔离保证**：不同 Session 的 AI 执行互不干扰，共享资源（知识库、工具）通过 Cognition 层统一访问，不直接跨 Session 读写

## 输入层：多模态意图表达

用户表达意图，系统统一解析为 DSL：

| 输入方式 | 示例 | 适用场景 |
|---------|------|---------|
| 自然语言 | "帮我创建一个用户管理模块" | 探索性、模糊需求 |
| DSL 指令 | `/create module user --fields name,email` | 精确操作、开发者 |
| 斜杠命令 | `/workflow` `/agent` `/doc` | 快速触发常用功能 |

## 意图理解层

**上下文融合的语义计算**：

```text
原始输入
  + 当前工作区状态（打开的文档、选中的内容）
  + 会话历史（近 N 轮对话）
  + 用户画像（角色、偏好、历史行为）
  + 系统状态（当前任务、置信度）
        ↓
  意图结构：{ action, target, params, context, confidence }
```

**意图澄清原则**：置信度 < 0.7 时，优先通过最少问题澄清，不猜测执行。澄清本身也是对话，不打断流程。

## 界面生成：语义组件动态组装

界面不是预先设计的，是由**语义组件 + 用户角色 + 场景上下文**在运行时组装的。

**语义组件**是携带语义元数据的 UI 单元：

```text
语义组件 = 视觉呈现 + 交互行为 + 语义描述 + 约束规则
```

- 同一功能，普通用户看到简化对话卡片，开发者看到完整配置面板
- 复杂配置是展开态，不是独立页面
- 工作区组件随对话状态实时更新，无需手动刷新

**前端引擎职责**：后端元引擎输出 DSL，前端引擎负责将 DSL 转化为用户可见的界面，核心流程：

```text
DSL 解析（识别组件类型、属性、布局指令）
    ↓
组件组装（从注册表查找语义组件，按 DSL 结构嵌套组合）
    ↓
内容注入（将后端数据、AI 输出、工作区状态填入组件）
    ↓
插件加载（按 DSL 声明的插件注册点挂载插件，扩展组件行为）
    ↓
交互控制（事件绑定、权限过滤、置信度门控的界面表现）
```

前端引擎不包含业务逻辑，只负责「DSL → 界面」的映射和交互响应，业务逻辑变更只需更新 DSL，前端自动重新组装。

**流式渲染**：后端流式输出 DSL 片段，前端引擎边接收边解析组装，用户无需等待完整响应。

## 前端应用结构设计

前端应用对应应用模型的四个区域，共享同一套语义组件和 DSL：

```text
应用 Shell
  ├─ 工作区（Workspace）
  │    ├─ 画板引擎（Board Engine）
  │    │    ├─ DSL 解析器
  │    │    ├─ 组件注册表
  │    │    ├─ 内容注入层
  │    │    └─ 插件加载器
  │    ├─ 内容编辑器（块编辑 + 内联命令）
  │    └─ 实时协同层（OT/CRDT + 光标共存）
  ├─ 助理区（Assistant Panel）
  │    ├─ 对话流渲染（流式 + 语义卡片）
  │    ├─ 会话列表（多 Session 切换）
  │    └─ 协作可视化（Team/Assistant/Agent 分层展开）
  ├─ 命令区（Command Bar）
  │    ├─ 斜杠命令解析（/ @ # [[）
  │    └─ DSL 输入模式
  └─ 工具筱（Toolbox）
       ├─ 搜索 / 属性面板
       └─ 插件市场（按场景动态加载）
```

### 布局模式

| 场景 | 主布局 | 辅助区域 |
|------|--------|----------|
| 对话优先（移动端） | 助理区全屏 | 工作区折叠展开 |
| 双栏（桌面 Web） | 工作区 + 助理区并列 | 命令区浮层、工具筱右侧 |
| 全屏专注（深度工作） | 工作区全屏 | 助理区浮层小窗口 |

### 状态管理

前端状态分三层，不允许跨层直接读写：

- **全局层**：用户身份、工作区列表、全局主题配置
- **工作区层**：当前文档、画板状态、在线用户、会话列表
- **会话层**：对话历史、当前 Assistant 状态、暂存执行结果

**任务导向流程**：

```text
场景识别（空间 + 人 + 事件 + 当前任务）
    ↓
意图推断（由场景 + 输入推测目的）
    ↓
意图确认（置信度高则跳过，低则澄清）
    ↓
渐进决策（目标 → 规划 → 分解 → 执行 → 检查 → 调整）
    ↓
结果投影（工作区更新 + 对话反馈）
    ↓
状态更新（记忆写入 + 场景刷新）
    ↓
（循环，每轮结果作为下一轮上下文）
```

**场景识别**是对话的起点，三个维度共同构成上下文：

- **空间**：用户当前所在的工作区、文档、模块
- **人**：用户角色、权限、历史偏好
- **事件**：触发本次对话的事件（主动发起 / 系统推送 / 工作流回调）

**渐进决策**是关键：不要求用户一次说清所有需求，系统在执行中逐步细化，每步结果作为下一步输入。目标不清晰不阻塞执行，边走边收敛。

## 主导权与置信度门控

对话中的主导权动态切换：

| 置信度 | 行为 | 界面表现 |
|--------|------|---------|
| > 0.9 | 自动执行，结果暂存 | 进度条 + 异步通知 |
| 0.7–0.9 | 展示执行计划，等待确认 | 确认卡片 + 可编辑参数 |
| < 0.7 | 暂停，说明原因 | 澄清对话 + 建议选项 |

**可撤销原则**：所有执行结果先进入暂存态，用户确认后提交。语义化"撤销"——"把刚才的字段改成 email"而非仅撤回消息。

## 任务路由

意图确认后，系统根据任务特征选择执行路径：

```text
简单查询 / 直接回答  →  Assistant 直接响应
单一操作（CRUD）    →  元引擎直接执行
复杂业务流程        →  工作流引擎（Flowable）
不确定性探索        →  Agent 自主决策
多步骤协作任务      →  多 Agent 编排
```

路由决策对用户透明，但可通过对话区的状态指示器感知当前执行路径。

## AI 主动性

- **上下文感知**：检测工作区变化，主动提示相关操作
- **模式识别**：发现重复操作，建议自动化或系统化
- **提示词协作**：与用户共同迭代优化提示词质量
- **任务预判**：基于历史行为预判下一步，提前准备
- **适时推送**：不等用户触发，在合适时机主动推送提醒、建议、洞察（如「你上周提到要跟进此事」）
- **向用户推荐修改**：AI 可对用户的文档、工作流、提示词提出改进建议，用户确认后生效，记录学习

主动行为遵循**最小干扰原则**：以建议气泡或工作区侧边提示呈现，不打断当前对话流。

## 编辑器内联命令

工作区文档编辑器支持内联命令，与对话区共享同一套意图解析：

| 命令前缀 | 作用 | 示例 |
|---------|------|------|
| `/` | 插入块、触发操作、智能补全 | `/table` `/workflow` `/agent` |
| `@` | 引用用户、触发通知 | `@张三` |
| `#` | 添加标签、关联知识 | `#需求` `#待办` |
| `[[` | 链接文档 | `[[用户管理设计]]` |
| `?` | 行内提问，AI 就地回答 | `? 这个字段的约束是什么` |

内联命令触发后进入意图理解层，结果可就地渲染在文档中，也可同步到对话区。

## 多层智能协作可视化

对应五层智能架构（Team → Assistant → Agent → Core），对话区的可视化随任务复杂度**按需分层展开**，默认折叠，用户主动展开查看细节。

### 分层展示逻辑

```text
【Team 层】  目标对齐 → 任务分发 → 进度同步 → 冲突仲裁        ← 默认可见
    └─ 【Assistant 层】  意图理解 → Agent 调度 → 反馈整合      ← 点击展开
           └─ 【Agent 层】  感知 → 规划 → 执行 → 评估          ← 再次展开
                  └─ 【工具调用】  工具名 / 入参 / 出参 / 耗时  ← 最细粒度
```

- **Team 层**（项目级）：展示参与协作的 Assistant 列表、整体目标、当前进度、仲裁结果；用户在此层确认目标或介入仲裁
- **Assistant 层**（会话级）：每个 Assistant 有独立角色标识（头像 + 颜色 + 角色名，如「规划助理」「代码助理」「审查助理」），展示其当前调度的 Agent 和会话状态
- **Agent 层**（任务级）：展示单个 Agent 的认知循环进度（感知 → 规划 → 执行 → 评估），以及子任务分解列表（「正在检索知识库… 已生成实体定义… 正在生成 Service 层…」）
- **工具调用层**：最细粒度，展示具体工具名、入参、出参、耗时，供调试和审计

### 协作状态呈现

- **进度流**：实时流式更新各层状态，关键节点（任务完成、等待确认、异常）以醒目标记区分
- **冲突协商**：当两个 Assistant 建议矛盾时，以对比卡片呈现两方方案，由用户或 Team 层仲裁；仲裁结果记录到协作日志
- **置信度指示**：每个 Agent 的执行步骤附带置信度标记，低置信度步骤高亮提示，触发人工确认点
- **主导权标识**：当前主导层（人类 / Assistant / Agent / 系统）在状态栏实时显示，主导权切换时记录日志

### 机器可读模式

当调用方是另一个 AI（Assistant 间或 Agent 间通信）时，界面切换为**机器可读模式**：移除视觉装饰，输出语义化结构（DSL / JSON），支持函数调用式操作，保证层间协作的精确性。人类用户重新介入时自动恢复可视化模式。

## 异常接管

当执行遇到异常（置信度跌破阈值、沙箱告警、规范冲突），对话区的处理流程：

```text
1. 立即暂停当前执行，保存执行现场快照
2. 在对话区以醒目卡片说明：发生了什么 / 为什么暂停
3. 提供建议选项（继续 / 修改参数重试 / 回滚 / 人工处理）
4. 等待用户决策，不超时自动执行
5. 用户决策后恢复执行或回滚，记录本次异常到日志
```

异常卡片是对话的一部分，不是弹窗打断——用户可以在对话中直接回复「回滚」或「继续」。

## 多端适配

同一套语义组件和 DSL，在不同端呈现最优交互形式：

| 端 | 主要交互方式 | 界面特征 | 多用户协作支持 |
|----|------------|---------|---------------|
| 桌面 Web | 对话 + 工作区双栏 | 多面板、键盘快捷键、拖拽 | 实时光标共存、内联评论、冲突高亮 |
| 移动端 | 对话优先 | 大按钮、流式滚动、语音输入 | 查看共享工作区，不支持实时协同编辑 |
| 微信 | 消息 + 卡片 | 轻量卡片、快捷回复 | 单用户，工作区快照可分享 |
| CLI | DSL 指令 | 纯文本、管道操作 | 单用户，适合自动化脚本 |

多端共享同一套 DSL 定义，适配层只负责渲染差异，不重复业务逻辑。同一用户在不同端的会话状态实时同步，工作区内容各端一致。

## 安全与可控

- **操作预览**：执行前展示「我将执行以下操作...」，用户可修改或取消
- **权限显式授权**：首次访问敏感资源时明确提示，不静默获取
- **输出溯源**：每条 AI 输出携带生成链路 ID，可追溯到具体 Agent、工具调用、知识来源
- **不可逆操作保护**：删除、发布、提交等操作强制二次确认，不受置信度门控影响
- **幻觉抑制**：用户可开启「只回答确定的事实」模式，AI 对不确定内容明确标注而非猜测生成

## 设计可行性分析

### 已有成熟参照

- **对话 + 工作区双栏**：Cursor、Claude Artifacts、Notion AI 均已验证此模式可行，用户接受度高
- **流式渲染**：AG-UI、A2UI 协议已定义标准，Spring AI 支持 SSE 流式输出，前端渐进渲染技术成熟
- **语义组件动态组装**：Components 成熟，基于 DSL 驱动渲染在低代码平台中已有实践
- **多用户实时协作**：Notion、Figma 已验证 OT/CRDT 合并策略可行，光标共存、实时感知是成熟模式
- **多对话并行管理**：Cursor 多标签页对话、ChatGPT 会话列表均已验证用户需要并行管理多个不同主题的对话

### 主要挑战

- **意图理解准确率**：自然语言到 DSL 的转化在模糊需求下容易出错。缓解策略：置信度门控 + 澄清对话，宁可多问一句，不猜测执行
- **多层协作可视化复杂度**：默认只展示 Team 层进度，用户主动展开 Assistant / Agent 细节；简单任务不启用 Team 层
- **多用户意图冲突**：多用户同时操作同一工作区时可能发出矛盾指令。缓解策略：工作区实时展示其他用户的 Assistant 状态，冲突时以对比卡片呈现等待仲裁
- **多对话上下文切换成本**：并行会话过多时用户切换成本高。缓解策略：会话列表显示每个 Session 的摘要和状态，快速定位当前关注点
- **流式渲染与状态一致性**：组件边渲染边更新可能导致界面抖动。缓解策略：关键状态变更批量提交，非关键更新节流渲染
- **多端 DSL 一致性**：同一 DSL 在不同端渲染结果差异。缓解策略：适配层只处理渲染差异，DSL 语义不变

## 与元引擎的关系

元引擎是一个**前后端一体的整体**，不是单纯的后端服务：

```text
┌─────────────────────────────────────────────────┐
│                    元引擎                         │
│                                                  │
│  后端引擎                    前端引擎              │
│  ─────────────────          ────────────────     │
│  意图理解 / DSL 生成          DSL 解析             │
│  Agent 调度 / 工作流          组件组装             │
│  状态管理 / 记忆读写          内容注入             │
│  工具执行 / 知识检索          插件加载             │
│  元数据管理（模块/插件/工具）  交互控制             │
│                                                  │
│         ←────── DSL / 流式输出 ──────→            │
└─────────────────────────────────────────────────┘
```

- **后端引擎**：理解意图、生成 DSL、调度执行、管理状态，是「大脑」
- **前端引擎**：解析 DSL、组装组件、注入内容、加载插件、控制交互，是「手脚」
- **分工边界**：业务逻辑和 AI 推理在后端，渲染和交互响应在前端；两者通过 DSL 解耦，后端变更不需要前端改代码，前端换渲染方案不影响后端逻辑

对话式交互是元引擎的**输入端和输出端**：

- 输入：用户意图（自然语言 / DSL）→ 后端引擎解析执行
- 输出：后端引擎生成 DSL → 前端引擎渲染 → 对话反馈 + 工作区更新

## 与整体架构的兼容性

### 对应五层智能架构的位置

对话式交互运行在 **Assistant 层（Layer 3）**，不直接触达 Agent 层：

对话区的消息流对应 Assistant 的认知循环：意图理解 → 上下文构建 → Agent 调度 → 反馈整合 → 记忆更新。用户感知到的是连续对话，底层是 Assistant 驱动多个无状态 Agent 完成任务后汇总；当多个 Assistant 组成 Team 时，对话区展示多层协作可视化界面。

### 三层上下文在意图理解中的边界

| 来源 | 类型 | 生命周期 | 在意图理解中的作用 |
|------|------|---------|------------------|
| 上下文（Context） | 临时 KV | 会话级 | 近 N 轮对话、当前工作区状态 |
| 记忆库（Memory） | 动态、个体 | 用户/Agent 私有 | 用户偏好、历史行为模式 |
| 知识库（Knowledge） | 静态、领域 | 全局共享 | 领域规范、约束规则 |

意图理解层只读取，不写入。写入操作在对话流程结束后由 Cognition 层统一处理。

### 规范与界面同步

对话产生的规范文档（用户故事、设计文档）写入 `docs/prd/` 后，元引擎检测到规范变更，自动触发语义组件元数据更新，工作区界面随之刷新。

语义组件的元数据不只是 UI 组件定义，还包括：

- **模块元数据**：模块名称、边界、依赖关系、暴露的能力接口
- **插件元数据**：插件类型、注册点、输入输出契约、版本约束
- **工具元数据**：工具名、参数 schema、权限要求、调用方式
- **UI 组件元数据**：组件类型、交互行为、约束规则、适用角色

规范变更 → 元引擎更新对应元数据 → 工作区界面、对话区可用能力、Agent 可调用工具同步刷新，保证「规范是人机共同语言」在运行时始终成立。

### 防退化约束

- **人类未响应不自动超时执行**：等待人工确认时，系统保持等待态，不因超时降级为自动执行
- **主导权切换必须记录日志**：每次切换记录到审计日志，支持事后复查和规范改进，不允许静默切换

### 安全原则层级在对话层的体现

对话层受三层原则约束，从外到内依次收紧：

```text
系统级原则（不可变）：内容安全审查、注入防护、数据隐私
  └─ 助理级原则（可定制）：角色人格、回答风格、领域约束
       └─ 任务级原则（临时）：单次对话的特殊约束
            └─ 对话执行（受所有层约束）
```

输入净化和意图一致性校验在进入意图理解层之前完成，不在对话流程内部处理。

### 对应核心 KPI

| 指标 | 目标值 | 对话层的责任 |
|------|--------|-------------|
| 对话响应时间 | < 2s | 流式渲染首字符 < 500ms，完整响应 < 2s |
| 意图识别准确率 | > 90% | 置信度门控兜底，< 0.7 触发澄清而非猜测执行 |
| 用户满意度 | > 4.5/5 | 主动性、可撤销、透明度是核心影响因子 |

## 多端交互场景示例

### 场景一：任务管理

**桌面 Web**（主场景）：

```text
用户：“帮我整理一下本周的任务”
  ↓ 助理区流式输出
助理：检索记忆库中本周任务...
     发现 3 个进行中、2 个逾期、1 个新增
  ↓ 工作区同步更新
工作区：生成任务看板语义组件，展示分组卡片
     逾期任务高亮标记，提供「延期 / 删除 / 转交」快捷操作
用户：点击「延期」→ 内联日期选择器弹出，确认后写入记忆库
```

**微信**（轻量接入）：

```text
用户发送：“今天要做什么”
助理回复卡片：
  「今日任务 (3)」
  • 完成需求评审 — 待处理
  • 更新设计文档 — 进行中
  • 提交代码 PR — 逾期 ⚠️
  [查看详情] [处理逾期]
```

**CLI**（自动化脚本）：

```bash
# 查询本周任务
aaf task list --week --status=overdue
# 批量延期
aaf task update --ids=T001,T002 --due=+3d
```

### 场景二：在线开发

**桌面 Web**（主场景）：

```text
用户：“帮我创建用户管理模块”
  ↓ 任务路由：多步骤协作任务 → Team 层启动
助理区展示 Team 层进度：
  「规划助理」 ✔ 已完成需求分析

  User.java 语义组件渐进出现，内容流式填入
  完成后展示「确认提交 / 修改」操作卡
用户展开「代码助理」查看 Agent 层细节：
  Agent: 感知→规划→执行
  工具调用: knowledge_search(“用户管理”) → 200ms
  工具调用: code_generate(“User.java”) → 1.2s
```

**移动端**（审批场景）：

```text
工作区推送通知：“代码助理已完成 User 模块生成，等待审查”

用户回复：“确认提交” → 助理写入工作区，同步到桌面端
```

```text
用户甲（桌面）：对话中要求修改字段类型
用户乙（桌面）：同时向同一助理要求保持原字段
  ↓ 意图冲突检测
工作区展示对比卡片：
  用户甲方案： email: String
  用户乙方案： email: Email（自定义类型）
  [选用甲方案] [选用乙方案] [人工合并]
```
