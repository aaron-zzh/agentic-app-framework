# 元引擎设计

> 元引擎不是又一个引擎，它是引擎的引擎——将意图转化为执行，将执行转化为知识。

## 设计哲学

元引擎破局：**开发即运行，运行即开发**，**一切皆文档，文档即程序**。

## 本质定位

```text
元引擎 = 统一执行环境（开发时 + 运行时）
       + DSL 解释器（意图 → 执行）
       + 引擎编排层（工作流 / 智能体 / 知识库 / 记忆）
       + 自进化机制（行为 → 评估 → 规范更新 → 重生成）
```

元引擎不替代工作流引擎、智能体引擎、知识库引擎——它**编排**这些引擎，为它们提供统一的执行上下文和生命周期管理。

## 整体架构

**前后端一体的整体**：

```text
┌─────────────────────────────────────────────────────────────────┐
│  输入层                                                           │
│  对话意图（自然语言）/ DSL 指令 / API 调用 / 事件触发              │
└──────────────────────────┬──────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────────┐
│  DSL 层（统一中间表示）                                            │
│  意图解析 → DSL 生成 → DSL 校验 → DSL 版本管理                    │
└──────────┬───────────────────────────────────┬──────────────────┘
           ↓ 后端执行                           ↓ 前端渲染
┌──────────────────────┐           ┌───────────────────────────┐
│  后端引擎             │           │  前端引擎                  │
│  ──────────────────  │           │  ─────────────────────    │
│  执行调度器           │           │  DSL 解析器               │
│  状态管理器           │  ←─DSL──→ │  组件渲染器                │
│  置信度门控器         │  ←─事件─→  │  内容注入层               │
│  引擎编排层           │           │  插件加载器                │
│  元数据管理器         │           │  交互控制器                │
│  自进化层             │           │  实时协同层                │
└──────────────────────┘           └───────────────────────────┘
```

- **后端引擎**：理解意图、生成/解析 DSL、**组装组件树**、调度执行、管理状态——「大脑」
- **前端引擎**：生成/解析 DSL、**渲染组件**、注入内容、加载插件、控制交互——「手脚」
- **分工边界**：后端生成组件树 DSL（AI 意图 → 结构），前端生成交互 DSL（用户操作 → 意图上传）；后端解析 DSL 用于执行调度和规范校验，前端解析 DSL 用于渲染和交互绑定。「组装什么组件」是语义计算在后端，「把组件树画出来」是渲染在前端

## DSL 层：统一中间表示

DSL 是元引擎的核心语言，贯穿开发时和运行时。

多范式，解决怎么写，同一内容可以用声明式/命令式/函数式/自然语言混合表达
分层，解决精确度， L1 宽松给用户，L2 结构化给 AI，L3 严格给系统执行
分域，解决是什么，dev/runtime/doc 区分内容的职责归属和生命周期

### DSL 的三重身份

| 身份     | 面向对象 | 作用                               |
| -------- | -------- | ---------------------------------- |
| 规范文档 | 人类     | 描述业务逻辑、界面结构、工作流定义 |
| 生成目标 | AI       | LLM 将自然语言意图转化为 DSL       |
| 执行程序 | 系统     | 元引擎直接解析 DSL 驱动执行        |

### DSL 多范式设计

DSL 采用**多范式**设计，不强制单一语法风格，元引擎统一解析并转化为内部表示：

| 范式                    | 适用场景                       | 示例                                                |
| ----------------------- | ------------------------------ | --------------------------------------------------- |
| **声明式**              | 界面结构、实体定义、配置描述   | `component: TaskCard { fields: [...] }`             |
| **命令式**              | 用户操作、快捷指令、脚本自动化 | `/create module user --fields name,email`           |
| **函数式**              | 工作流节点、数据转换、条件过滤 | `filter(tasks, t => t.status == 'open')`            |
| **自然语言 + DSL 混合** | 模糊意图、探索性输入、快速表达 | `帮我创建用户模块，字段是 name:String, email:Email` |

### DSL 分层设计

DSL 分三层，对外暴露简单灵活的表达，对内维护规范严格的执行表示：

```text
L1  用户层 DSL（宽松、多范式、可不精确）
    用户手写 / 对话输入 / 前端操作序列化
    容许：缺字段、模糊语义、自然语言混入、多范式混写
      ↓ 引擎解析 + AI 补全 + 规范推断

L2  AI / 协作层 DSL（结构化、语义明确、可读可生成）
    AI 生成 / 人工精确编写 / 元引擎中间表示
    要求：语义完整、字段明确、可被校验、人类可读
      ↓ 编译 / 转换

L3  系统执行层 DSL（严格、标准、机器可直接执行）
    元引擎内部 IR，不对外暴露
    要求：类型完备、无歧义、可直接路由到对应引擎执行
```

**层间转化责任在元引擎（系统 + AI 协作完成）**，不在用户：

- 系统负责：范式识别、语法解析、DSL 片段提取、L2 → L3 编译（规则确定，不需要 AI）
- AI 负责：自然语言理解、缺失字段补全、模糊语义推断、规范匹配（不确定性部分）

```text
L1 输入（任意范式 / 模糊表达）
  ↓ 范式识别 + AI 补全缺失字段 + 规范推断
  ↓ 置信度评估（模糊则低置信度，触发澄清）
L2 结构化 DSL（语义校验 + 规范一致性检查）
  ↓ 置信度门控（高→自动，中→确认，低→人工）
L3 执行层 IR（路由到对应引擎执行）
```

**分层的核心价值**：用户层降低表达门槛，系统层保证执行精确性，中间层是 AI 和人类协作的共同语言。同一层内支持多范式混写，不强制统一语法风格。
**多范式的核心价值**：**降低表达门槛**——普通用户用自然语言，开发者用命令式，工作流用声明式，脚本用函数式，同一引擎处理全部。

**元引擎统一处理原则**：输入不需要精确符合某一范式，引擎内部按以下顺序处理：

```text
输入（任意范式 / 混合表达）
  ↓
范式识别（声明式 / 命令式 / 函数式 / 自然语言）
  ↓
归一化为 L2 结构化 DSL
  ↓
语义校验 + 规范一致性检查
  ↓
置信度评估（模糊输入则低置信度，触发澄清）
  ↓
编译为 L3 执行层 IR，路由到对应引擎执行
```

**DSL 域结构:**

```text
L1 高层域（对用户和 AI 可见，按生命周期）
├── dev       开发域：定义系统「是什么」
├── runtime   运行时域：描述系统「怎么跑」
└── doc       文档域：一切皆文档，人机交互的呈现载体

L2 子域（引擎内部路由，按内容类型）
├── dev 开发域，生产规范文档、模型文档、接口文档
│   ├── schema    业务实体、数据模型、字段约束
│   ├── api       接口定义、请求响应契约
│   ├── spec      验收标准、关联关系、状态标记
│   └── flow      工作流定义、节点、条件
├── runtime 运行时域，驱动文档的执行和演化
│   ├── flow      工作流执行、自动化触发、事件管道
│   ├── agent     智能体配置、角色、工具、记忆策略
│   └── policy    权限规则、访问控制
└── doc 文档域，文档的呈现、交互、样式、结构
    ├── content   文档结构、块类型、层级关系
    ├── layout    组件组装、语义布局规则
    ├── style     设计 token、主题、视觉变量
    └── behavior  交互行为、事件绑定、状态转换

```

```text
一段 DSL 输入
  ├── 属于哪个域？       → 分域（dev / runtime / doc）
  ├── 在哪一层？         → 分层（L1 用户 / L2 AI协作 / L3 执行）
  └── 用什么范式写的？   → 多范式（声明式 / 命令式 / 函数式 / 混合）
```

**示例:**

```text
「帮我创建用户模块，字段是 name:String, email:Email」

域：    dev 域（在定义系统是什么）
层：    L1（自然语言混合 DSL，宽松输入）
范式：  自然语言 + DSL 混合

引擎处理：
  识别域 → dev
  识别层 → L1，触发 L1→L2 转化（系统+AI协作补全）
  识别范式 → 混合，拆分自然语言部分和 DSL 片段分别处理
  归一化为 L2 dev/schema 结构化 DSL
  编译为 L3 执行 IR
```

### DSL 覆盖范围

```text
dev 域（定义系统「是什么」，生产规范文档）
  - 业务实体定义（数据模型、字段约束）
  - API 接口定义（请求响应契约）
  - 工作流定义（流程、节点、条件）
  - 规范元数据（验收标准、关联关系、状态标记、任务绑定）

runtime 域（描述系统「怎么跑」，驱动文档执行和演化）
  - 工作流执行（自动化触发、事件管道）
  - 智能体配置（角色、工具、记忆策略）
  - 权限规则（访问控制、数据隔离）

doc 域（一切皆文档，文档的呈现、交互、结构）
  - 文档结构（块类型、层级、关系）
  - 内容格式（富文本、表格、代码、图表）
  - 界面布局（语义组件组装规则）
  - 样式与主题（设计 token、视图模式）
  - 交互行为（事件绑定、状态转换）
  - 模板定义（组件 + 内容 + 交互规则的跨域组合快照）
```

### DSL 生命周期

```text
意图输入（任意范式）
  ↓ AI 生成 / 用户编写 / 前端操作序列化
DSL 草稿
  ↓ 语法校验 + 语义校验 + 规范一致性检查
DSL 验证版
  ↓ 置信度门控（高→自动执行，中→确认，低→人工）
DSL 执行版
  ↓ 元引擎解析执行
运行时状态
  ↓ 效果评估
DSL 迭代版（自进化）
```

## 元引擎核心

### 执行调度器

执行调度器是元引擎的中枢，负责将 DSL 路由到对应的专项引擎：

```text
DSL 解析
  ↓
域识别（dev / runtime / doc）
  ↓
任务类型识别
  ├── dev 域    → 规范驱动开发流程
  ├── runtime 域 → 工作流 / 智能体 / 权限引擎
  └── doc 域    → 文档引擎 / 前端渲染管道
```

**关键设计**：调度器不包含业务逻辑，只做路由和生命周期管理。业务逻辑在 DSL 中，执行逻辑在各专项引擎中。

**Agent 启用判断**（在路由到智能体引擎前，先做四维评估）：

| 维度           | 判断         | 结论                        |
| -------------- | ------------ | --------------------------- |
| 任务复杂度     | 低           | 走工作流，不启用 Agent      |
| 任务价值       | 低（< 阈值） | 走工作流，不启用 Agent      |
| 所有步骤可执行 | 否           | 缩小范围或加人工节点        |
| 错误成本       | 高           | 启用 Agent 但加人工审核节点 |

四维均满足才启用 Agent 自主决策，否则降级到工作流或直接执行。

### 状态管理器

元引擎维护四层状态，严格隔离，支持工作区多维并发：

```text
会话状态（Session）      临时，会话结束销毁
  - 当前对话上下文
  - 执行中的任务列表
  - 暂存的执行结果

工作区状态（Workspace）  持久，多用户共享
  - 文档 / 代码 / 工作流（OT/CRDT 合并）
  - 在线用户列表（实时同步）
  - 会话列表（Session[]，每个绑定「用户 × Assistant」）
  - 组件布局状态

系统状态（System）       持久，全局共享
  - DSL 版本库
  - 规范文档
  - 知识库索引

元数据状态（Metadata）   持久，规范驱动更新
  - 模块元数据（边界、依赖、能力接口）
  - 插件元数据（注册点、契约、版本约束）
  - 工具元数据（参数 schema、权限、调用方式）
  - UI 组件元数据（类型、行为、约束、适用角色）
```

工作区状态支持四个维度并发，状态管理器负责隔离边界：

| 维度   | 隔离边界                         | 状态管理器责任                     |
| ------ | -------------------------------- | ---------------------------------- |
| 多端   | 会话状态同步，渲染层各自适配     | 向各端推送会话快照                 |
| 多用户 | 用户私有记忆隔离，工作区状态共享 | OT/CRDT 合并，冲突升级处理         |
| 多助理 | 各 Assistant 会话上下文独立      | Team 层协调，不跨 Session 直接读写 |
| 多对话 | 会话间上下文隔离                 | 支持显式跨会话引用（只读快照）     |

状态变更遵循**渐进提交**原则：执行结果先写入会话状态（暂存），用户确认后提升到工作区状态或系统状态。

### 文档引擎

文档引擎是元引擎支撑「一切皆文档」的核心模块，负责文档全生命周期管理：

```text
文档引擎职责：
  ├─ 文档 CRUD：创建、读取、更新、删除（软删除）
  ├─ 版本管理：快照、历史、回滚
  ├─ 关系管理：链接、包含、引用（虚拟块 → 实体文档）
  ├─ 权限控制：空间级 / 文档级 / 块级权限
  ├─ 全文检索：语义检索 + 关键词检索
  └─ 实时协同：多用户共同编辑，OT/CRDT 合并
```

系统内所有制品均以文档形式存储，文档引擎统一管理：

| 文档类型 | 所属域        | 存储内容               | 元引擎如何使用             |
| -------- | ------------- | ---------------------- | -------------------------- |
| 规范文档 | dev           | 用户故事、设计方案     | 触发元数据更新和代码重生成 |
| DSL 文档 | dev / runtime | 工作流、实体、组件定义 | 直接解析执行               |
| 组件文档 | doc           | 语义组件定义和元数据   | 前端引擎加载渲染           |
| 插件文档 | doc           | 插件定义、注册点、契约 | 前端引擎动态加载           |
| 业务文档 | doc           | 用户创建的内容         | 工作区渲染展示             |
| 日志文档 | runtime       | 执行日志、审计记录     | 自进化评估输入             |

### 元数据管理器

元数据管理器统一管理四类元数据，规范变更时自动触发同步：

```text
规范变更（docs/requirements/ 写入）
  ↓ 元引擎检测
元数据管理器更新对应元数据
  ├─ 模块元数据：边界、依赖、能力接口
  ├─ 插件元数据：注册点、契约、版本约束
  ├─ 工具元数据：参数 schema、权限要求、调用方式
  └─ UI 组件元数据：类型、行为、约束、适用角色
  ↓ 同步刷新
工作区界面 + 对话区可用能力 + Agent 可调用工具
```

元数据管理器还负责语义漂移检测：工具行为与文档描述不一致时触发告警并暂停该工具，不依赖开发者自觉遵守。

### 置信度门控器

置信度门控是元引擎的安全阀，贯穿所有执行路径：

```text
每个执行步骤携带置信度评分
  > 0.9  →  自动执行，异步通知
  0.7–0.9 →  生成执行计划，等待用户确认
  < 0.7  →  暂停，说明原因，转人工处理

不可逆操作（删除、发布、提交）：
  无论置信度，强制人工确认
```

置信度来源：意图理解置信度 × 规范匹配置信度 × 历史成功率。

### 响应式执行模型

元引擎内部采用**响应式管道**处理执行流，而非同步调用链：

响应式管道    →  Project Reactor
流式输出接口  →  Spring WebFlux SSE
普通接口      →  Spring MVC（后期可迁移到 WebFlux）

```text
输入事件（Event）
  ↓
管道（Pipeline）：一组有序的操作符（Operator）
  ├── 过滤（filter）：不满足条件的事件丢弃
  ├── 转换（transform）：DSL 解析、意图结构化
  ├── 路由（route）：分发到对应引擎
  ├── 并行（parallel）：多子任务并发执行
  └── 聚合（reduce）：汇总子任务结果
  ↓
数据项（Items）：执行结果流
  ↓
输出事件（Event）→ 对话区 / 工作区 / 记忆系统
```

响应式模型的优势：天然支持流式输出、并发子任务、背压控制，与 Spring AI 的 Flux 流式响应对齐。

## 开发时能力


### 自开发设计

> AAF 用自己开发自己——元引擎不只是构建业务系统的工具，它本身也是被自己驱动开发和演化的系统。

**自开发的本质**：AAF 的开发流程和运行时能力共用同一套机制。开发 AAF 引擎本身，和用 AAF 构建业务系统，走的是同一条路径：意图 → 规范 → DSL → 代码生成 → 热部署。这不是巧合，而是设计目标——**系统必须能够驱动自身的开发和演化**。

**为什么这样设计**：

- **验证可行性**：用 AAF 开发 AAF，是对框架能力最真实的压力测试。框架能驱动自身开发，才能真正驱动用户的业务系统
- **消除双重标准**：框架维护者和业务开发者使用同一套工具和流程，规范不会因为"自己用"而降低标准
- **加速自进化**：框架的每次迭代都经过自身的代码生成、沙箱验证、热部署流程，自进化机制在开发阶段就持续运转

**自开发的执行者是 aaf-auto-dev**，它是运行时在线代码生成引擎，不是离线工具：

```text
规范文档（docs/）
  ↓ AI 理解规范，生成 DSL
DSL 定义（dev/schema + dev/api + dev/flow）
  ↓ aaf-auto-dev 解析 DSL
Java 代码（FreeMarker 模板渲染 + JavaParser 精确修改）
  ↓ 沙箱编译验证
热部署（URLClassLoader 热加载，无需重启）
  ↓ 运行时生效，数据采集
自进化评估（下一轮迭代输入）
```

**自开发与自进化的区别**：

| | 自开发 | 自进化 |
|---|---|---|
| 触发方 | 人类（提出需求）或 AI（发现改进点） | 系统（行为数据驱动） |
| 目标 | 实现新功能或改进现有功能 | 优化已有功能的效果和性能 |
| 审核级别 | 按置信度分级，架构变更强制人工 | 同左，引擎级变更强制人工 |
| 产物 | 新代码或修改后的代码 | 规范更新 + 重生成代码 |

两者共享同一套代码生成和热部署基础设施（aaf-auto-dev），区别在于触发来源和审核流程。

元引擎支撑两类开发对象，各自有独立的开发流程和自进化机制。

### 两类开发对象

```text
核心引擎开发    框架维护者开发 AAF 本身
                   需要生成 Java 代码 → 编译 → 部署
                   目标：AI 辅助提效，规范驱动开发

业务系统开发    用户在 AAF 上构建自己的业务
                   目标：以无代码为主，分层递进，配置即运行
```

### 核心引擎开发流程

框架维护者开发 AAF 引擎本身，遵循规范驱动开发流程：

```text
用户描述需求（对话）
  ↓ AI 生成用户故事
规范文档（docs/requirements/）
  ↓ AI 生成设计方案
设计文档（docs/design/）
  ↓ AI 生成 DSL 定义（dev/schema + dev/api + dev/flow）
DSL 规格（数据模型 + 接口 + 约束）

  ↓ 沙箱编译验证 → 热部署

| 置信度        | 场景                | 策略                       |

| 高（>0.9）    | 标准 CRUD、实体定义 | 直接生成并提交             |
| 中（0.7–0.9） | 业务逻辑、API 设计  | 生成后自动测试，通过则提交 |
| 低（<0.7）    | 架构变更、安全相关  | 生成草稿，必须人工审核     |

  ↓ 效果评估（自动 + 人工标注）

  ↓
规范更新建议（人工确认）
  ↓ 元引擎 + auto-dev 重生成受影响模块
  ↓ 沙箱验证 → 热部署
新一轮数据采集
```

### 业务系统开发流程

用户在 AAF 上构建业务，以**无代码为主，分层兴起**，配置即运行对用户透明：

```text
用户自然语言 + DSL 描述需求

```

#### 业务系统分层开发实现方案

业务运行时内置四个层次，按业务复杂度自动选择执行路径：

```text
第一层：实体运行时（无代码）
  基于 dev/schema DSL 动态建表 + 自动生成 CRUD API
  覆盖场景：所有标准实体的增删改查、分页、排序、过滤
  参照：JeecgBoot Online 表单、苋道动态表单（已验证可行）

第二层：工作流运行时（无代码）
  基于 dev/flow DSL 驱动 Flowable 解释执行
  覆盖场景：审批流程、自动化触发、事件管道
  参照：Flowable 本身就是 DSL 解释执行（已验证可行）

第三层：权限运行时（无代码）
  基于 runtime/policy DSL 动态鉴权
  覆盖场景：按角色、按数据、按字段的精细权限控制

第四层：自定义逻辑挂载（AI生成代码）
  用户自然语言描述复杂业务逻辑
  AI 基于当前系统上下文生成实现代码
  用户确认后元引擎后台编译（Javac + 沙箱隔离）
  URLClassLoader 热加载挂载到扩展点，秒级生效
  约束：生成代码只能实现预定义接口，不能访问引擎内部
```

四层覆盖场景占比：

| 层次           | 开发方式 | 场景占比 | 改变生效 |
| -------------- | -------- | -------- | -------- |
| 实体运行时     | 无代码   | ~50%     | 立即     |
| 工作流运行时   | 无代码   | ~20%     | 立即     |
| 权限运行时     | 无代码   | ~10%     | 立即     |
| 自定义逻辑挂载 | 手写代码 | ~20%     | 热部署   |

模式识别（哪些 DSL 模式效果好，哪些需要改进）

## 运行时能力

运行时是元引擎的执行态，负责将开发时定义的 DSL 驱动为实际运行的业务系统。运行时不区分「开发完再部署」和「配即运行」——DSL 变更立即反映到运行时，代码变更热加载后立即生效，开发与运行的边界消失。

### 工作流执行

- Flowable 工作流由 DSL 定义，元引擎负责实例化和生命周期管理
- 工作流节点可嵌入 Agent 任务，实现确定性流程与不确定性任务的混合编排
- 工作流执行状态实时反映到对话区和工作区

### 智能体编排

遵循五层智能架构（详见 [架构思想文档](../../explanation/architecture-thought.md)）：

```text
元引擎作为 Team 层的编排者：
  - 根据任务复杂度决定启用单 Agent 还是多 Agent
  - 管理 Agent 间的通信和任务分配
  - 汇总 Agent 执行结果，决定是否需要人工介入
```

### 知识与记忆集成

元引擎在每次执行前自动组装上下文：

```text
执行前：
  从知识库检索相关规范和领域知识
  从记忆系统加载用户偏好和历史上下文
  组装高质量执行上下文

执行后：
  工具调用结果归档到知识库
  执行日志写入记忆系统
  效果评估触发知识更新
```

### 智能降级策略

元引擎在各专项引擎不可用时自动降级，保证系统持续可用：

```text
AI 服务不可用       →  降级到规则引擎（预定义工作流）
知识检索失败        →  使用默认知识库（内置规范文档）
Agent 超时          →  切换简化流程（直接 LLM 调用）
沙箱执行失败        →  暂停并转人工处理
所有 AI 不可用      →  纯工作流模式，保留核心业务功能
```

降级不静默发生，对话区会明确告知用户当前处于降级模式及原因。

### 运行时沙箱

所有不可信代码在隔离沙箱中执行，防止影响引擎核心，生产环境推荐安装 GraalVM JDK 21 JIT 模式，获得完整沙箱能力，标准 JDK 环境自动降级为子进程隔离方案。

隔离对象：

- 用户自定义工具 / MCP 插件
- 工作流自定义脚本节点
- Agent 工具调用结果处理逻辑

隔离机制（按环境选择）：
  首选：GraalVM Polyglot Sandbox（GraalVM JDK 21）
    - 统一支持 JS / Python / Groovy 等多语言脚本
    - allowAllAccess(false)     禁止访问宿主 JVM
    - allowIO(IOAccess.NONE)    禁止文件 IO
    - allowCreateThread(false)  禁止创建线程
    - allowNet(false)           禁止网络（白名单除外）
    - statementLimit(N)         限制执行语句数，防死循环
    - 每次执行用新 Context，执行完销毁，无状态残留

  降级：子进程隔离 + 超时控制（无 GraalVM 时）
    - 启动独立子进程执行脚本（Python 解释器）
    - 通过 stdin/stdout 传递输入输出
    - 超时强制 kill 子进程
    - 限制：需要宿主机安装对应解释器，进程启动有百毫秒级开销

执行结果：

- 成功 → 结果返回引擎，写入状态
- 失败 → 触发降级策略，记录日志，通知用户

## 自进化机制

自进化是元引擎区别于传统引擎的核心特征，支持两类对象的自进化：
引擎自身和业务系统。两者共享同一套评估和审核框架，但触发条件、
产物和审核级别不同。

### 人类审核分级

所有自进化变更在执行前经过审核分级，不允许绕过：

  自动执行（置信度 > 0.9，低风险）：
    - 业务 DSL 小幅调整（新增字段、修改样式、调整布局）
    - 无副作用的配置变更

  用户确认（置信度 0.7-0.9，中风险）：
    - 业务流程变更
    - 权限规则调整
    - 新增实体或接口

  人工审核（置信度 < 0.7 或高风险）：
    - 引擎模块重生成
    - 架构级变更（模块边界、依赖关系）
    - 安全相关变更
    - 跨模块影响的变更

  硬约束（禁止自动执行，无论置信度）：
    - 引擎核心模块变更
    - 安全相关代码
    - 不可逆操作（删除、清空）

### 引擎自进化闭环

引擎自进化风险高，影响所有用户，全程强制人工审核：

  引擎运行数据（性能指标、错误日志、用户反馈）
    ↓ 效果评估（自动分析 + 人工标注）
  模式识别（哪些模块性能差、哪些规范需要更新）
    ↓
  AI 生成优化方案 + 影响范围分析
    ↓ 强制人工审核（无论置信度）
  规范更新（docs/requirements/ 和 docs/design/）
    ↓ 人工确认规范变更
  auto-dev 重生成受影响模块代码
    ↓ 沙箱编译验证 + 自动化测试
  人工审核代码变更
    ↓ 确认后热部署
  新一轮数据采集

  触发条件：
    - 性能指标持续异常（响应时间、错误率超阈值）
    - 引擎模块规范冲突检测（代码与文档不一致）
    - 新的架构模式被重复提出（N 次以上）

  约束：
    - 每次进化保留完整快照，支持一键回滚
    - 架构级变更必须人工审核，不允许 AI 自行决定
    - 安全相关代码不参与自动重生成

### 业务系统自进化闭环

业务系统自进化风险低，只影响当前业务，按审核分级自动处理：

  用户行为数据（操作日志、满意度、修正操作）
    ↓ 效果评估（自动 + 人工标注）
  模式识别（哪些 DSL 模式效果好，哪些需要改进）
    ↓ 写入历史决策记录（供下次 AI 决策参考）
  AI 生成优化方案（基于当前系统状态 + 历史决策）
    ↓ 审核分级
    ├── 自动执行  → DSL 直接更新，立即生效
    ├── 用户确认  → 对话区展示变更方案，用户确认后生效
    └── 人工审核  → AI 生成代码 → 沙箱验证 → 人工确认 → 热加载
  新一轮数据采集

  触发条件：
    - 用户满意度持续下降（连续 N 次负反馈）
    - 相似需求被重复提出（可系统化的重复模式）
    - 业务 DSL 与实际使用行为出现偏差
    - 用户主动发起优化请求

  约束：
    - 变更范围限定在当前业务，不影响其他业务或引擎
    - 每次变更保留快照，支持回滚
    - 历史决策记录持久化，保证进化方向一致性

## 知识能力一体

知识和能力如时空一体，相互定义、缺一不可——没有能力的知识是死的信息，没有知识的能力是盲目执行。元引擎强制保证知识库与工具系统协同演化，禁止独立迭代导致语义漂移。

### 技能与知识库绑定

每个工具（技能）必须与知识库中的领域文档强绑定：

  工具注册时必须关联：
    - 使用规范文档（什么场景用、怎么用、约束是什么）
    - 示例文档（典型输入输出示例）
    - 领域知识文档（工具所属领域的背景知识）

  运行时强制校验：
    - 知识库更新时，关联工具的调用规范同步校验一致性
    - Agent 调用工具后，执行结果自动归档到对应知识库条目
    - 形成「工具执行 → 知识生长」的正向闭环

  语义漂移检测：
    - 元引擎定期对比工具行为与文档描述的一致性
    - 发现漂移时触发告警并暂停该工具，等待人工修正
    - 不依赖开发者自觉遵守，由引擎在运行时强制执行

### 工具元数据规范

每个工具在注册时必须提供完整元数据，元引擎基于元数据进行
调度、权限控制和语义漂移检测：

  基础元数据：
    - name：工具唯一标识
    - description：语义描述（供 AI 理解何时调用）
    - domain：所属领域（对应 DSL 域：dev / runtime / doc）
    - version：版本号，支持多版本共存

  参数元数据：
    - inputSchema：输入参数 JSON Schema（类型、约束、示例）
    - outputSchema：输出结果 JSON Schema
    - requiredParams：必填参数列表

  权限元数据：
    - requiredPermissions：调用所需权限列表
    - allowedRoles：允许调用的角色
    - dataScope：数据访问范围（用户私有 / 工作区 / 全局）

  执行元数据：
    - timeout：最大执行时长
    - retryPolicy：重试策略（次数、间隔、退避）
    - sandboxRequired：是否需要沙箱隔离
    - costEstimate：预估 Token / 资源消耗

  知识绑定元数据：
    - knowledgeRefs：关联知识库文档 ID 列表
    - exampleRefs：关联示例文档 ID 列表
    - specRef：使用规范文档 ID

## 预算感知

元引擎对每次执行维护资源预算，在任务执行前给出预估，
执行中实时监控，超出阈值时主动介入。

### 执行前预算预估

任务执行前，元引擎基于任务特征给出预算预估，用户确认后再执行：

  预估维度：
    - Token 预算：基于任务复杂度 + 历史同类任务均值估算
    - 时间预算：基于任务步骤数 + 工具调用次数估算
    - 工具调用预算：基于任务分解结果统计工具调用次数
    - 费用预算：Token + 工具调用折算为积分 / 费用

  预估展示（对话区）：
    「本次任务预计消耗：
      Token：约 2000-3000
      时间：约 30-60 秒
      费用：约 0.5-1 积分
      工具调用：约 5-8 次
     是否继续？」

  预估策略：
    - 保守估算（上限 × 1.2），宁可高估不低估
    - 基于历史同类任务数据持续校准，越用越准
    - 简单任务（置信度 > 0.9）可跳过预估直接执行
    - 复杂任务（多 Agent / 多工具）必须展示预估等待确认

### 执行中实时监控

任务执行过程中持续监控预算消耗，动态调整：

  实时监控：
    - 每个工具调用后更新消耗统计
    - 对话区状态栏实时显示当前消耗 vs 预估

  阈值介入：
    - 接近阈值（80%）：对话区提示，询问是否继续或扩大预算
    - 超出阈值（100%）：暂停执行，保存现场，等待用户决策
    - 用户可选择：继续（扩大预算）/ 暂停 / 回滚

### 预算配置

  配置分级：
    - 系统默认值：框架维护者设定的安全上限
    - 用户自定义：用户在设置中配置个人预算上限
    - 单次任务临时覆盖：本次任务特殊指定，不影响默认配置

  预算学习：
    - 记录每次任务的实际消耗 vs 预估偏差
    - 自动校准同类任务的预估模型
    - 用户反馈「预估偏差大」时触发模型更新

## 人类计算支撑

> 核心思想来自 Human Computation：通过设计任务和激励机制，
> 让用户在完成自身目标的过程中，宏观上是在解决一个高价值问题。
> 人既是用户，也是计算节点——单用户看起来是在做自己的事，
> 但从系统视角是在贡献群体智慧、推动系统演化。

元引擎为人类计算提供执行底座，内置积分引擎和结算引擎，
形成可持续的生态激励闭环。

### 贡献行为类型

  知识贡献：
    - 知识标注（为知识库条目打标签、纠错、补充）
    - 规范评审（评审用户故事、设计文档、DSL 定义）
    - 专家知识输入（领域专家贡献专业知识）
    - 知识拆解（将复杂知识拆解为可索引的原子单元）

  计算贡献：
    - 向量计算（本地设备参与知识索引构建）
    - 小模型训练（贡献本地算力参与模型优化）
    - 知识索引分片（分布式知识索引构建）

  协作贡献：
    - 众包任务完成（知识翻译、数据校验、内容生成）
    - 反馈与评分（对 AI 输出质量打分、标注好坏）
    - 游戏化任务（通过游戏形式完成高价值标注任务）

### 积分引擎

积分引擎是人类计算的量化层，将贡献行为转化为可流通的积分：

  积分来源：
    - 贡献行为积分：按贡献类型和质量评分计算
    - 任务完成积分：完成众包任务获得奖励
    - 游戏得分积分：游戏化任务的得分转化
    - 推荐积分：邀请新用户贡献获得分成

  积分质量评估：
    - AI 自动评估贡献质量（准确性、完整性、一致性）
    - 高质量贡献进入知识库，低质量退回重做
    - 多人交叉验证，防止刷分

  积分用途：
    - 兑换服务额度（API 调用次数、存储空间）
    - 解锁功能权限（高级功能、优先队列）
    - 社区排行榜（贡献排名、等级勋章）
    - 参与治理投票（社区决策权重）

  积分规则：
    - 规则以 DSL 定义，存储在 dev/prd 域
    - 规则变更需社区投票确认，不允许单方面修改
    - 所有积分记录链上存储，不可篡改

### 结算引擎

结算引擎基于智能合约保证结算透明可信：

  结算流程：
    贡献行为发生
      ↓ 积分引擎量化评分
    积分写入用户账户（链上记录）
      ↓ 达到结算条件（周期 / 阈值）
    智能合约自动触发结算
      ↓ 验证贡献有效性
    积分兑换为对应权益
      ↓ 结算记录归档
    用户可查询完整结算历史

  结算约束：
    - 智能合约代码开源，规则透明
    - 结算不可逆，归档后不允许修改
    - 争议处理走社区仲裁流程，元引擎提供仲裁工作流

### 元引擎的职责边界

元引擎负责触发和编排，不实现业务逻辑：

  元引擎负责：
    - 贡献行为事件采集（工作流节点触发）
    - 调用积分引擎计算积分
    - 触发结算引擎执行结算
    - 众包任务分发（通过工作流分发给社区用户）
    - 知识质量评估后写入知识库

  积分引擎负责：
    - 积分规则解析和执行
    - 积分账户管理
    - 质量评估和积分计算

  结算引擎负责：
    - 智能合约调用
    - 结算记录管理
    - 争议仲裁工作流

任何角色都可以查看细节，但修改权限严格分级。

默认态（所有用户）：

- 复杂性完全隐藏，只看到结果

- 查看 DSL 定义（只读）
- 查看执行计划和步骤日志（只读）
- 查看工作流 DSL（纯文本 / 可视化切换）
- 查看 AI 推理过程和工具调用记录（只读）
- 查看积分明细和结算记录（只读）

开发态（需要开发者权限）：

- 编辑业务 DSL
- 编写自定义逻辑片段（AI 生成 + 用户确认）
- 配置工作流节点
- 管理自定义工具和插件
- 查看和调试沙箱执行结果

框架维护态（需要框架维护者权限）：

- 修改引擎配置
- 调整路由规则和置信度阈值
- 管理系统级 DSL 规范
- 访问引擎内部状态和性能指标

### 权限分级

查看权限（所有角色）：

- DSL 定义、执行日志、工作流、推理过程
- 目的：透明度，让用户理解系统在做什么

操作权限（按角色分级）：

普通用户：
  ✅ 查看所有细节（只读）
  ✅ 配置个人偏好和助理设置
  ✅ 管理自己的业务文档和数据
  ❌ 编辑 DSL / 修改工作流 / 开发插件

开发者：
  ✅ 普通用户的所有权限
  ✅ 编辑业务 DSL 和工作流
  ✅ 开发自定义工具和插件
  ✅ 调试沙箱执行结果
  ❌ 修改引擎配置 / 调整系统级规范

  ✅ 开发者的所有权限
  ✅ 修改引擎配置和路由规则
  ✅ 管理系统级 DSL 规范
  ✅ 访问引擎内部状态

### 展开原则

- 对话框是默认态，DSL 查看是展开态，DSL 编辑是开发态
- 查看不需要权限，修改需要权限，两者严格分离
- 普通用户查看 DSL / 工作流 / 推理过程，有助于理解和信任系统
- 复杂性展开是渐进的，不强制一次暴露所有细节

## 设计可行性分析

### 已有成熟参照

- **DSL 驱动执行**：Flowable 本身就是 DSL（BPMN XML）驱动的执行引擎，证明 DSL → 执行的路径可行
- **开发运行一体**：代码生成器均验证了「配置即运行」的可行性，元引擎是其泛化
- **响应式管道**：Spring WebFlux + Project Reactor 已是成熟方案，与 Spring AI 的 Flux 流式输出天然对齐
- **多引擎编排**：Agent 框架已支持工具调用和多步骤编排，元引擎在其上加调度层

### 主要挑战

- **DSL 分域扩展**：分域设计天然支持分阶段扩展，各域独立演化不互相阻塞。缓解策略：v1 先实现 dev 域（schema + flow 定义），v2 实现 runtime 域（agent + policy + flow 执行），v3 实现 doc 域（content + layout + style + behavior）
- **开发时与运行时统一**：同一套 DSL 在开发时是规范，在运行时是程序，两种语义可能冲突。缓解策略：DSL 版本化，开发时版本与运行时版本显式区分
- **自进化的可控性**：自动规范更新和代码重生成风险高。缓解策略：规范变更强制人工确认，代码重生成先进沙箱验证，保留完整快照支持回滚
- **预算感知的精确性**：Token 消耗难以精确预估。缓解策略：保守估算 + 实时监控，宁可提前预警不超支

### 最小可行实现路径

两条路径并行推进，传统开发兜底保证可交付，
AI 原生路径逐步替代，后期传统路径逐步退出。

传统开发路径（兜底，后期退出）：

- 手写 Java 代码 + Spring Boot 标准开发模式
- 保证核心功能可交付，不依赖 AI 生成
- 随 AI 原生路径成熟度提升逐步减少占比
- 最终目标：AI 原生路径覆盖 > 90% 场景后退出

AI 原生路径（主线，逐步替代）：

  v1：dev 域（schema + flow 定义）+ 工作流执行 + 基础置信度门控
    核心目标：规范驱动开发跑通，DSL → 代码生成可用
    可交付：实体定义、标准 CRUD、基础工作流

  v2：runtime 域（agent + policy + flow 执行）+ 知识记忆集成 + 响应式管道
    核心目标：智能体编排可用，业务系统无代码层跑通
    可交付：多 Agent 协作、权限动态鉴权、知识检索增强

  v3：doc 域（content + layout + style + behavior）+ 自进化闭环 + 预算感知
    核心目标：全域 DSL 覆盖，自进化机制闭环
    可交付：界面动态生成、业务系统自进化、预算透明

每个版本独立可运行，不为未来版本预留抽象层。
传统路径和 AI 原生路径共享同一套数据模型和接口契约，
切换时不需要迁移数据。

## 与整体架构的兼容性

### 元引擎在五层智能架构中的定位

元引擎不是五层中的某一层，而是**跨层的编排基础设施**：

```text
Layer 4  Team        ← 元引擎提供项目级任务分发和冲突仲裁能力
                        元引擎不是 Team，但为 Team 提供编排基础设施
Layer 3  Assistant   ← 对话式交互运行在此层，元引擎为其提供执行上下文
Layer 2  Agent       ← 元引擎调度无状态 Agent，管理其生命周期
Layer 1  Cognition   ← 元引擎的状态管理器与此层对齐，不跨层直接读写
Layer 0  Core        ← 元引擎通过 Agent 间接调用，不直接操作 LLM
```

**认知循环分层原则的遵守**：元引擎的执行调度器只向下调用（元引擎 → Agent），不允许跨层直接触发（元引擎不直接调用 Core）。Agent 执行结果通过回调返回元引擎，元引擎汇总后再返回对话层。

### 三层上下文的隔离执行

元引擎在每次执行前组装上下文时，严格遵守三层隔离，不允许跨层直接读写：

```text
元引擎执行前组装上下文：
  上下文（Context） ← 会话状态管理器读取，不写入
  记忆库（Memory）  ← 通过 Cognition 层 API 读取，不直接操作存储
  知识库（Knowledge）← 通过知识库引擎 API 检索，不直接操作向量库

DSL 域与上下文的对应关系：
  dev 域 DSL      ← 从系统状态（System）读取规范文档和 DSL 版本库
  runtime 域 DSL  ← 从 Cognition 层读取记忆和知识，组装执行上下文
  doc 域 DSL      ← 从工作区状态（Workspace）读取文档内容和组件布局

元引擎执行后写入：
  执行结果 → 会话状态（暂存）→ 用户确认 → Cognition 层持久化
  工具调用日志 → 异步归档 → 评估后更新知识库
```

### 规范与代码一致性的运行时保证

「文档是唯一真理」原则在元引擎中的具体体现：

```text
定期扫描：对比 docs/prd/ 与 aaf-modules/ 的语义一致性
  ↓ 发现不一致
元引擎触发告警，在对话区提示开发者
  ↓ 开发者确认
以文档为准，生成修正代码的任务
```

这一机制保证代码与规范长期不会漂移，而非依赖人工定期检查。

### 元引擎自身的五度空间约束

元引擎作为核心模块，自身设计也遵守五度空间原则，每个子模块设计及实现复杂度不超过 5，超出则强制递归分解为子模块

```text
元引擎各模块当前复杂度：
  后端核心（5）：执行调度器 / 状态管理器 / 置信度门控器 / 文档引擎 / 元数据管理器
  前端核心（5）：DSL 解析器 / 组件渲染器 / 内容注入层 / 插件加载器 / 交互控制器
  引擎编排（5）：工作流 / 智能体 / 知识库 / 记忆 / 工具
  DSL 层  （2）：解析 / 校验
  自进化层（3）：采集 / 评估 / 重生成
```

后端引擎核心和引擎编排层均已达上限 5，不允许再添加新模块而不分解。

### 安全执行链路的完整约束

元引擎执行链路受三层原则约束，从外到内依次收紧：

```text
用户请求
  ↓ [输入净化 + 注入检测]          ← 系统级原则（不可变）
元引擎 DSL 解析与调度
  ├→ [工具白名单校验] → 沙箱执行   ← 系统级原则
  ├→ [记忆隔离查询]  → 用户私有记忆 ← 系统级原则
  ├→ [知识分级访问]  → 加密知识库   ← 系统级原则
  └→ [模型配额校验]  → LLM 调用    ← 助理级原则（可定制）
  ↓ [输出内容审查 + 溯源标注]       ← 系统级原则
返回对话层
```

### 防退化约束在元引擎层的执行

- **人类未响应不自动超时执行**：置信度门控进入等待态后，元引擎保持等待，不因超时降级为自动执行
- **主导权切换必须记录日志**：每次切换写入审计日志，支持事后复查和规范改进，不允许静默切换
- **AI 不允许静默降低标准执行**：置信度不足时只能上报，不能自行降低置信度阈值绕过门控
