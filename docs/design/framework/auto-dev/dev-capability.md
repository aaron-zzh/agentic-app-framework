# 开发时能力

> AAF 用自己开发自己——元引擎不只是构建业务系统的工具，它本身也是被自己驱动开发和演化的系统。

> **实现态提示**：本文描述目标态设计。沙箱编译、`URLClassLoader` 热加载、动态建表与四层业务运行时的落地进度以 [auto-dev 引擎](auto-dev.md)、[自进化机制](../engine/meta/evolution.md)和代码为准，不得据本文声称已具备相关能力。

## 自开发设计

**自开发的本质**：AAF 的开发流程与运行时能力共用同一套机制。开发 AAF 引擎本身，和用 AAF 构建业务系统，走的是同一条路径：意图 → 规范 → DSL → 代码生成 → 热部署。这不是巧合，而是设计目标——**系统必须能够驱动自身的开发和演化**。

为什么这样设计：

- **验证可行性**：用 AAF 开发 AAF，是对框架能力最真实的压力测试。框架能驱动自身开发，才能真正驱动用户的业务系统
- **消除双重标准**：框架维护者和业务开发者使用同一套工具和流程，规范不会因为“自己用”而降低标准
- **加速自进化**：框架的每次迭代都经过自身的代码生成、沙箱验证、热部署流程，自进化机制在开发阶段就持续运转

自开发的执行者是 `aaf-auto-dev`，它是运行时在线代码生成引擎，不是离线工具：

```text
规范文档（docs/）
  ↓ AI 理解规范，生成 DSL
DSL 定义（dev/schema + dev/api + dev/flow）
  ↓ aaf-auto-dev 解析 DSL
Java 代码（FreeMarker 模板渲染 + JavaParser 精确修改）
  ↓ 沙箱编译验证
热部署（URLClassLoader 热加载，无需重启）
  ↓ 运行时生效，数据采集
自进化评估（下一轮迭代输入）
```

## 自开发与自进化的区别

| | 自开发 | 自进化 |
|---|---|---|
| 触发方 | 人类（提出需求）或 AI（发现改进点） | 系统（行为数据驱动） |
| 目标 | 实现新功能或改进现有功能 | 优化已有功能的效果和性能 |
| 审核级别 | 按置信度分级，架构变更强制人工 | 同左，引擎级变更强制人工 |
| 产物 | 新代码或修改后的代码 | 规范更新 + 重生成代码 |

两者共享同一套代码生成与热部署基础设施（`aaf-auto-dev`），区别只在触发来源和审核流程。

## 两类开发对象

```text
核心引擎开发    框架维护者开发 AAF 本身
                   需要生成 Java 代码 → 编译 → 部署
                   目标：AI 辅助提效，规范驱动开发

业务系统开发    用户在 AAF 上构建自己的业务
                   目标：以无代码为主，分层递进，配置即运行
```

## 核心引擎开发流程

框架维护者开发引擎本身，遵循规范驱动开发流程：

```text
用户描述需求（对话）
  ↓ AI 生成用户故事
规范文档（docs/prd/）
  ↓ AI 生成设计方案
设计文档（docs/design/）
  ↓ AI 生成 DSL 定义（dev/schema + dev/api + dev/flow）
DSL 规格（数据模型 + 接口 + 约束）
  ↓ 元引擎 + auto-dev 生成 Java 代码
业务代码
  ↓ 沙箱编译验证 → 热部署
可运行的引擎模块
```

代码生成策略按置信度分级：

| 置信度 | 场景 | 策略 |
|---|---|---|
| 高（>0.9） | 标准 CRUD、实体定义 | 直接生成并提交 |
| 中（0.7–0.9） | 业务逻辑、API 设计 | 生成后自动测试，通过则提交 |
| 低（<0.7） | 架构变更、安全相关 | 生成草稿，必须人工审核 |

## 业务系统开发流程

用户在 AAF 上构建业务，以**无代码为主、分层递进**，配置即运行对用户透明：

```text
用户自然语言 + DSL 描述需求
  ↓
AI 感知当前系统状态
  （已有 schema / flow / policy / 代码扩展点 / 历史决策）
  ↓
AI 提出实现方案（选择哪层实现、影响范围、风险提示）
  ↓ 置信度门控
用户确认 / 修改 / 拒绝
  ↓
元引擎执行
  ├── 无代码层：DSL 更新，立即生效
  └── 代码层：AI 生成代码 → 热加载，秒级生效
```

### 业务运行时四层

按业务复杂度自动选择执行路径：

| 层次 | 机制 | 覆盖场景 | 开发方式 | 场景占比 | 变更生效 |
|---|---|---|---|---|---|
| 实体运行时 | `dev/schema` DSL 动态建表 + 自动生成 CRUD API | 标准实体增删改查、分页、排序、过滤 | 无代码 | ~50% | 立即 |
| 工作流运行时 | `dev/flow` DSL 驱动 Flowable 解释执行 | 审批流程、自动化触发、事件管道 | 无代码 | ~20% | 立即 |
| 权限运行时 | `runtime/policy` DSL 动态鉴权 | 按角色、按数据、按字段的精细权限 | 无代码 | ~10% | 立即 |
| 自定义逻辑挂载 | AI 生成代码 → 沙箱编译 → 热加载挂载扩展点 | 复杂业务逻辑 | AI 生成代码 | ~20% | 热部署 |

前三层的可行性有成熟参照：动态表单参照 JeecgBoot Online 表单与芋道动态表单，工作流参照 Flowable 本身的 DSL 解释执行。

自定义逻辑挂载的硬约束：生成代码只能实现预定义接口，**不能访问引擎内部**。
