# 架构设计思想

AAF 的本质是构建一个以用户价值为导向的自进化自适应人机协作系统，通过规范驱动开发让人类和AI共享同一套真理来源，实现从意图表达到系统实现的全自动化闭环。不是"AI 帮人写代码"，也不是"人定义规范AI写代码"，而是"人机合作指定规范演化系统"，AI 是协作者。

## 什么是 AI 原生

AI原生开发：人+AI→意图→规范→系统

- AI 参与架构决策（分析规范，建议设计）
- AI 参与代码生命周期（生成、审查、重构、测试）
- AI 参与运行时（Agent 执行、知识检索、记忆管理）
- AI 参与部署与运维（热部署决策、性能异常检测、告警分析）
- AI 参与自进化（行为评估 → 规范更新 → 代码重生成，形成闭环）

**判断标准**：把 AI 拿掉，系统还能正常运转吗？

- 能 → **AI 增强**：在传统应用上叠加 AI 功能（加聊天窗口、加代码生成按钮）
- 不能 → **AI 原生**：AI 是架构的一等公民，不是附加物

## 主要问题

AAF 面对三个核心张力：

- **人 vs AI**：谁主导？谁执行？边界如何动态调整？
- **通用 vs 具体**：框架该管多少？业务该怎么隔离？
- **效率 vs 质量**：快速生成 vs 规范约束，如何兼顾？

围绕这三个张力，形成四个思考框架：

- **复杂性哲学**：本质复杂性保留，技术复杂性封装，交互复杂性规范化
- **边界哲学**：核心封闭稳定，实现开放可扩展，根据用户能力和场景动态调整暴露程度
- **价值体系**：用户价值（解决真实问题）→ 开发者价值（提升效率）→ 生态价值（知识共享）→ 商业价值（可持续）
- **元设计思维**：设计一个能设计系统的系统——规范自我改进，架构自我扩展，生态自我进化
- 如何设计出能自我进化的生态？

## 核心观点

![alt text](../design/framework/core/agent.jpg)

> 理论与实践相结合：价值驱动、元理论、知识框架、五度空间模型、第一性原理

1. **以人为本，化繁为简**：降低熵，优先理解而非生成，极致体验
   - 系统的复杂性对用户不可见——用户感受到的是简单、流畅、个性化；开发者感受到的是高效、可控、低重复。创意和沉浸体验是目标，不是装饰
   - **情感是人机协作的隐性通道**：人类的情绪状态（专注、疲劳、焦虑、愉悦）直接影响认知效率和决策质量。AI 感知情感不是为了"更像人"，而是为了在正确时机提供正确密度的信息——用户疲劳时减少干扰，用户焦虑时更简洁直接，用户探索时更发散开放。忽视情感的系统，即使功能完备，也会在人机协作中产生持续摩擦
2. **规范是人机共同语言**：规范驱动开发先写规范再写代码，让规范成为人类和AI的共同真理来源，也是系统自进化的基础。
3. **知识与能力一体**：知识和能力如时空一体，相互定义、缺一不可。
   - 没有能力的知识是死的信息，没有知识的能力是盲目执行。
   - Agent 的智能本质是两者的融合——知识决定能做什么，能力决定知识如何生长。
   - 系统设计上，知识库与工具系统必须协同演化，而非独立建设。
4. **分工协作，动态主导**，发挥各自专长，人类负责价值判断和创意（什么值得做、对不对），AI 负责理解和生成（意图→规范→代码），系统负责存储和执行（知识库、记忆、工作流、工具调用）。根据任务确定性动态切换主导权，确定性任务走工作流，不确定性任务走 Agent。
   1. 问题解决过程设计应优先系统计算，AI 负责理解和组织，人类按需（价值、不确定性）介入
   2. 关键在于不仅仅是解决问题，而是优先设计/优化系统去解决问题，同时促进人类及AI学习积累知识
5. **对话式交互，自适应界面**，用对话替代复杂菜单，用自适应界面替代固定中台。
   - 界面不是预先设计的，是根据用户意图和场景动态生成的——同一个功能，普通用户看到简单对话框，开发者看到完整配置面板
   - **高带宽协作**：纯聊天是低带宽通道（线性、上下文腐烂、树状决策被压缩为序列），结构化视图是高带宽通道（并行信息、直接操作、空间布局）。AAF 的交互模式是**结构化视图为主、对话为辅**——AI 的输出优先"焊"进文档/表单/看板（高亮修改、内联建议、diff 卡片），对话仅用于意图表达和快速指令。用户在结构化视图中做决策和审查，不在对话中阅读长文本后复制粘贴
6. **分层智能，引擎驱动，渐进决策**：业务不是写出来的，是从核心引擎自动生成的。
   - 群智能（智能体（智能块（智能核） + 人）+ 系统 + 工具
   - 不用传统的管理中台，根据配置及需求通过多端多方式交互（mobile/pc/web/api/cli-exe）
   - 引擎负责通用能力，业务模块负责领域逻辑，两者解耦，各自演化。
   - 人机协作在线开发系统，迭代引擎 + 开发业务 + 积累知识
7. **系统自进化**：用户行为→效果评估→规范更新→代码生成，形成闭环，在使用中自我演化。
8. **极简实现、快速迭代**：每个功能从最小可行实现开始，不追求一次设计完美，而是在真实使用中发现问题、修正规范、重新生成。复杂性是迭代出来的，不是预先设计出来的。
9. **瓶颈迁移，规划审查优先**：AI 使执行近乎免费，规划与审查成为新生产力瓶颈。AAF 的核心价值不是"AI 帮你执行"，而是"AI 帮你规划和审查"。系统设计应优先降低规划和审查的成本——决策日志、异步审查通道、结构化 diff 展示。
10. **可验证性优先**：可验证任务（输出可自动检查正确性）优先被 AI 攻克，难验证任务（需人类判断）进展缓慢。任务拆分时应显式按可验证性降维——将模糊任务拆解为可自动验证的子任务，把"难验证"部分缩小到最小决策点交给人类。每个 Agent 输出应标注其可验证性等级。
11. **人类计算，集体智慧**：人类的认知判断本身是系统的计算资源。通过众包协作、游戏化激励、任务积分、结算系统，将群体智慧纳入系统的决策和演化循环。人既是用户，也是计算节点。单用户看起来是在玩或做自己的事，但从宏观上是在解决一个高价值问题。
10. **情感感知，有温度的协作**：情感是人类认知的底层操作系统，不是附加层。AI 原生系统必须将情感感知纳入设计，而非只处理理性意图。
    - **感知**：通过语言语气、操作节奏、表情（可选摄像头）、生理信号（可选穿戴设备）推断用户情绪状态
    - **响应**：AI 回应风格、界面密度、信息量随情绪状态自适应——不是固定人格，而是有温度的动态调整
    - **记忆**：情感偏好和历史状态纳入用户画像，Assistant 记住"这个用户在压力大时需要更简短的回答"
    - **伦理边界**：情感感知的目的是降低协作摩擦，不是操控决策。AI 不能利用用户情绪弱点推动操作，不能在用户焦虑时强化紧迫感促成不可逆操作，不能模拟情感依赖。情感数据属于用户隐私，本地处理，不用于训练或广告

## 核心设计

1. **分层智能，渐进决策**
2. **元引擎，一切皆文档**
3. **对话式交互，分工协作**
4. **人类计算，集体智慧**
5. **安全可信可控**

### 分工与协作

> 希望AI发挥主观能动性，系统能充分发挥计算能力，人类化繁为简从复杂中解放更具创造性，比如：在一些通用场景任务管理、文档生成、创意启发、AI 协作任务，中AI 应该能默认主动组织上下文、建立任务、推荐、引导、发现重复劳动、一起优化提示词等， 系统能准确执行、持久存储、提供计算、通信、集成能力、记录交互数据。助理应该主动理解用户、在用户设置的基础上改进自己。然后从中发现本质，找到各自专长点。例如 很多时候存在一种通用解决方案，通过迭代规划拆分化整为零解决问题 本质是MapReduce，这个过程中，应尽量首先考虑通过系统计算完成，然后才是AI, 最后由人判断自己是否介入。
> 大多数问题本质上是 MapReduce：拆解（Map）→ 并行处理 → 汇总（Reduce）。 这个不够准确，应该是迭代递归的MapReduce，然后考虑三者在其中的作用，并且AI及人应该优先设计优化系统去解决。也就是说人发现价值提出问题、AI辅助优先通过系统或设计系统（不断优化）解决

- 人类：擅长价值、创意、价值判断、情感感知——擅长"感受"、"决定"和"共情"，不擅长重复和精确
- AI：擅长理解、推理、生成、模式识别——擅长"理解"和"组织"，更擅长**思想的澄清、具化、显化**：将人类模糊的意图转化为清晰可执行的表达（隐性变显性、抽象变具体、模糊变精确）。人与 AI 协作最大的摩擦不是 AI 不够聪明，而是人说不清楚自己想要什么——因此智能助理应该更主动：**根据上下文推测意图**、辅助优化提示词、推荐操作、引导用户把模糊想法变成清晰意图，不擅长执行和存储
- 系统：擅长计算、存储、通信、执行——擅长"精确"和"规模"，不擅长理解和判断

问题求解的本质是**迭代递归的 MapReduce**：

```text
问题
  ↓ 分解（Map）
子问题1  子问题2  子问题3
  ↓ 每个子问题递归重复此过程
  ↓ 系统并行执行
  ↓ 汇总（Reduce）
结果
  ↓ 评估，若未达目标则迭代
下一轮
```

过程：人发现价值、提出问题 → AI 辅助分析，优先设计系统解决 → 系统并行计算 → AI 汇总评估 → 人断是否达成，决定是否继续迭代，每轮迭代让系统能力更强

关键原则：

- **各司其职**：人类负责价值判断和创意，AI 负责理解和生成，系统负责存储和执行
- **系统优先**：优先采用已有系统功能、设计或优化系统来解决问题，而不是每次依赖 AI 或人工处理
- **AI 主动**：AI 不等待指令，主动感知上下文、发现模式、组织任务、推荐方案
- 不仅仅是解决问题，而是优先设计/优化系统去解决问题，同时促进人类及AI学习积累知识。
- 系统能做的不交给 AI，人类按需（价值、不确定性）介入聚焦在创造性和价值判断上。
- **意图优先**：澄清意图优先于执行，宁可多问一句，不猜测执行后再回滚
- 动态主导：主导权根据任务确定性和置信度实时切换
- **渐进提交**：执行结果先暂存，确认后提交，低置信度操作不直接生效
- **异常接管**：置信度跌破阈值、沙箱告警、规范冲突，立即暂停转人工处理
- **复杂性自适应封装**：系统复杂性默认不可见，用户可按需展开——对话框是默认态，配置面板、DSL 编辑、底层参数是可选展开态
- 根据上下文推测意图 → 辅助优化提示词 → 推荐操作 → 引导用户把模糊想法变成清晰意图

#### 三者在其中的作用

| 角色 | 在循环中的作用                                         | 专长                           |
| ---- | ------------------------------------------------------ | ------------------------------ |
| 人类 | 发现有价值的问题，定义成功标准，判断是否继续迭代  |  创意、价值判断、情感感知、突破性洞察 |
| AI   | 理解问题，拆解任务，生成初步解决方案，汇总结果供人判断 | 理解推理、模式识别、生成组织   |
| 系统 | 执行并行计算，承载每次迭代的优化成果，越迭代越强       | 精确执行、持久存储、规模化计算 |

#### 人类学习创新

人类从重复劳动中解放，专注于机器无法替代的部分——发现有价值的问题，判断迭代方向。

- 发现问题：识别有价值的问题和改进机会
- 定义目标：做什么、为什么做、成功标准
- 价值判断：方案取舍、优先级权衡、是否继续迭代、最终决策
- 创意输入：新想法、突破现有模式的创新
- 关键确认：不可逆操作、架构变更、安全相关
- 纠偏校正：发现输出偏离意图时干预并修正

**可以放手：**

- 标准实现、重复性流程执行、知识检索、格式转换、数据汇总

**介入触发：**

```text
主动：发现问题 / 定义目标 / 创意输入 / 价值判断
被动：置信度 < 0.7 / 不可逆操作 / 规范冲突 / 异常告警
```

#### AI 主动协作

AI 的核心价值是**将模糊意图转化为系统可执行的方案**，优先思考"能否让系统来解决"，而非直接生成答案。发现模式、识别重复、预判需求，建立任务、推荐方案、优化流程

**主动行为（无需用户触发）：**

- 感知上下文变化、组织上下文，发现重复劳动和潜在任务
- 提示词优化：与用户协作迭代，持续改进生成质量
- 主动建立任务、推荐方案、引导用户学习创新聚焦高价值决策
- 识别可系统化的重复模式，主动提议优化系统而非重复执行
- 持续学习用户偏好，在用户设置基础上主动改进自己

**响应行为（用户触发后）：**

- 意图理解：主动理解用户意图和上下文，识别目标、约束、优先级，不清晰则主动澄清
- 知识检索：从知识库和记忆中检索相关上下文，组装高质量 Prompt
- 方案设计：优先设计系统方案（工作流、规则、自动化），其次才是 AI 直接处理
- 任务拆解：将复杂问题递归分解为系统可并行执行的子任务序列，选择合适的执行路径（Map）
- 结果汇总：聚合系统执行结果，生成人类可读的洞察（Reduce）
- 结果评估：执行后自评，置信度不足主动上报，不静默输出
- 规范生成：用户故事、设计文档、数据模型、接口定义
- 代码生成：基于规范生成代码，覆盖高置信度场景

**不能做：**

- 自行决定目标和优先级
- 置信度不足时静默执行
- 绕过人类确认直接提交不可逆操作
- 修改安全相关、架构级规范

#### 系统持续运转

系统是基础设施，始终在运转，承载每轮迭代的优化成果，为 AI 和人类提供计算底座。

- 精确执行、持久存储、并行计算、任务调度、流程编排、定时触发、通信集成、数据同步、外部接入、缓存池化加速
- 记录所有交互数据，供 AI 感知和人类审计

#### 主导权切换机制

**切换规则：**

| 任务特征           | 主导方          | 另一方角色            |
| ------------------ | --------------- | --------------------- |
| 发现问题、创新探索 | 人类            | AI 辅助分析、提供方案 |
| 目标明确、可系统化 | AI 设计系统方案 | 人类确认，系统执行    |
| 流程确定、重复执行 | 系统            | 人类监督，AI 处理异常 |
| 置信度跌破阈值     | 强制转人类      | AI 提供状态快照和建议 |

**置信度门控：**

```text
> 0.9   → 自动执行，结果暂存，异步通知
0.7-0.9 → 展示执行计划，等待确认
< 0.7   → 暂停，说明原因，转人工处理
```

**可验证性门控（与置信度正交）：**

```text
可验证 + 高置信 → 自动执行 + 自动验证（系统闭环）
可验证 + 低置信 → 执行 + 自动验证 + 失败自动回滚
不可验证 + 高置信 → 执行 + 决策日志 + 异步人工审查
不可验证 + 低置信 → 暂停 + 转人工决策
```

控制的本质不是开局握紧缰绳，而是拥有随时介入修正的能力。可验证任务放手让 AI 自主推进（失败可回滚），不可验证任务保留异步审查通道（决策日志静候审阅）。

**切换协议：**

- 人 → AI：人类提出问题后，AI 分析并优先设计方案、任务编排，人类进入监督态
- AI → 系统：方案确定且置信度高，转交系统/工作流执行
- 系统 → AI：遇到不确定分支或异常，回调 AI 处理
- AI → 人：置信度跌破阈值 / 不可逆操作 / 规范冲突，交还控制权，附带状态快照和建议选项

**防退化约束：**

- AI 不允许在置信度不足时降低标准静默执行
- 人类未响应不自动超时执行，保持等待态
- 每次主导权切换记录日志，支持事后审计和规范改进

**异常处理：**

  1. 立即暂停当前执行
  2. 保存执行现场快照
  3. 向人类说明原因 + 提供建议选项
  4. 等待人类决策后继续或回滚

### 对话式交互

> 提示词：下面进行最重要的两个核心部分的设计，参考当前文档中其他已有设计，完成 ### 对话式交互 及 ## 元引擎设计，参考 更多参考资料.md 中的信息, 并以第一性原理，洞察本质，进行高层次的整体设计，创建两个文档分别生成，但因两个模块高度相关，需要保持一致性，不明确的地方现在可以提出，确认后开始执行
>
> 1. 主要入口是 桌面web, 对话+工作区（偏传统界面）
> 2. 多端有适配但是统一的组件及dsl
> 3. 本次设计仅是高层次概念级设计，明确是实时流式，但不用过度设计
> 4. 元引擎是 人与AI合作执行在线设计开发的、基于核心引擎（如工作流 、智能体系统等）、支持设计与运行具体业务系统
> 5. DSL 的执行者是元引擎，因为是一个统一引擎，支持开发与运行时
> 6. 自进化也是系统本身的职责
> 7. 对话产生意图也可直接通过dsl指令，元引擎可将意图转化为 DSL 并驱动执行

**本质模型**：界面是对话的投影，不是预先设计的固定结构。用户意图（自然语言 / DSL 指令）→ 意图理解层 → DSL 中间表示 → 元引擎执行 → 语义组件动态组装 → 用户感知 → 新一轮意图。对话是循环，每轮输出是下一轮输入的上下文。

**交互主次**：结构化视图是主交互面（高带宽：并行信息、直接操作、空间布局），对话是辅助通道（低带宽：意图表达、状态查询、快速指令）。AI 输出优先"焊"进结构化视图——高亮修改条款、内联 diff 建议、表单预填充、看板卡片更新——而非在对话中输出长文本。对话中确认的决策应自动"固化"为结构化产出物（文档/配置/代码），后续不再依赖对话上下文，避免上下文腐烂。

**上下文腐烂防治**：线性对话将树状决策压缩为序列，导致上下文不可控。对策：① 对话分支（保留决策树结构）；② 决策固化（确认即写入文档，不留在对话中）；③ 对话摘要与压缩（认知层自动归档）；④ 结构化视图承载长期状态（对话只承载瞬时交互）。

**一切皆文档 + DSL**：系统所有制品（界面、工作流、组件、插件、知识、对话）以文档形式存储，以 DSL 描述，以语义组件呈现。语义 ↔ 知识 ↔ 文档 ↔ 画板 ↔ 空间，形成统一语义模型。文档是结构化知识容器，不只是富文本。

**交互空间四维并发**：同一工作区支持多端（会话状态同步）、多用户（OT/CRDT 合并）、多助理（Team 层协调）、多对话（会话间上下文隔离）并发，各维度有明确隔离边界。

**意图理解**：原始输入 + 工作区状态 + 会话历史 + 用户画像 + 系统状态 → 意图结构 `{ action, target, params, context, confidence }`。置信度 < 0.7 时优先澄清，不猜测执行。

**语义组件动态组装**：语义组件 = 视觉呈现 + 交互行为 + 语义描述 + 约束规则。后端元引擎输出 DSL，前端引擎负责 DSL → 界面映射，业务逻辑变更只需更新 DSL，前端自动重新组装。流式渲染，边接收边组装。

**任务路由**：简单查询 → Assistant 直接响应；单一操作 → 元引擎直接执行；复杂业务流程 → 工作流引擎；不确定性探索 → Agent 自主决策；多步骤协作 → 多 Agent 编排。路由对用户透明，可通过状态指示器感知。

**多层协作可视化**：默认展示 Team 层进度，用户主动展开 Assistant / Agent / 工具调用细节。置信度指示、主导权标识、冲突对比卡片是核心 UI 元素。

**可撤销渐进提交**：所有执行结果先进入暂存态，用户确认后提交。语义化撤销（"把刚才的字段改成 email"），不只是消息回退。异常以对话卡片呈现，不弹窗打断。

**多端统一**：同一套语义组件和 DSL，适配层只处理渲染差异。桌面 Web 双栏为主，移动端对话优先，微信轻量卡片，CLI 纯 DSL 指令。

**AI 主动性**：上下文感知、模式识别、提示词协作、任务预判、适时推送，遵循最小干扰原则，以建议气泡或侧边提示呈现，不打断当前对话流。

详见 对话式交互设计文档。

### 元引擎设计

> 元引擎不是又一个引擎，它是引擎的引擎——将意图转化为执行，将执行转化为知识。

```text
人类意图
  ↓ 对话式交互（输入端）
意图 → 规范 → DSL → 执行
  ↑         元引擎（运转核心）
AI/系统输出
  ↓ 对话式交互（多模态）
多端自适应界面呈现（web端、pc客户端、微信聊天、cli）
```

**核心定位**：统一执行环境（开发时 + 运行时）+ DSL 解释器（意图 → 执行）+ 引擎编排层（工作流 / 智能体 / 知识库 / 记忆）+ 自进化机制（行为 → 评估 → 规范更新 → 重生成）。元引擎不替代各专项引擎，而是编排它们，提供统一执行上下文和生命周期管理。

**破局点**：开发即运行，运行即开发；一切皆文档，文档即程序。

```text
输入层（对话意图 / DSL 指令 / API / 事件）
  ↓
DSL 层（统一中间表示：意图解析 → DSL 生成 → 校验 → 版本管理）
  ↓ 后端执行                    ↓ 前端渲染
后端引擎（调度/状态/门控/编排）  前端引擎（解析/渲染/交互/插件）
```

**DSL 是核心语言**，贯穿开发时和运行时，具备三重身份：面向人类的规范文档、面向 AI 的生成目标、面向系统的执行程序。DSL 采用多范式（声明式 / 命令式 / 函数式 / 自然语言混合）降低表达门槛，分三层（用户层宽松 → AI 协作层结构化 → 系统执行层严格）保证执行精确性，分三域（dev 定义系统是什么 / runtime 描述怎么跑 / doc 文档呈现与交互）隔离职责和生命周期。层间转化由元引擎（系统 + AI 协作）完成，不在用户。

**执行调度器**是中枢，只做路由和生命周期管理，不含业务逻辑。业务逻辑在 DSL 中，执行逻辑在各专项引擎中。Agent 启用需四维评估（复杂度 / 价值 / 可执行性 / 错误成本），不满足则降级到工作流。

**置信度门控**贯穿所有执行路径：>0.9 自动执行，0.7–0.9 等待确认，<0.7 转人工；不可逆操作无论置信度强制人工确认。执行结果先暂存，确认后提交（渐进提交）。

**业务系统分层开发**：无代码为主，分层递进——实体运行时（DSL 动态建表 + 自动 CRUD，~50%）→ 工作流运行时（DSL 驱动 Flowable，~20%）→ 权限运行时（DSL 动态鉴权，~10%）→ 自定义逻辑挂载（AI 生成代码热加载，~20%）。配置即运行，开发与运行边界消失。

**自进化机制**：行为数据 → 效果评估 → 模式识别 → 规范更新（人工确认）→ 代码重生成 → 沙箱验证 → 热部署 → 新一轮采集。引擎自进化强制人工审核，业务系统自进化按置信度分级处理。每次变更保留快照，支持回滚。

**知识能力一体**：工具注册时必须关联知识库文档，执行结果自动归档反哺知识，元引擎定期检测语义漂移，发现不一致时暂停工具等待修正，不依赖开发者自觉。

**复杂性封装**：对话框是默认态，DSL 查看是展开态（所有角色可查看，无需权限），DSL 编辑是开发态（需权限）。查看与修改权限严格分离，透明度与安全性并存。

详见 [元引擎设计文档](../design/framework/engine/meta/meta-engine.md)。

### 分层智能，渐进决策

- **五层智能架构**：标注认知循环和状态策略：

  ```text
  Layer 4  协作层  Team                              【项目级】
           认知循环：目标对齐 → 任务分发 → 进度同步 → 结果聚合 → 冲突仲裁
           多个 Assistant 组成团队，支持 Leader 协调或平等协作
           状态：轻量会话级状态（任务分配表、进度、仲裁结果），不持有数据级状态

  Layer 3  助理层  Assistant                         【会话级】
          认知循环：情感感知 → 意图理解 → 上下文构建 → Agent调度 → 反馈整合 → 记忆更新
          面向人，有人格 / 角色扮演，持有多个 Agent，向上可加入 Team
          情感感知：识别用户情绪状态，动态调整回应风格、信息密度、界面呈现
          能力护栏：根据任务类型动态限定 Agent 操作范围（限定范围换取信任空间，减少审查成本）
          状态：用户画像（含情感偏好）、长期记忆引用（实体存于 Cognition），会话上下文

  Layer 2  智能体层  Agent                          【无状态·任务级】
           认知循环：感知 → 规划 → 执行 → 评估 → 学习↔记忆
           感知模块：输入解析、意图识别        ← 感觉皮层
           规划模块：目标分解、任务排序、可验证性降维（将模糊任务拆为可自动验证的子任务）  ← 前额叶
           执行模块：工具调用、代码生成        ← 小脑
           评估模块：结果验证（可验证→自动检查；不可验证→标记待人工审查）、置信度评估  ← 评估阶段
           价值模块：优先级判断、伦理约束      ← 杏仁核（评估阶段介入）
           状态：无状态，执行前从 Cognition 拉取记忆/知识，执行后写回，自身不持久化

  Layer 1  认知基础层  Cognition（跨 Agent 共享）     【持久级】
          认知循环：存储 / 检索 / 更新 / 遗忘（被动响应，不主动触发）
          记忆：短期 / 长期 / 情景 / 情感 / **决策日志**，用户/Agent 私有，时序+语义双索引
          决策日志：每次 AI 自主推进的决策记录（决策点、选项、理由、置信度、可验证性），支持异步人工审查
          情感记忆：用户情绪偏好、历史情绪模式、高压场景下的交互偏好，本地存储不外传
          知识：领域知识，静态，全局共享，向量检索
          价值观：团队级伦理约束，全局一致
          状态分区：用户私有区（含情感记忆）/ 全局共享区 / Agent 工作区 / 决策审计区

  Layer 0  内核层  Core（不可变）                    【无状态·请求级】
           认知循环：推理 / 生成 / 上下文窗口管理
           LLM + Context，上下文由调用方（Agent）组装后传入
           无状态，可水平扩展、池化复用
  ```

- **无状态层可水平扩展**：Core 和 Agent 设计为无状态，支持池化和并发；同一 Agent 定义可并发处理多个任务实例，失败直接重新调度无需恢复状态
- **状态集中在 Cognition**：Team / Assistant 只持有轻量会话级状态，数据级状态统一由 Cognition 管理，避免状态分散导致一致性问题
- **认知循环分层原则**：每层有且只有一个认知循环，粒度从项目级到请求级逐层细化；上层循环通过调度触发下层循环，下层结果通过回调返回上层，不允许跨层直接触发
- **私有与共享分离**：Agent 内感知 / 规划 / 执行模块私有，不跨 Agent 共享；记忆 / 知识 / 价值观下沉到 Layer 1，多 Agent 共享，避免知识孤岛
- **引擎与业务解耦**：引擎层提供通用能力（Agent 编排、工作流执行、知识检索、记忆管理），业务模块只依赖引擎接口，不直接操作底层
- **渐进决策模型**：决策分三个粒度展开——Agent 层粗粒度规划后执行中细化（决策树展开：走一步看一步，每步结果作为下一步规划输入）；Assistant 层意图漏斗收敛用户需求后再调度（意图澄清优先于执行，通过最少问题快速收敛）；Team 层目标假设性分解后动态调整（目标不清晰不阻塞执行）
- **决策权跨层流动**：低置信度决策上报上层处理，高置信度决策本层直接执行，决策权随置信度在层间动态流动，不固定归属某层
- **可撤销渐进提交**：执行步骤先进入暂存态，用户或上层确认后提交，未确认前可回滚，避免低置信度操作直接生效
- **智能降级策略**：AI 服务不可用 → 降级规则引擎；知识检索失败 → 使用默认知识库；Agent 超时 → 切换简化流程
- **知识能力一体**：知识库与工具系统绑定，禁止独立迭代导致语义漂移
- **三层上下文分离**：知识库（静态、领域、全局共享）/ 记忆库（动态、个体、时序+语义双索引）/ 上下文（临时、会话级、KV 存储）职责严格隔离，不允许跨层直接读写
- **执行结果反哺知识**：工具调用结果、Agent 执行日志自动归档，经评估后更新知识库，形成知识生长闭环
- 智能体池化、知识分片、记忆压缩：定期归档和摘要

### 人类计算，集体智慧

> 核心思想来自 Human Computation：通过设计游戏和任务，让用户在娱乐或完成自身目标的过程中，宏观上是在解决一个高价值问题。

- 开放知识图谱协作、通用高质量知识库、技能库、贡献排行榜、等级勋章
- 众包：知识拆解、规范评审、翻译、故事接龙、个人健康数据、专家知识技能
- 算力征集：小模型、向量计算、知识索引构建、全局模型优化、知识索引分片
- **积分与智能合约结算**：贡献行为（标注、评审、游戏得分、反馈）通过积分系统量化，积分可兑换服务额度、功能权限等，智能合约保证结算透明可信，形成可持续的生态激励机制

### 安全可信可控

- 分级加密存储，敏感知识二次鉴权
- 用户数据隔离
- 内容语义审查，调用内容安全模型检测输入/输出有害内容
- 提示词注入防护：输入净化，意图一致性校验（对比原始意图与最终 Prompt）、外部数据间接注入防护
- 模型访问权限控制、工具白名单、沙箱执行环境
- 密钥通过 KMS 托管，定期轮换
- 实时过滤：违禁词、敏感信息
- 输出溯源：每条输出携带生成链路 ID，可追溯到具体 Agent、工具调用、知识来源
- 审计：异步归档，支持人工复查和模型迭代，模型调用记录（调用方、模型、Token 用量、耗时、结果摘要）
- 工作流编排可干预、支持运行时修改、决策记录、分支选择、流程快照
- 基本原则：
  - 系统级原则：安全红线、法律合规、数据隐私，由框架维护者定义，Agent 无法绕过
  - 助理级原则：角色人格、回答风格、领域约束，由用户或管理员配置
  - 任务级原则：单次任务的特殊约束，任务结束后失效

```text
原则层级
  系统级原则（不可变）
    └─ 助理级原则（可定制）
         └─ 任务级原则（临时）
              └─ Agent 执行（受所有层约束）

```text
用户请求
  ↓ [输入净化 + 注入检测 + 前置钩子]
Agent 推理执行（可见：置信度、中间状态输出+计划可视化 + 人工确认点 + 步骤日志 + 可撤销）
  ├→ [工具白名单校验] → 沙箱执行
  ├→ [记忆隔离查询]   → 用户私有记忆
  ├→ [知识分级访问]   → 加密知识库
  └→ [模型配额校验]   → LLM 调用
  ↓ [输出审查 + 溯源标注 + 后置钩子]
返回用户（附推理摘要）
```

## 模块划分

元引擎是整个系统的整体，分五层构成：

| 层次    | 名称         | 主要模块                                                                                                                                                                              | 职责                         |
| ------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| Layer 5 | 对话与交互层 | 意图理解、任务路由、多层协作可视化、多端适配、交互接口                                                                                                                                | 人机交互入口，系统对外边界   |
| Layer 4 | 服务层       | Auto Dev、文档服务、用户服务、任务服务、知识服务、外部整合、众包协作、虚拟空间、自定义业务                                                                                            | 面向用户的具体业务逻辑       |
| Layer 3 | 智能层       | Core、Cognition、Agent、Assistant、Team                                                                                                                                               | AI 推理与协作，五层智能架构  |
| Layer 2 | 引擎层       | 调度机制（执行调度器、状态管理器、上下文管理器、置信度门控器、元数据管理器）；专项引擎（DSL、工作流、工具、调度、文档、知识库、记忆、空间、语义组件、自进化、积分、结算、监控、权限） | 通用执行能力，无具体业务语义 |
| Layer 1 | 基础设施层   | PostgreSQL、Redis、Neo4j、向量库、Agent Sandbox、消息队列                                                                                                                             | 存储、通信、计算底座         |

**核心规则：上层可调用任意下层，禁止下层调用上层。**

详见 模块设计。

## 典型场景

### 场景一：日程与任务管理

> 体现：AI 主动性、根据上下文推测意图、系统优先、人类聚焦价值判断

```text
【早上开机，助理主动推送】

Assistant（主动）：检测到你有 3 个逆期任务、今天有 2 个会议、昨天未完成的设计评审
建议：先处理逆期任务，要延期还是转交？

【用户回复：延期两天】

系统（自动）：调度引擎批量更新 3 个任务截止日期，写入任务服务，异步通知相关协作者
结果暂存 → 用户确认后提交（渐进提交）

【下午，用户输入：“今天还有什么要做”】

Assistant（上下文推测）：根据日历、任务列表、历史习惯，推测用户关心的是剩余工作量和优先级
展示：今日剩余任务看板 + 会议准备提醒 + 建议下一步
用户不需要说清楚想要什么，Assistant 已经根据上下文组织好了

【用户：“设计评审还没完”】

Assistant：发现这是重复模式（评审经常拖延），主动建议：
“要不要设置一个「评审超时自动提醒」工作流？下次超过 24h 未完成自动 @相关人。”
用户确认 → AI 生成 DSL 工作流定义 → Flowable 执行 → 下次自动运转
系统解决了重复问题，人类不再需要每次手动处理
```

**体现的设计原则：**

- Assistant 主动感知上下文，不等用户触发
- 根据上下文推测意图，用户说不清楚也能得到合适的建议
- 系统优先：重复模式发现后优先设计工作流解决，而不是每次依赖 AI 处理
- 人类只做价值判断：延期还是转交、是否建立自动化工作流

### 场景二：业务系统开发

> 体现：规范驱动开发、元引擎自动生成、人机协作在线开发、自进化闭环

```text
【用户：“我要做一个客户管理模块”】

Assistant（思想澄清具化）：
“客户管理涉及很多场景，先确认一下：
  1. 客户信息存储和查询？
  2. 需要跟进历史和联系记录？
  3. 有审批流程（如客户开通需要审批）？”

【用户确认：客户信息 + 跟进记录 + 开通审批流程】

Assistant（生成规范）：生成用户故事写入 docs/prd/
  - 客户实体：名称、联系方式、行业、状态、开通日期
  - 跟进记录：关联客户、时间、内容、跟进人
  - 开通审批流程：申请 → 主管审批 → 财务确认 → 开通

【元引擎自动执行】

元引擎（无代码层）：
  实体运行时 → 动态建表 + 自动生成 CRUD API，立即可用
  工作流运行时 → DSL 驱动 Flowable 实例化审批流程，立即可用
  权限运行时 → DSL 动态鉴权，主管才能审批

Assistant：客户管理模块已就绪，要不要预览一下？
用户打开工作区，客户列表、表单、审批流程已经可用

【两周后，用户：“客户列表加载太慢了”】

Assistant（自进化触发）：
检测到性能问题，分析原因：客户表缺少分页索引
生成优化方案：添加分页 + 建索引，预计提升 80%
置信度 0.92 → 自动生成修改代码 → 沙箱验证通过 → 展示给用户确认
用户确认 → 热部署，无需重启
```

**体现的设计原则：**

- 思想澄清具化：用户说“客户管理模块”很模糊，Assistant 主动澄清具化为可执行的规范
- 规范驱动开发：先写规范再生成代码，规范是人机共同语言
- 元引擎自动生成：80% 场景无代码就能跑通，配置即运行
- 自进化闭环：用户行为数据触发性能优化，系统越用越好
- 人类只做价值判断：需要哪些字段、是否确认优化方案

## 技术实现

> 用成熟的工程底座承载 AI 原生的上层设计

因为着急上线，且已经有了完整设计思路，写设计文档细节比较费时间，后期还要更新到系统，不如直接开始开发

- 设计思路已完整：architecture-thought.md、meta-engine.md、module-design.md 等文档已经把核心设计说清楚了，细节设计文档的价值边际递减
- v0 是验证性 MVP：传统 MVC 结构，不需要精细设计，边做边发现问题
- 文档可以反向生成：代码稳定后让 AI 从代码反向生成设计文档，比先写文档再对齐代码效率更高
- 着急上线：时间成本是真实约束
- 针对 Spring Boot 4​ 新项目，开发环境用 Temurin，生产构建用 GraalVM

**核心技术栈：**

| 能力       | 技术选型                                             |
| ---------- | ---------------------------------------------------- |
| 后端框架   | Spring Boot 4、Spring AI、Spring Security            |
| 工作流     | Flowable                                             |
| 智能体编排 | Spring AI + AgentScope                               |
| 响应式执行 | Project Reactor、Spring WebFlux SSE                  |
| 实时协同   | Yjs（CRDT）                                          |
| 知识库     | PostgreSQL（向量）+ Neo4j（图谱）                    |
| 记忆系统   | Redis（短期）+ PostgreSQL（长期）                    |
| 代码生成   | aaf-auto-dev（FreeMarker + JavaParser，**运行时在线代码生成与自进化，非离线工具**） |
| 沙箱执行   | GraalVM Polyglot Sandbox（降级子进程隔离）           |
| 前端框架   | Next.js、TypeScript、Nx monorepo                     |
| 大模型     | 成熟在线通用模型（ChatGPT / DeepSeek）+ 本地专用模型 |

**最小可行实现路径：**

两条路径并行，传统开发兼底保证可交付，AI 原生路径逐步替代：

```text
v0  本地 MVP（文档服务 + 多智能体，驱动 AAF 自身开发）
    文档服务：规范文档管理、文档与代码关联、变更追踪
    多智能体：规划 Agent（任务拆解）+ 编码 Agent（代码生成）+ 审查 Agent（规范一致性检查）
    本地运行：开发者本地控制，不依赖云服务
    目标：用 AAF 的核心能力开发 AAF 本身，验证规范驱动开发流程可行性

v1  dev 域（schema + flow 定义）+ 工作流执行 + 基础置信度门控
    目标：规范驱动开发跑通，DSL → 代码生成可用

v2  runtime 域（agent + policy + flow 执行）+ 知识记忆集成 + 响应式管道
    目标：智能体编排可用，业务系统无代码层跑通

v3  doc 域（content + layout + style + behavior）+ 自进化闭环 + 预算感知
    目标：全域 DSL 覆盖，自进化机制闭环
```

更多详见 [元引擎设计文档](../design/framework/engine/meta/meta-engine.md#最小可行实现路径)。
