# 通用智能体迁移设计

面向普通用户迁移 Kiro CLI，保留其受控执行闭环，再隐藏文件路径、工具名和协议细节。用户只需要表达目标、理解影响、授予必要权限，并在重要节点做决定；系统负责把这些行为翻译成 Agent、工具和策略。

## 迁移的核心判断

开发者习惯通过参数和配置精确控制系统，普通用户则更依赖结果预期和生活语言。两者需要的底层能力相似，但心智模型不同。

例如，开发者可以理解“允许 `@finance/create_expense` MCP 工具”；普通用户更容易理解“允许报销助手在本次任务中创建一张报销草稿”。
因此迁移必须完成三次转换：从工具名转为业务动作，从技术作用域转为用户能判断的影响范围，从一次调用确认转为围绕任务的信任关系。

迁移遵循以下边界：

- 保留能力契约、最小权限、执行事件、会话状态和协议解耦。
- 隐藏 JSON、命令正则、STDIO、Hook 退出码和模型上下文窗口等实现细节。
- 不把“自动化”等同于“无需解释”，越自动越需要明确边界、预算和停止条件。
- 不把多 Agent 数量当作用户价值，用户只应看到责任主体和最终结果。

## 普通用户的产品模型

通用智能体可以收敛为五个用户概念。每个概念都能在 Kiro CLI 中找到技术来源，但需要重新命名和组织。

| 用户概念 | 用户理解 | 对应技术来源 |
| --- | --- | --- |
| 助手 | 谁在帮我，它负责什么 | Agent 身份、提示词、模型与欢迎信息 |
| 任务 | 这次要完成什么，现在到哪一步 | 会话、Todo List 入口、工具事件与回合状态 |
| 能力 | 它会做哪些业务动作 | 内置工具、Skill、Hook 和 MCP 工具 |
| 资料 | 它依据哪些文件、规则和知识做判断 | Resources、Steering、Skill、Knowledge 与会话上下文 |
| 权限 | 哪些动作可自动做，哪些必须问我 | 工具可见性、预授权、参数限制和执行前阻断 |

### 从技术配置到产品表达

身份和上下文应通过“助手卡片”呈现：名称、职责、适用任务、可使用的资料、维护者和版本。用户可以查看本次任务实际使用了哪些资料，解决隐式继承带来的不确定性。

执行能力应通过“应用连接”和“业务动作”呈现。例如连接企业邮箱后，权限不是笼统的“访问邮箱”，而是区分搜索邮件、读取正文、创建草稿和发送邮件。底层仍可使用 MCP 或原生工具，但用户只看到稳定的业务语义。

确定性规则应通过“自动化与安全规则”呈现。例如“创建报销草稿后检查金额和成本中心”可以由 Hook 或策略引擎完成；普通用户无需知道它在哪个生命周期触发。

## 目标交互模型

交互模式应由任务不确定性和风险决定，而不是由用户选择某个晦涩的运行参数。建议提供四种逐级增强的模式。

### 问答模式

助手只读取用户授权的信息并给出解释、建议或草稿，不产生外部变更。它适合政策咨询、资料总结和方案比较，也是首次使用时建立信任的默认模式。

### 协作模式

助手展示简短计划，边执行边反馈；低风险步骤可以连续完成，重要动作在执行前确认。用户可以随时暂停、修改目标或接管。
它对应 Kiro CLI 交互式会话的核心价值，但界面应把工具调用翻译为业务进度。

### 委托模式

用户确认目标、范围、权限、预算和完成条件后，任务可在后台推进。系统只在遇到授权缺口、关键分歧或失败恢复选择时打扰用户。
它借鉴 Headless 的端到端执行，但增加了普通用户需要的任务中心、通知和人工接管。

### 自动化模式

系统按事件或规则重复执行已验证的任务模板，例如“每周汇总销售异常并生成草稿”。 启用前必须经过试运行，并明确触发条件、频率、权限、预算、失败处理和停用入口。
模式可以升级，但不能静默升级。问答转协作时要说明将产生哪些变更；协作转委托时要补齐后台执行条件；委托转自动化时要把一次性意图固化为可审查规则。

## 目标架构与任务状态

目标架构可分成五层，每层只暴露稳定契约：

```text
渠道层：Web / Mobile / IM / Voice / API
  ↓ 统一消息、确认、通知
交互与任务层：意图澄清 / 计划 / 状态机 / 人工接管
  ↓ 任务契约
智能体运行层：主助手 / 专业助手 / 模型选择 / 上下文组装
  ↓ 能力调用
能力与资料层：Skill / 工具 / MCP 连接器 / 知识 / 记忆
  ↓ 策略约束
治理与基础设施层：权限 / Hook / 审计 / 预算 / 沙箱 / 可观测性
```

客户端协议可以借鉴 ACP 的事件化方式，但不应直接把协议对象当作产品对象。客户端至少要接收消息片段、业务动作、进度更新、待确认事项和任务结束事件，并能发送提示、确认、取消和接管请求。

后端任务状态需要比聊天消息更稳定。建议使用如下主路径：

```text
草稿 → 规划中 → 待授权 → 执行中 → 验证中 → 完成
                    ├→ 待用户补充 ─┤
                    ├→ 已暂停
                    ├→ 已取消
                    └→ 失败 → 待恢复或结束
```

普通用户界面不必展示全部内部状态，可收敛为“准备中、进行中、需要你、已完成、未完成”。每一次状态变化仍应保留原因、发起者、时间、输入输出摘要和可恢复点。

多智能体协作属于运行层实现。主助手可以委派专业助手，但对用户仍承担单一责任：解释为什么委派、汇总冲突、给出最终结果。由于现有 Kiro 内置资料没有完整公开 Subagent 调度协议，这里的状态和责任模型是迁移提案，不是对 Kiro 实现的复刻。

## 安全、确认与信任

确认的目标不是让用户不断点击“允许”，而是让用户在真正理解影响时做决定。权限应同时包含动作、对象、范围、时效和条件，例如“允许本次报销任务读取这 12 张发票”，而不是“允许读取所有文件”。

| 风险级别 | 典型动作 | 默认交互 | 必需保护 |
| --- | --- | --- | --- |
| 低 | 搜索、读取、总结 | 可在明确范围内自动执行 | 数据来源可见、敏感字段最小化 |
| 中 | 创建草稿、更新可恢复记录 | 首次确认后可按任务授权 | 变更预览、版本记录、撤销入口 |
| 高 | 对外发送、正式提交、批量修改 | 每个关键动作确认 | 明确接收方和影响范围、二次校验 |
| 极高 | 付款、删除、权限变更、不可逆操作 | 默认禁止自动执行 | 强认证、双重确认或人工审批 |

每个确认卡片都应回答五个问题：助手要做什么、为什么现在做、会影响什么、使用哪些数据、如何撤销或补救。系统策略仍要在用户确认之后继续生效，因为用户授权不能绕过合规、数据隔离或组织权限。

信任应逐步积累：先只读试用，再允许可撤销写入，最后才考虑受限委托。用户必须能在任务中心查看和撤销授权，停止后台任务，导出执行记录，并看到哪个助手、哪个连接器在何时进行了什么动作。

这套设计最终追求的不是“让智能体尽量自动”，而是“让用户用最低认知成本保持有效控制”。实施顺序和质量门槛见 [通用智能体交付路线](./general-agent-delivery-roadmap.md)。
