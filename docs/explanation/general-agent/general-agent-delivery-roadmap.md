# 通用智能体交付路线

通用智能体不宜从“全自动、多 Agent、全工具接入”起步。更稳妥的路线是先证明用户能看懂并控制一次执行，再逐步增加后台委托、重复自动化和专业协作。每个阶段都以可验证的信任能力作为进入下一阶段的门槛。

## 路线原则

能力建设遵循四条顺序关系：先可见再自动，先单任务再多任务，先可撤销再高风险，先统一责任再内部协作。底层可以提前预留协议和扩展点，但不应把尚未验证的复杂度暴露给用户。

范围管理也要区分“必须有”和“看起来先进”。MVP 必须有清晰状态、工具授权、取消、审计和失败说明；多 Agent 市场、自动触发器和复杂编排即使有展示价值，也不能替代这些基本能力。

## 分阶段推进

### 可信对话

目标是让普通用户安全完成第一个有价值的任务，并理解助手使用了什么资料、做了什么动作。

核心范围：

- 单一主助手，支持问答和协作模式。
- 会话保存、恢复、取消和清晰的任务结束状态。
- 只读工具与一个可撤销的写入场景，例如创建草稿。
- 业务化确认卡片、最小权限和完整审计记录。
- 统一的消息、动作、进度、确认和结束事件。

阶段内不建设后台长期任务、自动触发和用户可见的多 Agent 编排。退出条件是：所有外部写入均有授权依据和审计记录；高风险动作不会静默执行；用户可以解释任务当前状态并能主动停止。

### 引导任务

目标是把多轮聊天升级为可恢复的任务，让用户能审阅计划并在中途修改目标。

核心范围：

- 任务计划、步骤状态、检查点和失败恢复。
- “准备中、进行中、需要你、已完成、未完成”的统一用户状态。
- 资料范围展示、任务级临时授权和授权撤销。
- 结果验证与“完成条件未满足”的明确表达。
- 面向任务的历史记录，而不是只有消息时间线。

退出条件是：刷新、断线或人工暂停后任务可以从明确检查点恢复；系统不会把“模型结束回答”误判为“业务任务完成”；每个等待用户的任务都说明所需输入和不处理的后果。

### 受控委托

目标是在用户离线时继续执行条件完备的任务，同时保持预算、时限和人工接管能力。

核心范围：

- 委托模式、后台执行、通知和任务中心。
- 运行时间、调用次数、费用或资源预算。
- 应用连接器、OAuth 凭证托管和细粒度业务动作。
- 执行前后策略、结果校验、重试和降级路径。
- 超出权限、目标冲突或连续失败时自动暂停。

退出条件是：后台任务都有停止条件和负责人；超过预算或策略边界会自动停止；用户可以查看中间产物、撤销未提交变更并人工接管。只有在此阶段稳定后，才应允许用户把一次任务保存为重复自动化。

### 规模化协作

目标是复用成熟任务模板并引入专业助手协作，而不是单纯增加 Agent 数量。

核心范围：

- 经试运行验证的自动化模板、事件触发与版本管理。
- 主助手对专业助手的委派、结果汇总和冲突处理。
- 助手、Skill 和连接器的发布、审核、停用与兼容管理。
- 组织级策略、数据隔离、审计检索和异常检测。
- 多渠道接入，共享任务状态而非复制独立会话。

退出条件是：自动化变更可预览、可灰度、可停用；专业助手失败不会让责任链消失；连接器和助手升级有影响分析与回退方案。多 Agent 的收益应通过完成率、时延或专业质量证明，而不是通过“调用了多少 Agent”证明。

## 验收指标

指标需要先在试点用户中建立基线，再确定正式阈值。下表给出应持续采集的指标和建议质量底线，数值属于迁移方案，不代表 Kiro CLI 的产品指标。

| 维度 | 核心指标 | 建议底线 |
| --- | --- | --- |
| 任务价值 | 首次任务成功率、业务完成率、结果被采用率 | 每阶段相对上一阶段有可解释提升 |
| 交互成本 | 完成任务所需轮次、确认次数、等待用户时长 | 无意义重复确认持续下降，关键确认不可省略 |
| 可控性 | 取消成功率、恢复成功率、人工接管成功率 | 取消和接管请求必须被确定性处理并留痕 |
| 安全性 | 未授权写入、越权访问、不可逆误操作 | 生产环境为零容忍指标 |
| 透明度 | 动作可解释率、来源可追溯率、状态理解率 | 所有外部变更均可关联目标、授权和执行主体 |

阶段验收还应覆盖典型异常：连接器不可用、权限过期、用户长时间未响应、同一任务重复触发、模型输出与工具结果冲突、任务在执行中被撤销。只验证顺利路径，会高估委托模式的成熟度。

## 风险与决策门

| 风险 | 早期信号 | 控制方式 |
| --- | --- | --- |
| 模式混淆 | 用户不知道助手会不会执行 | 每次模式变化显式说明能力和影响 |
| 确认疲劳 | 用户不阅读就连续允许 | 合并同类低风险授权，保留高风险逐项确认 |
| 权限过宽 | 为避免打断而长期全量授权 | 任务级、对象级、限时授权，默认最小范围 |
| 上下文泄漏 | 助手使用了用户不知道的资料 | 展示有效资料清单，隔离个人、组织和任务上下文 |
| 后台失控 | 重试、费用或通知无限增长 | 预算、截止时间、熔断和全局停止入口 |
| 多 Agent 不透明 | 用户不知道谁负责最终结果 | 主助手统一负责，内部委派全程可审计 |

产品推进设置四个决策门：

- **可信门**：外部写入、授权、取消和审计闭环未完成，不进入引导任务。
- **状态门**：任务不能可靠暂停和恢复，不开放后台委托。
- **治理门**：预算、策略和人工接管未验证，不开放重复自动化。
- **责任门**：单助手责任链尚不清晰，不引入用户可感知的多 Agent 协作。

任何阶段若安全指标恶化，应先收缩自动化范围，而不是增加提示词补丁。确定性问题优先由权限、状态机、Hook 或策略引擎解决。

## 与 AAF 的衔接

本路线与 AAF 的五层结构可以自然对应，但这里只表达能力归属，不构成具体模块或版本承诺。权威领域契约、P0-P6 可执行拆分和退出标准统一见 [五层智能架构](../../design/framework/intelligent/architecture.md)。

交付路线与技术阶段按信任能力对齐：

| 通用智能体阶段 | 架构开发阶段 | 关键门禁 |
|---|---|---|
| 可信对话 | P2 | 控制模式、任务状态、有效上下文、最小 CompletionValidator |
| 引导任务 | P3 | 长期记忆治理、细粒度授权、连接器凭证、可恢复 HITL |
| 受控委托 | P4 | 预算、期限、通知、接管、多副本和复杂任务恢复 |
| 规模化协作 | P5 | 自动化试运行与版本治理、Team 和 A2A |

下表继续说明这些能力在 AAF 端到端分层中的归属：

| AAF 层次 | 本专题关注点 |
| --- | --- |
| 对话与交互层 | 多渠道消息、任务状态、确认卡片、通知和人工接管 |
| 服务层 | 面向报销、文档、知识等具体业务的助手与任务模板 |
| 智能层 | 主助手、专业助手、上下文组装和结果汇总 |
| 引擎层 | 工具、工作流、调度、状态、权限、Hook、记忆与可观测性 |
| 基础设施层 | 数据存储、事件传输、凭证托管、沙箱和隔离运行环境 |

下一步不应直接拆分全部技术模块，而应选择一个低风险、结果可验证的普通用户场景完成“可信对话”试点。试点通过后，再依据真实的确认次数、失败类型和接管行为细化任务状态与接口设计。
