# Kiro CLI Agent 能力解析

Kiro CLI Agent 是由角色、上下文、工具、权限、生命周期规则和会话协议共同组成的执行容器。它形成了“理解目标—装配上下文—选择能力—受控执行—验证反馈—保存状态”的闭环。面向普通用户迁移时，真正值得复用的是这个闭环，而不是终端命令和 JSON 配置本身。

## 结论与证据边界

本文把信息分为三类：**已证实能力**指内置文档或官方文档明确描述的行为；**功能推导**指由多项已证实机制共同支持、但需要在通用产品中重新抽象的能力；**未确认能力**表示当前资料只出现名称或开关，不能据此推断实现细节。

主要依据如下，外部页面访问日期均为 2026-07-23：

- Kiro CLI 内置文档：`Agent Configuration`（校验于 2026-07-14）、`Hooks System`（2026-07-14）、`kiro-cli chat`（2026-06-04）、`kiro-cli settings`（2026-07-01）、`kiro-cli acp`（2026-04-02）、`Steering Files`（2026-04-28）。
- 官方总览与交互：[Kiro CLI](https://kiro.dev/docs/cli)、[Chat](https://kiro.dev/docs/cli/chat/)、[Custom agents](https://kiro.dev/docs/cli/custom-agents/)、[Headless mode](https://kiro.dev/docs/cli/headless)。
- 官方上下文与扩展：[Steering](https://kiro.dev/docs/cli/steering/)、[MCP](https://kiro.dev/docs/cli/mcp/)、[Hooks](https://kiro.dev/docs/cli/hooks/)、[ACP](https://kiro.dev/docs/cli/acp/)。
- 项目已有的 [Kiro CLI 指南](../../guide/kiro/kiro-cli-guide.md) 负责操作说明，本文只讨论能力结构和迁移意义。

官方总览将 Interactive Chat、Custom Agents、MCP Integration、Smart Hooks、Agent Steering 和 Auto Complete 列为核心特性，并把 Headless Automation 列为主要用例。ACP 页面进一步说明同一 Agent Runtime 可以通过标准协议接入不同编辑器。本文据此提炼运行时核心功能；Auto Complete 属于输入效率增强，不作为通用智能体第一阶段的运行时核心。

内置文档随 CLI 构建发布，官方网页可能更新更快。出现冲突时，应记录资料日期，并以目标运行版本复核，不能静默选择其中一方。

## Agent 是一份可执行能力契约

Kiro CLI 的自定义 Agent 由配置文件定义。配置不只包含提示词，还同时声明“是谁、知道什么、能做什么、哪些操作可直接做、在什么时机附加规则”。这使 Agent 从一段提示词升级为可部署、可共享、可约束的能力单元。

| 构成 | 已证实机制 | 迁移意义 |
| --- | --- | --- |
| 身份 | `name`、`description`、`prompt`、`model`、欢迎语 | 用稳定角色和职责边界替代每轮重复提示 |
| 工具 | `tools` 限定可见工具，内置工具和 MCP 工具可组合 | 能力应按助手职责装配，而非全部默认暴露 |
| 信任 | `allowedTools` 预先批准指定工具或模式 | 将频繁确认转为可审查的最小权限策略 |
| 工具约束 | 可限制写入路径、Shell 命令和 Web URL | 权限不仅是“能否调用”，还要约束参数范围 |
| 上下文 | `file://` 资源始终加载，`skill://` 资源按需加载 | 区分稳定规则与临时专业知识，控制上下文成本 |
| 生命周期 | Hook 覆盖启动、提交消息、工具前后和响应结束 | 把校验、审计和自动化从提示词移到确定性机制 |
| 集成 | Agent 可配置本地、远程或注册表 MCP 服务 | 用标准连接器扩展业务系统，而非把集成写死 |
| 切换 | 可在启动时选择 Agent，也可在会话中切换 | 同一入口可以承载多个专业角色 |

例如，一个“报销助手”不应只是写着“你负责报销”的提示词。能力契约还应限定它只能读取指定发票、查询制度、创建报销草稿；正式提交或付款必须额外授权。只有角色、资料、能力和权限共同定义，用户才能判断助手会做什么、不会做什么。

## 能力地图

### 工具执行与信任

交互会话默认会对未预先批准的工具请求确认；启动参数可以信任全部工具或指定工具。Agent 配置还能进一步限制允许和拒绝的路径、命令与 URL。`preToolUse` Hook 在工具执行前运行，并可阻断调用，因此关键安全规则不必只依赖模型自觉遵守。

这套机制形成三层边界：工具是否对 Agent 可见、工具是否需要用户批准、即使获批后参数是否仍满足系统策略。面向普通用户迁移时，也应保留这三层，而不是压缩成含义模糊的“完全访问”开关。

### 上下文、规则与知识

Agent `resources` 支持固定文件和渐进式 Skill。内置文档说明 Skill 启动时只加载名称、描述和路径，完整内容在需要时加载；Steering 用于跨会话持续生效的规则。设置中还存在知识库、代码智能和自动上下文压缩能力的开关。

资料在“自定义 Agent 是否自动继承 Steering”上存在版本差异：2026-07-14 的内置 `Agent Configuration` 说明自定义 Agent 默认继承 Steering、Skill 和项目标记文件，并可通过设置关闭；较早的内置 `Steering Files` 与官方 Steering 页面则要求显式加入资源。因此产品必须展示本次实际生效的资料和规则，并针对目标版本验证继承行为。

### Hook 与质量闭环

官方 Hooks 文档确认 Hook 可以在 Agent 启动、用户提交、工具执行前后以及一轮响应结束时运行。它适合承载上下文补充、安全校验、日志、格式化和结果检查。

更重要的是，官方文档说明 Stop Hook 可以返回 `decision: "block"` 和原因，阻止 Agent 结束；该原因会作为新的用户消息反馈给模型，使其继续工作。例如测试未通过时，系统可以拒绝结束并要求修复。这说明 Hook 不只是外围自动化，而是可以形成“执行—验证—反馈—继续执行”的确定性质量闭环。

### MCP 与外部连接

官方 MCP 文档将其用途归纳为访问专业知识、连接外部服务和 API、扩展领域工具以及创建自定义工具，并支持工作区、用户级和 Agent 级配置。远程服务可以通过 OAuth 限定访问范围。

因此 MCP 的迁移价值不只是“增加工具数量”，而是建立统一的连接器边界：业务系统负责认证和提供原子动作，Agent 负责根据目标选择动作，权限系统负责限制可用范围。普通用户应看到“连接企业邮箱”“创建报销草稿”等业务语义，而不是服务器进程和协议参数。

### 会话、任务辅助与多模态

会话按目录保存，可恢复最近会话、按 ID 恢复、选择或删除会话；ACP 会话还持久化元数据和事件日志。设置中明确提供 Todo List、Subagent、Knowledge、Code Intelligence 和自动压缩的开关，ACP 初始化能力明确声明支持图片提示。

但当前检索到的资料没有完整说明 Subagent 的调度模型、并发策略和结果合并方式，也没有给出 Todo List 的状态协议。因此只能确认这些能力入口存在，不能把特定多 Agent 编排或任务状态机描述为 Kiro CLI 的既定实现。

## 交互模式

Kiro CLI 提供四种互补的交互方式，分别服务于探索、直接操作、自动执行和客户端集成。

| 模式 | 已证实行为 | 适合场景 | 主要限制 |
| --- | --- | --- | --- |
| 交互式对话 | 自然语言、多轮会话、流式工具进度、上下文管理、Agent/模型切换 | 需求尚需澄清、需要边做边确认 | 人必须在线，频繁确认会打断流程 |
| 终端直接操作 | 在聊天中用 `!` 前缀直接运行命令，不经过 AI | 用户明确知道要执行什么 | 属于专业用户快捷方式，不宜直接迁移给普通用户 |
| Headless | 提供初始提示后非交互执行，权限需预先授予 | CI/CD、脚本和后台任务 | 无中途输入、交互选择和终端 UI；授权不完整会阻塞 |
| ACP | 通过 JSON-RPC 创建、加载、提示、取消会话，并接收消息和工具事件 | 编辑器或自定义客户端嵌入 | 协议负责互操作，不直接定义普通用户体验 |

交互式与 Headless 并不是简单的前台和后台皮肤。前者可以在不确定时询问用户，后者必须在开始前拥有足够的目标、权限、预算和失败策略。普通用户产品若允许把交互任务转到后台，就必须先把这些前置条件固化为任务契约。

ACP 的价值在于把 Agent Runtime 与具体界面分离。官方文档明确提供会话创建、恢复、取消、模式和模型切换，并发送流式消息、工具调用、工具进度和回合结束事件。这意味着同一智能体内核可以服务 Web、移动端、桌面端或企业入口，客户端只负责用合适方式呈现状态和收集授权。

## 面向通用智能体的核心功能推导

### 从功能清单推导执行闭环

官方文档展示的是 Chat、Custom Agents、Steering、MCP、Hooks、Headless 和 ACP 等分散特性。把它们按一次任务的因果顺序重排，可以得到通用智能体的核心闭环：

```text
表达目标
  → 建立或恢复会话
  → 装配角色、规则、资料和专业能力
  → 生成并维护任务状态
  → 选择工具或连接器
  → 权限与策略校验
  → 执行业务动作并流式反馈
  → 验证完成条件
  → 完成、继续修复、暂停或转人工
  → 保存结果、状态和审计记录
```

其中“任务状态”和“面向普通用户的完成条件”不是当前 Kiro CLI 文档完整定义的独立产品能力，而是由 Headless 的端到端执行、ACP 的工具事件与取消能力、Hook 的结束阻断共同推导出的必要控制层。没有这层，系统只能知道一轮模型响应结束，不能可靠判断用户的业务目标已经完成。

### 应直接继承的核心能力

| 核心功能 | 官方证据组合 | 面向通用智能体的抽象 |
| --- | --- | --- |
| 统一交互与会话 | Chat、会话恢复、Headless、ACP | 同一任务可在对话、后台和不同终端之间连续流转 |
| 助手定义与专业化 | Custom Agents 的角色、工具、权限和上下文配置 | 可版本化、可共享、职责明确的助手模板 |
| 上下文与认知装配 | Steering、Resources、Skill、Knowledge | 按作用域和任务动态组装规则、资料与专业知识，并展示来源 |
| 能力路由与外部连接 | 内置工具、MCP、OAuth | 统一业务动作目录和连接器中心，由目标驱动选择能力 |
| 受控执行与质量闭环 | 工具信任、参数约束、PreToolUse、Stop Hook | 权限中心、策略引擎和“验证不通过继续修复”的完成门禁 |
| 事件化运行时 | ACP 消息、工具调用、进度、取消和回合结束事件 | 向任意客户端提供稳定的执行状态与人工接管接口 |

这些能力共同说明，通用 Agent Runtime 的最小单位不应是“一次模型调用”，而应是“一个带身份、上下文、能力、权限、状态和完成条件的任务执行实例”。

### 通用产品必须补齐的能力

Kiro CLI 的开发者界面可以依赖命令、文件和工具名称，普通用户产品还需要补齐以下产品层能力：

- **任务控制面**：保存目标、计划、步骤、检查点、预算、截止时间和完成条件，区分“回答结束”与“任务完成”。
- **业务语义权限**：把工具授权翻译成“对什么对象执行什么动作、持续多久、是否可撤销”，并提供影响预览。
- **可解释上下文**：展示本次使用的资料、规则、个人记忆和组织知识，支持纠正、移除和隔离。
- **结果与责任链**：关联目标、输入、工具动作、验证结果、授权人和执行主体，支持审计与人工接管。
- **持久记忆治理**：会话恢复不等于长期记忆；长期偏好和事实需要独立的授权、来源、纠错和遗忘机制。

这些是从 Kiro 能力闭环推导出的迁移需求，不应反向表述为 Kiro CLI 已经完整提供的普通用户功能。

### 应暂缓的能力

多 Agent 自动编排、助手市场和无人值守高风险操作不应成为第一阶段核心。现有资料尚不足以确认 Subagent 的完整协议，而普通用户场景还需要先验证单助手的任务状态、权限、质量门禁和责任链。

因此建议按优先级推进：先完成单助手的可信执行闭环，再开放受限后台委托，最后以可量化收益决定是否引入多 Agent。Kiro CLI 最值得迁移的不是“可以调用多少 Agent”，而是自然语言与确定性系统共同约束执行的方式。
