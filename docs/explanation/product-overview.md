# AAF 产品概述

> AAF（Agentic App Framework）是面向开发人员的生产级 AI 原生框架。AI 是架构的一等公民，不是附加物。

## 解决什么问题

当前 AI 应用开发面临三个核心张力：

- **人 vs AI**：谁主导？谁执行？边界如何动态调整？大多数系统要么 AI 越权自动执行，要么人工干预太多失去 AI 价值
- **通用 vs 具体**：框架该管多少？业务该怎么隔离？通用框架无法感知业务语义，业务代码又充斥重复实现
- **效率 vs 质量**：快速生成 vs 规范约束，AI 生成的代码难以与人类维护的规范保持一致

AAF 的答案：**让规范成为人类和 AI 的共同真理来源**，通过人/AI/系统三者明确分工，将模糊意图转化为可执行的系统。

## 产品定位

AAF 是一套**规范驱动、AI 原生**的应用开发框架，目标是让开发者用 AI 协作的方式构建 AI 原生应用——不只是在应用里集成 AI，而是用 AI 驱动整个开发过程本身。

**判断标准**：把 AI 拿掉，系统还能正常运转吗？能 → AI 增强；不能 → **AI 原生**。AAF 是后者。

## 目标用户

| 用户类型 | 场景 | 核心诉求 |
|---------|------|---------|
| 框架开发者 | 构建和维护 AAF 本身 | 自举式开发，框架是自己最真实的压力测试场 |
| 业务开发者 | 基于 AAF 构建业务系统 | 快速搭建 AI 原生业务，少写重复代码，AI 承担实现工作 |
| 普通用户 | 使用 AAF 驱动的应用 | 通过对话完成复杂任务，可视化搭建工作流和知识库 |

## 核心价值

### 对业务开发者

- **规范驱动**：先写规范再写代码，规范是人类和 AI 的共同真理来源，减少沟通成本和返工
- **AI 自动开发**：规范 → DSL → 代码生成 → 热部署，AI 承担重复性实现，开发者聚焦设计和决策
- **元引擎自动生成**：80% 场景无代码就能跑通——实体建表、CRUD、工作流、权限，配置即运行

### 对普通用户

- **对话即操作**：用自然语言完成复杂业务操作，不需要学习复杂界面
- **可视化搭建**：无需编写代码，拖拽搭建工作流、技能、知识库
- **多端统一**：同一套体验，适配 Web / 小程序 / APP

### 典型场景

**场景一：日程与任务管理**

早上开机，助理主动推送逆期任务和今日会议，用户说"延期两天"，系统自动批量更新并通知协作者。下午用户问"今天还有什么要做"，助理根据上下文直接给出优先级看板，不需要用户说清楚想要什么。发现评审经常拖延后，助理主动建议建立"超时自动提醒"工作流，用户确认后系统自动运转，不再需要每次手动处理。

**场景二：业务系统开发**

用户说"我要做一个客户管理模块"，助理主动澄清具化为可执行规范（客户实体、跟进记录、开通审批流程），元引擎自动建表、生成 CRUD API、实例化审批工作流，立即可用。两周后用户反馈列表加载慢，系统检测到性能问题，自动生成优化方案，沙箱验证通过后展示给用户确认，热部署无需重启。

## 人机协作模型

AAF 的核心差异化是三者明确分工、动态协作：

| 角色 | 专长 | 在系统中的作用 |
|------|------|--------------|
| 人类 | 价值判断、创意、情感感知 | 发现问题、定义目标、最终决策 |
| AI | 理解、推理、生成 | 将模糊意图转化为可执行方案，优先设计系统解决 |
| 系统 | 精确执行、持久存储、规模化计算 | 承载迭代优化成果，越用越强 |

**关键原则**：系统能做的不交给 AI，AI 能做的不交给人。主导权根据任务确定性动态切换——确定性任务走工作流，不确定性任务走 Agent，置信度不足时强制转人工。

## 产品边界

**AAF 做什么**：
- 提供 AI 原生应用的开发框架和运行时
- 提供规范驱动的开发流程和工具链
- 提供多智能体协作的基础设施
- 支持普通用户可视化搭建工作流、技能、知识库

**AAF 不做什么**：
- 不是通用 Web 框架（不替代 Spring Boot 本身）
- 不绑定特定 AI 模型（模型无关，通过 Spring AI 适配）
- 不替代人类的价值判断和创意决策

## 需求评估原则

评估新需求时，对照以下原则判断是否符合产品方向：

### 核心能力边界

| 能力类型 | AAF 框架层提供 | 业务层/示例层实现 |
|---------|---------------|------------------|
| 工作流引擎 | ✅ 通用工作流编排、状态管理 | 具体业务流程定义 |
| 知识库管理 | ✅ 向量存储、语义检索、知识图谱 | 领域知识内容 |
| 多智能体协作 | ✅ Agent 编排、记忆系统、对话管理 | 具体 Agent 技能 |
| 外部系统集成 | ✅ 标准化 API/MCP 接口 | 具体系统对接 |
| 模型推理 | ✅ Spring AI 适配层（模型无关） | 具体模型选型、微调 |
| 多模态识别 | ✅ OCR/图像理解（通过在线多模态 API） | 具体单据模板、领域术语 |

### 部署模式

AAF 采用**在线部署优先**策略，通过云端大模型 API 获得最佳 AI 能力。

**为什么优先在线部署**：

| 维度 | 在线部署 | 离线/私有化部署 |
|------|---------|----------------|
| 模型能力 | ✅ 最新最强模型（GPT-4o、Claude 3.5、Gemini 2）| ⚠️ 本地模型能力有限，多模态/长上下文受限 |
| 多模态支持 | ✅ 原生支持图像、音频、视频理解 | ⚠️ 需自行部署多模态模型，硬件要求高 |
| 运维成本 | ✅ 零运维，按需付费 | ❌ 需自建 GPU 集群、模型更新、故障处理 |
| 硬件投入 | ✅ 无需 GPU | ❌ 高端显卡（如 5090）成本高、折旧快 |
| 模型更新 | ✅ 自动获得最新能力 | ❌ 需手动更新、重新微调 |
| 弹性扩展 | ✅ 按需扩容 | ❌ 容量受限于本地硬件 |

**离线部署的适用场景**：
- 法规强制要求数据不出境（金融、政务、医疗）
- 网络隔离环境（军工、涉密单位）
- 极低延迟要求（实时控制系统）

> 对于一般企业用户，在线部署 + 数据安全措施是更优选择。

**在线部署的数据安全保障**：

AAF 通过多层安全机制降低在线部署的数据风险：

| 安全层 | 措施 | 说明 |
|--------|------|------|
| **传输加密** | 强制 HTTPS + TLS 1.3 | API 通信全程加密 |
| **数据脱敏** | 敏感字段自动脱敏后再调用 LLM | 金额、姓名、身份证等字段替换为占位符，结果返回后还原 |
| **多 LLM 分散** | 敏感数据分片调用不同 LLM | 单个 LLM 只看到部分数据，无法还原完整业务语义 |
| **本地预处理** | 结构化提取在本地完成 | OCR、格式解析等不涉及 LLM，数据不出域 |
| **审计日志** | 完整记录 LLM 调用内容 | 可追溯、可审计、支持合规检查 |
| **数据留存控制** | 选择不留存训练数据的 API | 使用 OpenAI/Anthropic 的企业版 API，明确数据不用于训练 |
| **私有化 LLM 网关** | 可选部署企业专属 API 网关 | 统一管控、流量审计、敏感词过滤 |

**多 LLM 并行的安全增强**：

```
原始数据: "张三向李四转账 50000 元"
    ↓ 分片脱敏
LLM-A 收到: "[人名A]向[人名B]转账[金额]元" → 理解意图
LLM-B 收到: "张三, 李四" → 实体识别（无金额上下文）
LLM-C 收到: "50000" → 数值校验（无人名上下文）
    ↓ 本地聚合
最终结果: 结构化转账记录（LLM 无法还原完整信息）
```

**框架层支持**：
- Spring AI 适配层：统一接口，可切换在线/本地模型
- 数据脱敏组件：自动识别敏感字段，调用前脱敏、返回后还原
- 多 LLM 路由：按数据敏感度自动分发到不同模型
- 审计中间件：记录所有 LLM 交互，支持合规审查

### 数据安全原则

对于数据敏感场景，AAF 的技术方案：
- **数据不出域**：支持私有化部署，数据存储在用户自有基础设施
- **模型本地化**：通过 Spring AI 适配本地模型（Ollama、vLLM 等）
- **传输加密**：API 通信强制 HTTPS，敏感字段加密存储
- **审计追溯**：所有 Agent 操作记录完整审计日志

### 评估检查清单

新需求评估时，回答以下问题：

1. **是否符合产品定位**：是 AI 原生能力还是传统功能？
2. **框架层 vs 业务层**：该能力应该在框架层通用提供，还是作为业务示例？
3. **核心能力依赖**：需要哪些框架核心能力支撑？是否已具备？
4. **部署模式影响**：是否影响部署模式选择？有无离线要求？
5. **数据安全要求**：是否有数据不出域、本地化等特殊要求？
6. **用户接受度**：如果需要在线部署，如何让用户接受？（数据加密、审计、合规认证等）

```text

v1.0.0  生产就绪（性能、安全、可观测性、多租户）
```
