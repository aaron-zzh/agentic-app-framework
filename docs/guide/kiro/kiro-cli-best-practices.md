# Kiro CLI 最佳实践参考文档

## 1. Token 节省策略

### 1.1 会话管理
- 每次对话聚焦一个任务，完成后开新会话
- 长对话会累积历史 token，导致成本上升和上下文污染
- 避免在同一会话中混合不相关任务

### 1.2 高效提示词
```
# ❌ 模糊需求（多轮追问，浪费 token）
"帮我优化一下这个项目"

# ✅ 精确需求（一轮搞定）
"在 src/api/users.ts 的 getUsers 函数中加分页，参数用 page/pageSize，返回 total"
```

### 1.3 让工具代替对话
- 给文件路径，让 agent 自己读，而非手动贴代码
- 让 agent 跑测试验证，而非你手动测完再描述结果
- 让 agent 读配置文件判断项目结构，而非你解释

### 1.4 节省效果参考

| 做法 | 预估节省 |
|------|----------|
| 短会话，任务完成就新开 | 50%+ |
| 给文件路径而非贴代码 | 30%+ |
| 一次说清需求 | 省 2-3 轮对话 |
| 复杂调研用 sub-agent | 主上下文省 60%+ |
| 只要代码不要解释 | 输出省 40% |

## 2. Sub-agent 使用指南

### 2.1 何时不需要 sub-agent
- 单文件修改
- 查找某个函数/符号
- 简单的 bug 修复
- 直接做比分发更快更省

### 2.2 何时使用 sub-agent
- **大范围代码调研**：需要读几十个文件了解架构
- **并行独立任务**：如同时改前端和后端
- **流水线工作流**：研究 → 实现 → 审查

### 2.3 推荐配置
- 一般 **2-3 个 stage** 足够，不要过度拆分
- 典型模式：`调研 → 实现` 或 `调研 → 实现 → 审查`

### 2.4 示例：调研 + 实现流水线
```
stage 1: research (sub-agent)
  - 扫描代码库，理解架构和约定
  - 输出：相关文件列表 + 实现建议

stage 2: implement (主 agent，依赖 stage 1)
  - 基于调研结果直接编码
  - 上下文干净，只包含必要信息
```

## 3. 项目开发工作流

### 3.1 首次接触项目
1. 让 agent 读 `package.json` / `Cargo.toml` / `pom.xml` 等配置
2. 让 agent 浏览目录结构
3. 说明你要做什么，agent 会基于项目上下文行动

### 3.2 功能开发
1. 用一句话描述需求 + 涉及的文件路径
2. agent 读代码 → 实现 → 跑测试 → 返回结果
3. 复杂功能先让 agent 出方案，确认后再实现

### 3.3 Bug 修复
1. 提供错误信息或复现步骤
2. 让 agent 搜索相关代码定位问题
3. agent 修复 → 跑测试验证

## 4. 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 把整个文件贴到对话里 | 给文件路径让 agent 自己读 |
| 一个会话做 10 件事 | 一个任务一个会话 |
| 每个小任务都开 sub-agent | 简单任务直接做 |
| 需求模糊反复修改 | 一次描述清楚 |
| 要求 agent 解释每一行代码 | 只在需要时要求解释 |
| 手动描述项目结构 | 让 agent 自己探索 |

---

## 5. 总结

**核心原则**：需求写清楚 + 会话保持短 + 让工具干活

**最佳配置**：主 agent 做实现 + 1-2 个 sub-agent 做调研/审查。大多数任务一个 agent 直接干最省 token。
