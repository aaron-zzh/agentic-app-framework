## 规范

完整规范见 [Skill 规范](../../docs/reference/team/skills/Readme.md)。

## 创建流程

### 1. 明确技能范围

向用户确认：
- 技能要解决什么问题？（一个连贯的工作单元，不要太宽也不要太窄）
- 触发场景是什么？（用户会怎么说来触发它）
- 智能体自身不知道的专业知识是什么？（项目约定、特定 API、边缘情况）

### 2. 创建目录和 SKILL.md

```text
.kiro/skills/{skill-name}/
├── SKILL.md          # 必需
├── references/       # 可选：详细文档（按需加载）
├── scripts/          # 可选：可执行脚本
└── assets/           # 可选：模板、资源
```

`name` 规则：小写字母 + 数字 + 连字符，1-64 字符，不以连字符开头或结尾，必须与目录名一致。

### 3. 编写前置元数据

```yaml
---
name: {skill-name}
description: '{功能描述}。USE WHEN: (1) 场景一、(2) 场景二。'
---
```

description 要求（≤1024 字符）：
- 用祈使语气："USE WHEN..."，不用"此技能用于..."
- 关注用户意图，不是实现细节
- 列出具体触发场景，包括用户没有直接提及关键词的场景
- 提供清晰的默认行为，简要提及替代方案

### 4. 编写正文指令

原则：
- **只写智能体不知道的内容**：项目约定、特定流程、边缘情况。省略通用知识
- **流程优于声明**：教"如何处理一类问题"，而非"对特定实例产出什么"
- **提供默认值**：多种方案时选一个默认，简要提及替代
- **校准控制力**：灵活的地方解释 why，脆弱的地方给精确步骤

推荐章节（按需选用）：
- 规范文档链接
- 分步指令
- Gotchas（坑点）：违背合理假设的项目特定事实
- 输出格式模板
- 检查清单（多步骤工作流）
- 验证循环（执行→验证→修复→重复）

### 5. 拆分大型内容

SKILL.md 控制在 500 行 / 5000 token 以内。超出部分移到 `references/` 并在 SKILL.md 中说明何时加载：

```markdown
如果遇到 X 情况，读取 [详细说明](references/x-detail.md)。
```

避免泛泛的"详见 references/"——明确触发条件。

## 优化现有技能

### 优化 description

1. 找出失败场景：哪些该触发的没触发？哪些不该触发的误触发了？
2. 该触发没触发 → description 太窄，扩大范围或补充上下文
3. 不该触发却触发了 → description 太宽，增加边界说明或澄清与相邻技能的区别
4. 避免塞入特定查询的关键词（过拟合），找通用类别解决

### 优化指令

1. 读智能体的执行轨迹，不只看最终输出
2. 智能体在非生产性步骤上浪费时间 → 指令太模糊或选项太多
3. 智能体犯了需要纠正的错误 → 加入 Gotchas 章节
4. 智能体每次都重构相同逻辑 → 提取为 `scripts/` 中的可复用脚本

## 质量检查清单

- [ ] `name` 与目录名一致，符合命名规则
- [ ] `description` ≤1024 字符，包含具体触发场景
- [ ] SKILL.md ≤500 行
- [ ] 只包含智能体自身不知道的专业知识
- [ ] 详细参考资料在 `references/` 中，SKILL.md 说明了何时加载
- [ ] 针对真实任务测试过触发和执行效果
