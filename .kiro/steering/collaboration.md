# 协作流程

详见 [docs/ai-development.md](../../docs/ai-development.md)。

## 角色

协调者(kiro_default) + 职能agent(product/architect/tester/reviewer) + 开发群组(developer-xxx，可并行) + 人类用户

## 人机协作模式

采用**异步协作**：AI 团队自主推进任务，人类按需介入。

**核心原则**：AI 不等待人类审批，完成即提交；人类不被阻塞，按需检查。

**AI 侧职责**：
- 完成任务后立即提交代码并记录到工作日志
- reviewer 检查后在 review.md 中标注风险等级
- 发现需要人类决策的事项，记录到工作日志并标注 `🔴 需人类决策`，继续推进其他任务

**人类侧职责**：
- 按需查看工作日志和 review.md，优先关注高风险项
- 对 `🔴 需人类决策` 的事项给出决策
- 版本发布前做最终验收

**风险等级**（reviewer 在 review.md 中标注）：

| 等级 | 含义 | 人类响应 |
|------|------|---------|
| 🟢 低风险 | 常规变更，符合规范 | 可跳过，批量确认 |
| 🟡 中风险 | 有设计取舍或边界情况 | 建议抽查 |
| 🔴 高风险 | 架构变更、破坏性变更、安全相关 | 必须审查 |

## 流程

想法 → product(requirement.md) → architect(design.md) → developer-xxx(代码) → tester(test-report.md) → reviewer(review.md) → 质量门控

## 质量门控

blocker=0 且 major≤2 才通过。不通过则回退：需求问题→product，设计缺陷→architect，实现问题→developer，测试不足→tester。

## 文档驱动

智能体间通过文档沟通，每个任务产出到 `docs/tasks/{版本}/{任务名}/`。

模板在 `docs/tasks/_template/` 下：requirement.md → design.md → dev-log.md → test-report.md → review.md

## 接口契约

模块间通过 Java 接口交互，接口由提供方定义，使用方只依赖接口。

## 变更规则

- 改接口签名 → 协调者同步所有使用方
- 加新接口 → 定义方自行添加
- 改 common/ → 必须通过协调者评估影响

## 任务管理

[docs/backlog.md](../../docs/backlog.md) 是所有待办的唯一来源。

**任务编号**：
- 格式 `AAF-{三位序号}`，全局递增，不按版本重置
- 新任务取当前最大编号 +1
- 已完成条目不编号
- 提交时在脚注中关联：`Task: AAF-XXX`（详见 [提交规范](../../docs/commit-conventions.md)）

**任务来源**：
- 路线图拆解 → 功能任务
- 改进意见采纳 → 优化任务
- 工作日志待办 → 转入 backlog

**工作流**：
- 会话开始 → 协调者读 backlog，选取任务执行
- 会话结束 → 更新 backlog 状态，写工作日志（只记已完成和关键决策）
- 新待办 → 直接写入 backlog，不散落在其他文档

**任务排序**：
- 新任务插入时，协调者评估依赖关系和优先级，插入到合适位置
- 被依赖的任务排在前面，依赖方排在后面
- 有依赖时在任务描述后标注 `(依赖: AAF-XXX)`
- 同优先级无依赖的任务可并行，顺序不限

**任务拆分**：
- backlog 级别的任务由协调者创建和管理，其他 agent 不直接修改 backlog
- 开发者可在自己的 dev-log.md 中将大任务拆分为实现步骤，无需协调者审批
- 拆分过程中发现需要新增 backlog 任务（如缺少依赖模块、需要新接口），在 dev-log.md 中提出，由协调者评估后写入 backlog

**维护规则**：
- backlog 只保留当前版本 + 待排期，控制在 30 条以内
- 版本完成后，已完成和已取消的条目移入 `docs/tasks/archive/` 备份
- 具体任务的执行细节在 `docs/tasks/{版本}/{任务名}/` 中，backlog 只记标题和状态


## 风险管理

协调者在迭代开始时识别风险，开发过程中持续更新。

| 风险类型 | 示例 | 应对措施 |
|---------|------|---------|
| 上下文溢出 | agent 任务过大导致中断 | 拆分任务，精简 resources |
| 接口不一致 | 模块间接口理解偏差 | architect 先定义接口，开发前确认 |
| 需求变更 | 开发中发现需求理解有误 | 按[需求管理规范](../../docs/requirement-management.md)走变更流程 |
| LLM 输出不稳定 | 生成代码不符合规范 | reviewer 检查 + 质量门控拦截 |
| 依赖阻塞 | 模块 A 等待模块 B 的接口 | 接口先行，mock 实现解耦 |

风险记录在迭代的 `dispatch-log.md` 中，标注状态（开放/已缓解/已关闭）。

## 迭代节奏

每个版本为一个迭代，目标周期 2-4 周。

- **迭代计划**：确认目标、选取任务、评估工作量
- **迭代执行**：按任务流程推进，每次会话更新 backlog 和工作日志
- **迭代评审**：验收完成功能，检查验收标准
- **迭代回顾**：分析效率、总结改进、更新规范

详细节奏定义见 [docs/schedule.md](../../docs/schedule.md)。

## 版本交付检查清单

版本发布前，协调者逐项确认：

- [ ] 所有 P0/P1 任务已完成
- [ ] 质量门控通过（blocker=0，major≤2）
- [ ] 编译通过，测试全部通过
- [ ] 接口变更有对应的破坏性变更说明
- [ ] 数据库迁移脚本就绪（如有）
- [ ] 文档已更新（README、架构文档、API 文档）
- [ ] 知识库已补充本迭代的设计决策和踩坑记录
- [ ] 发布说明已编写（`docs/tasks/{版本}/release-notes.md`）
- [ ] backlog 已归档，待排期任务已整理
